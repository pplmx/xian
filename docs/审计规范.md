# 审计规范 —— 一条判据要怎样才能算数

这份文档被 `core/contentReachabilityAudit.spec` 的文件头点名，**却从来没写过**。
那条引用一直指着一片空气（第 168 轮才发现，见 `core/docRefExistence.spec`）。

它要说的其实只有一句:**判据的价值等于「它能不能被打红」**。下面是这十几轮里
反复踩到的形状，以及把它做成可执行规则的办法。

## 一 · 每条判据都要附一份故障注入配方

新增一条判据时，先回答:**如果我把实现改坏，这条会不会红？**

具体的做法是把实现**临时**改坏一次，跑一遍，确认它红了，再改回来。

没有这一条，判据很容易写成「永远绿」——它看着像守卫，实际只是让测试计数 +1。
本轮修 `apexDeeds` 时连写三版都没红:

```text
第 1 版  「汇总分母 == 条数」     分母仍是 8，只是上界是 5 —— 红不了
第 2 版  「三条标签存在」         存在不等于已满 —— 红不了
第 3 版  「做过之后有没有翻成已满」 才真的钉住
```

三次都以为写好了。**故障注入不是形式,它是唯一的证明。**

## 二 · 判据要认「那件事」，不要认「那个写法」

把「当时正确的写法」写成字面量，是这一族错误的共同形状。踩过五次:

| 判据钉的东西 | 它当年拦的是什么 | 它后来守住了什么 |
| --- | --- | --- |
| `formatPercent(BT_FAIL_EXP_LOSS)` | 视图手抄数字 | 守住了那个**错的** 18% |
| `` 离{{row.nextStage}} `` | 要报下一步 | 守住了那句读反的话 |
| `mainIdx === MAIN_CHAIN_MAX_STEPS` | 守卫存在 | 守住了「永远推不完」 |
| 天道熔炉的闭标签位置 | 按钮包住文字 | 格式化一改就误报 |
| 「每秒」的固定搭配 | 单位不重复 | 连错的文案一起守 |

改法都是同一条:**换成「哪件事必须成立」**。例:不钉
`formatPercent(BT_FAIL_EXP_LOSS)`，改钉 `breakthroughFailLoss(` —— 意图不变
（不手抄），但不再指定手抄哪个数。

## 三 · 扫源码的判据：注释不是正文

注释里**举例**说明旧写法时，那段字会被「不许出现这一串」的判据命中。
`src/core/breakthroughCost.spec.ts` 与 `src/ui/rateUnit.spec.ts` 里各有一份
`stripComments` 先抹掉注释再判。

与此同时,**注释本身也要被检查**:「去读 docs/xxx.md」这类指路写在注释里，
而 `scripts/docs-check.mjs` 只扫文档正文。`core/docRefExistence.spec` 补的就是这一层。

## 四 · 判据自己的输入要能造出那个局面

- 造「整屏 0%」要先二分搜到 `exp 200 → level 25`（`入门` 的起点），
  `exp 1` 只到 level 0.17，断言会落空；
- 跳级到 `major 20` 的探针，主线卡在 1/32 —— 前几节吃的是计数器
  （`explores 1` / `kills 10`），跳级玩家从没打过一场；
- `seedSave` 的 `addInitScript` 自带一次性守卫，同一个 context 里注第二份**不生效**。
  判据在**正确实现**上也红，因为它量的是一份没落进去的存档 —— 要另开 context。

## 五 · 静默跳过是判据最坏的一种失效

扫不到东西时报绿，比红更糟:它让人以为验过了。两条硬规则:

1. **防空转**:「一条都没扫到」本身算失败（`expect(refs).toBeGreaterThan(0)`）；
2. **扫不到 ≠ 通过**。`layout-check` 里那条「扫 40 天没撞上雷鸣日 → 跳过」改成了
   直接失败 —— 后来查明雷鸣只在人间界出现，展示档在仙界，扫多少天都撞不到。

## 六 · 一条判据只该有一种真

`layout-check` 里那条「建筑卡的现 / 将必须同项」的第一版，归一化顺序写反了
（先剥数字再剥「升至 N 级」抬头），于是六行全部误报。判据红了一片，而产品是对的
—— 修的是判据，不是产品。

区分这两种红:

- **产品红** —— 实现确实错了，改实现；
- **判据红** —— 判据看错了地方，改判据。

改判据之前先确认:把实现改成「明显正确」的样子，它还会红吗？会，就是判据的问题。

## 七 · 浏览器门量渲染，源码判据量意图

两者不可互相替代:

- 源码判据能确认「两处都调同一个函数」（`weatherUnitConsistency.spec`），
  但确认不了「渲染出来读不读得懂」；
- 浏览器门能确认「那一行真的印着雷伤 +8%」，但确认不了「是不是同一个出口」。

本轮 `dailyRouteHint` 的链接被挤成 24px（文字全被压掉）——**「没溢出」不等于「看得见」**，
这条只有浏览器能量到。

## 八 · 判据最容易举报的是它自己

扫「源码里不许出现 X」的判据，通常**要在注释里举例子**说明它在抓什么。
而例子里往往就写着那个 X —— 于是判据在自己的文件上红。

这一仓里发生过**四次**:

```text
testSurfaceHygiene      文件头写着 TEMPORARY（说明它在抓什么）
stripCommentsParity     「地基」那条里写着两份样本实现
commentScaleClaims      文件头逐字引着那组过期数字
layoutViewportCoverage  ——（本轮尚未发生，但形态相同）
```

改法固定:**排除本文件，不是排除一大类**。

```ts
if (f.endsWith("stripCommentsParity.spec.ts")) continue;
```

排除整类（比如「所有 .spec.ts」）看起来更整齐，但会放走真问题 ——
`commentScaleClaims` 第一版就是这样漏掉了那两处。

## 九 · 判据红在「找不到」，还是红在「产品坏了」

判据靠名字定位时（`indexOf("function checkDaily()")`），函数一旦改名，
它会红在 `expected -1 to be greater than -1` —— 那是**判据过时**的红。

两种红混在一起时，下一个人最容易做的事是**把那条判据删掉**。

故每条按名字定位的判据都要有一条前置自检:

```ts
it("判据的前提还在 —— 那几个符号都还叫这个名字", () => {
  for (const name of ["export function track(", "function checkDaily()"]) {
    expect(src, `判据的前提没了：${name} —— 判据该跟着改，不是删掉`).toContain(name);
  }
});
```

`startupOrder.spec` 与 `dailySettleOrder.spec` 里各有一条，写法照抄即可。

## 十 · 用孤立调用测流程，会得到一个假的结论

转世那道题:单独调 `player.rebirth()`，发现道侣状态原样留着，
而界面承诺「折返带走」—— 差一点报成缺陷。

查下去发现:**归档在 `confirmReincarnation` 里，不在 `rebirth` 里。**

```text
370  const bondRec = archiveBond();        ← 读 bond 并置 null
397  player.rebirth(view.nextLinggen);      ← 之后才重生
```

顺序是对的。**是测法绕过了整条流程。**

下断言之前先问一句:**这个函数在真实链路里的位置是什么？**
拿孤立调用去证明流程缺陷，很容易得到一个看起来特别像真的假结论。

## 十一 · 加判据之前

1. 先写 RED（让它红在「产品确实错了」上）；
2. 修实现到 GREEN；
3. **把实现改坏一次**，确认它又红了；
4. 改回来，跑全量。

第 3 步不能省。这一份文档被点名的那句「新加的那条也得先证明自己能被打红」，
说的就是它。
