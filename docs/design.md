# 设计规范

## 配色:丹青 —— 水墨为底、朱砂为主、石青为次

![丹青配色 · 日间与夜间](../images/app/palette.webp)

> 上日间、下夜间。色值直读 `src/style.css` 的 `--color-*-rgb`(`bun run shots` 生成),
> 与界面同源 —— 改色只改一处,这张图跟着变。

`style.css` 存裸 RGB 通道变量(`--color-x-rgb`),`tailwind.config.js` 用
`rgb(var(...) / <alpha-value>)` 合成语义色 —— 斜杠透明度与 `color-mix` 两条路径共用一份变量。
夜间主题只覆盖通道值一处,就能同时换肤。

三色定了整幅画的调子:宣纸(`paper`)做底、松烟墨(`ink`)写字,**朱砂**(`cinnabar`,
主色:行动、要紧处)与**青**(`qing`,次色:信息、增益、可前往)是仅有的两个强色。

### 次色为什么是「青」而不是「蓝」

**题材**:国画里与朱砂并称的次色就是青 —— 「丹青」这个词本身即朱砂加青。蓝不是另一套
语言,它是青的深端(靛)。现代蓝色卡(blue/sky 那类)在暖宣纸底上读作网页超链接,
与水墨气质打架。

**可辨识**:色板里已有 `jade`(石绿一系的绿),青必须落在偏蓝的一侧才分得开,
故取石青而不是竹青。

**可读**:青是全站小字的主色(增益说明、属性数值、品阶名,10–11px)。原先照搬西式
`azure` 的明度(`#4F7699`)只有 4.17:1,低于 WCAG AA 的 4.5;国画颜料里的石青/花青
本身就是深色,压深到 `#2C5A7D` 得 6.38:1,反而更接近颜料真身。

界面实际承载文字的底色有四类,全部随昼夜翻转:**纸**(页面与当前道途卡)、
**纸深**(索引、胶囊与舞台起笔)、**抬纸**(`--color-paper-lifted`,仍需分组的纸面段落)
与**纸暗**(洞府、修炼卷首的渐变收笔)。抬纸最容易漏 —— 夜间主题里它比页面底色还亮,
浅色的字放上去对比度最低,只按前两张算会漏掉一整档(实测漏过一次:4.07:1)。
纸暗现在会承载卷首文字,故渐变上的最弱墨也纳入真浏览器像素门:修行副题在卷首内抬到
`ink-soft`,洞府卷首的眉题、天时与「其后」同样不低于这一档。

| 用在哪 | 色 | 对纸 `#F3EFE4` | 对纸深 `#EAE4D3` |
| --- | --- | --- | --- |
| 正文 | `ink` | 12.99 | 11.75 |
| 次级正文 | `ink-soft` | 8.18 | 7.40 |
| 三级正文 | `ink-faint` | 5.13 | 4.64 |
| 主色(朱砂) | `cinnabar` | 5.32 | 4.81 |
| 次色(石青) | `qing` | 6.38 | 5.77 |

**承载文字的每一档都按 AA 取**(≥4.5:1,《palette.spec.ts》逐档核)。这条以前欠着:
石绿 2.95、藤黄 1.90、琥珀 2.84、天青 2.54 等十一档比现在还浅,而它们全在做 10–13px
的说明文字(增益、品阶名、灵根名)。压深之后反而更像国画颜料本身的颜色。

书口暗场另用一组固定色:深墨 `42 39 33` / `31 29 25` 不跟主题换,上面只放奶油墨
`244 239 226`、淡墨 `201 193 174`、朱印 `255 153 143`、赭金 `214 178 104` 与
石青 `143 184 216`。这五档对两层暗底的最差对比度仍有 7.10:1。固定色组只用于
玄枢图题头这类真正的书口外壳,不再借给首页主舞台、修炼内观或手机顶栏、底栏。
固定色组与暗场对比度由 `palette.spec.ts` 核。

**纸上的墨只有三档**。原先还有第四档 `ink-ghost`(#B9B2A0,1.66:1)当最淡的一层,用在
118 处说明文字上 —— 但纸上放不下第四档还能读的字:再淡就低于 AA,再深就与 `ink-faint`
重合,故撤掉这一档,那些字落到 `ink-faint`。需要更淡的**装饰性**线条/色块(不是字),
用墨的透明度写:`border-ink/15`。

**印面是另一类角色**:`.btn-seal` 那行字是写死的奶油色 `#f6f1e5`,托它的底按
「奶油字 ≥4.5:1」取,而不是按它在纸上的对比度。暗色主题下这两种算法互相打架 ——
朱砂当字要够亮(255 119 115),当印面却要够深(182 73 69),故两边分工,见 `style.css`
夜间主题里那两行 `.btn-seal` 覆盖。

**禁用态:压色不压字**。按钮灰掉有两种做法,只有一种读得出来 —— 压色(边框/底色让位,
字保留一档能读的墨)读得出,压字(整块 `opacity-40`)读不出。禁用态那行字往往正是
「为什么不让我点」(「尚差 N 道源」「修为未至圆满」),它是答案不是装饰;整块压透明度
会让它和底一起向对方靠,实测浅色 2.31:1、夜间 2.94:1,连 3:1 都够不着,而
`getComputedStyle().color` 读到的仍是压之前的值 —— 源码里看着完全正常。
四个可禁用基类(`.btn-seal` / `.btn-ghost` / `.chip-ink`,以及当按钮用的 `.card-ink`)
各自带禁用态;夜间印面另有一档 `html[data-theme="dark"] .btn-seal:disabled`,
因为那条深朱覆写的特指度高过基类的 `:disabled`。

两条跟着来的写法约束(都由真浏览器那道门`scripts/layout-check.mjs`盯着):

- **文字不叠透明度**。`text-cinnabar/80` 这种写法算不出对比度,实测正好卡在 3.9:1;
  写字就用整色,要淡是设计的事(换一档 token),不是让浏览器去混。
- **同色底最多 6%**。「底 = 字色自己 6% 的墨」是品阶方块那类画法:底色比卡片亮一点,
  同色字放上去对比度就低一点。原先有 /8 /10 /15 几种写法,实测 8% 就已经掉到 4.44:1 ——
  6% 是既看得见底色、又托得住字的那一档,浓了就降回 6%(视觉上几乎看不出)。
- **投影墨不当纸上墨用**。色板上同名的两档墨分工:`--shadow-ink-rgb` 是投影的墨,夜间
  重定义成近黑(8 7 5);`--color-ink-rgb` 是纸上的墨,夜间翻成浅墨(232 226 210)。白天
  两者都是 41 39 34,看不出区别 —— 可一旦拿投影墨去画分隔线、进度槽、按下时的底色,
  夜间就成了「深纸上画深线」,22% 的透明度合成出来只差三五个色阶,等于没画。故 **只有
  `box-shadow` 许用投影墨**,凡是要在纸上被看见的(线、槽、滑块、冲击波)一律取纸上墨。
  背景里的墨浓度另有上限 25%:再浓就不是装饰,是第二条边框(`src/ui/ornament.spec.ts` 守着)。

### 命名与事实源

语义色名取中国传统色/国画颜料名,不取西式色名(`azure`/`amber` 这类):
`cinnabar` 朱砂、`qing` 石青、`jade` 石绿、`gold-ink` 赭金、`indigo-ink` 靛、
`violet-ink` 紫、`amber-ink` 琥珀、`zheshi` 赭石、`tenghuang` 藤黄、`bise` 碧色、
`he` 褐、`cangqing` 苍青、`tianqing` 天青。

九品色阶(凡→神)也照这套名字走,两两色差 ≥10(CIE76),相邻两档不许糊在一起 ——
压深之后最容易撞上的是地品(琥珀)与天品(藤黄),故一档偏赤、一档偏橄榄。

一份事实源在 `src/style.css`,界面与数据一律引用 `var(--color-*)` / utility 类名。
**引用的类名必须指向色板上真有的 token** —— Tailwind 对不存在的 token 不报错、不生成,
模板照写不误,浏览器照旧忽略:那个类编译后一个字节都没有,元素静默落到继承色。
这类缺陷行为测试看不见(元素在、字在、只是没颜色),人眼也容易当「设计就这样」;
实测清出九处,其中 `text-accent` / `text-ink-success` / `text-ink-warn` / `focus:border-azure`
指向的是**从来没定义过**的 token。判据按 `tailwind.config.js` 的 colors 与 theme.opacity
枚举(`uiLayering.spec.ts` 的「语义色类」),新增 token 自动纳入。
品阶九色(`qualities`)、器魂六阶(`souls`)、五行与特殊灵根(`linggen`)、天赋档位
(`talents`)原先各自手抄一份裸 hex,现全部改成引用变量 —— 它们从此跟着色板换肤,
也才有夜间档可言。

`public/privacy.html` 是唯一的例外:它是**独立成篇**的静态页(离线也要能直接打开),
只保留了它自己用到的几个颜色,与 `style.css` 是手抄关系 —— 改配色时两处都要动,
故 `palette.spec.ts` 会把这张手抄表与色板逐条核对。

## 版式:竖版文字风格,移动端优先

页面按手机竖屏的阅读节奏排:一屏一件事,长列表用章线、留白与小印分组。
全量路由 × 五档视口的排版审计在 `scripts/layout-check.mjs`。

### 玄枢视觉 v2：天穹卷

全站是一张连续的玄墨星场纸面,不再用整条深墨书口夹住正文。手机顶栏是一条悬浮的
天幕批注带:身份、境界、寿元与资源直接写在纸上,只以一道世界色星轨收口;底栏是
收敛的章印式导航,当前册只落朱砂光晕与文字色,不铺整块深墨 `dock`,也不抬起第二张
浅色卡片。二者都不是 App bar,不靠外框、投影或厚底色把自己从页面里切出去。

公共页首是开页题签而不是卡片:留册次水印、印章、世界色淡线与底缘切口,不再同时画
四边框和 4px 内框。章节、此刻账、总账、通用纸片、页签、弹窗与桌面书脊沿用同一条
规矩:**一个页面最多一层容器边**;已有页框或标题线时,内部只用留白、底线、落款与
光晕再分组。卡片可为纸色渐隐,不得超过一层容器边;弹窗可以靠悬浮投影离开纸面,
但不再加第二道内框。浮层卷身内也不再铺第二张纸卡:关于、数值体系、灵脉、天道熔炉、
道痕纪元变迁、器魂散置/凝炼两册、开炉丹方与灵草坊只沿卷身的上下账线与分段线续排。

首页洞府指挥台与修炼内观台是全出血晨昏纸面舞台:左右铺到页边,下缘用大圆角收住,
底色随主题从纸深走到纸暗,星盘、轨道与远山只做氛围层。它们下方的道途、日课与门径
继续落在连续纸面,以章线和小印组织,不再连续堆叠同权重方卡。朱砂仍只表示行动与
要紧处,石青仍只表示信息、增益与可前往;视觉减框不改这两条语义,也不改任何文字底色
与 AA 对比度判据。

### 册页骨架:玄枢图 + 书口落点

全站不再只靠五个底栏页签找路。顶栏左端是一枚方角「玄」印,打开 `玄枢图`:
十七册按修行、道场、行旅、身外、天机五卷展开,每册有一句「它回答什么」的说明,
当前页在图上留一枚「在」印,并压成一条只报卷次、册次、册名与身份的册口签。
卷目本身是一组 `tablist`:五枚卷次签同时报卷名与册数,只展开当前选中的一卷;
其余卷宗用 `v-show` 留在 DOM 里,检索、读屏与键盘仍能读到全部十七册。切卷只换
当前册页,不再沿用旧长目录的滚动跳转,刚点过的卷签与寻册口都留在视口内。
720px 以上把卷签铺到左侧、当前卷册页放右侧,总图上限放宽到 68rem;390 与 195
CSS px 仍按单列阅读。桌面的当前卷册页铺满右侧整张案台,不再沿用旧版双栏索引把
后一半留成空白;每册前补两位册次,用来对住五卷卷签与册口签。底栏只放洞府、修炼、
历练、背包、人物五个高频去处;其余页面从玄枢图进入,不再散落在人物页的入口卡里
靠记忆寻找。

总图顶部另有一枚「寻」口,按册名、说明、分卷、册内分册与玩家日常叫法一起检索:
写「背包」能找到册名「行囊」的页,写「人物」能找到「道躯」,写「周易」「灵兽」
则直接落到对应分册的 `?tab=`,不是只把玩家丢在页首。空格分词要求全部命中。桌面
书脊上有常驻「寻册」入口,全站也可按 `Ctrl K` / `⌘ K` 直接开图;打开后焦点落在
输入框。触屏设备改落当前卷签,不因开图自动弹起软键盘遮住五卷;寻册口仍只隔一次
轻点或 Shift+Tab。上下键循环结果时,polite 播报会报出第几处、卷名、册名与分册,
回车即入册。关键词、分册与路由一起住在 `NAVIGATION_ENTRIES`,
七册长页共用 `useRouteTab`,页面内换签也会把落点写回地址。不另维护第二份快捷表;
中文输入法组合期间的回车与方向键让给选字,不抢作翻册。

玄枢图不把跨页待办留在图外:行囊有新货时,「身外」卷签先落一枚朱砂点,行囊册报
「N 新」;可以破境时,「修行」卷签与修炼册各落一枚石绿点并写「可破境」。这些章与
手机底栏、桌面书脊同读 `useNavigationSignals`,不靠玩家点开每一卷才发现。键盘快捷键
只在精细指针设备上显示,触屏不摆一枚按不出的 `Ctrl K`,寻册口本身仍在原位。

键盘玩家第一次按 Tab 时,书页上缘会展开一枚「直入正文」朱砂书签,越过玄枢图、
书脊与底栏把焦点交给正文滚动宿主;hash 路由地址不因这条跳读改变。每次翻册后,
隐藏的 polite 播报区还会从玄枢册目同源报出「第几卷 / 第几册 / 册名」,让视觉上的
卷首、书口签与顶栏换页在读屏里也有同一个落点。判据在 `folioChrome.spec.ts` 与
`layout-check.mjs` 的首次 Tab 场景。

手机顶栏是一条悬在纸面上的天幕批注带,只有一行:左侧玄枢印的右下角压当前卷次,
中间是名号、境界与寿元,右侧是灵石、灵气与设置。灵石与灵气本身就是 40px 高的
精确值入口,点开仍报同一份资源账;五卷跳转归玄枢图,书首不再另起
第二行位置签,也不重复卷首册口签与底栏主册。620px 以上在同一行中段补出
「卷次 + 分卷 / 册次 + 册名 / 世界」;359px 以下先收寿元,220px 以下再收境界。
`data-folio-position` 留在 header 上供播报与测试同源读取,但不再占一行视觉高度。

桌面在 1100px 以上撤下书首,把名号、寿元、灵石、灵气与设置并进左侧书脊的
「随身账」,正文从书桌顶缘直接开卷。960~1099px 的窄桌面仍保留书首,因为那一档
书脊只露图标,没有身份与资源;桌面书首若常驻,同一册次会在书脊、书首和页头各报
一遍,还永久占掉一截阅读高度。

1200px 以上再把书脊五卷摊成两列总目:左列修行、道场、行旅,右列身外、天机。
十七册在一屏内全部可见,不把末卷藏进没有明显滚动条的暗处;每册仍保留 28px
触达高度,当前册用右上角一枚朱砂小印落位。960~1199px 的单列书脊仍可滚动,
因为窄桌面没有第二列需要的横向余量。

详情页共用一枚 `FolioPageHeader`:分卷、册名与册目说明从玄枢图同一份数据读出,
父页兜底也收在组件里;页面不再各手搓「返回 / 标题 / 读数」三栏。卷首页口再摊出
本卷诸册签,同卷兄弟册可直接横跳,当前册与顶栏当前卷共用同一份 `navigationPositionOf`。
卷首主标题是真正的 `h1`,左侧返回只报父册,右侧动作与页内读数各有独立槽位;
195 CSS px 时动作落整行,不把册名与说明挤成竖排。

手机与桌面卷首共用同一枚开页题签:只留底缘切口、世界色落款与右侧淡墨册次水印,
不再把卷首做成压在正文上的第二张厚卡。册次仍由 `navigationPositionOf` 的同一位置
生成,返回、动作与读数槽位不变。

历练、行囊、道躯与「人间」再走一层 `featured` 开卷版式:
册名、印章与读数放大成这一页的第一眼;`#backdrop` 铺世界色远山,
`#visual` 只放法球这类主视觉,默认正文槽承接行旅条与今日天时。它们仍与详情页
共用同一枚 `FolioPageHeader`,不是第二套页头;页面内不再另写 `h1`、旧 hero 或
同名的栏目标题。首页与修炼内观台是两处例外:它们不是另一册需要“开卷”的页面,
而是玩家每天停驻、反复查看的主屏。首页拥有唯一一枚 `h1`「洞府总览」与独立
晨昏指挥台;修炼页把同一枚卷首组件换纸成晨昏内观台,`h1` 仍是当前境界名。

修炼内观台把「我在哪一境、修为走到多远、此刻在做什么」压在上半屏:境界名、
阶段判据与仅展开一次的典籍来路在左,主题周天盘在右,底部一行同报余程、行速与
灵气。阶段按「关隘已开 → 修为已满 → 带伤行功 → 闭关中 → 吐纳中」排序,由
`cultivationStageOf` 单点判定,页面不另拼一套状态优先级。周天盘外圈二十一境读

就会印成「下一世的名」。空名整行不出（旧档可能没有名字）。

首页与修行页的星空是**同一片天**：`--sky-star-rgb` / `--sky-brightness` 挂在页面根节点上，
一处算、两处继承。两页的星样式逐字相同，第 47 轮只让首页跟着天时变时，修行页没跟——
同一天里首页抬头是稀星，翻到修行页却是满天亮星。以后再加第三处星空，只要挂在同一个根上
就自动一致。两处样式都留缺省值（`var(--color-gold-ink-rgb)` / `0.62`），没有天时的场合仍是金色。
浏览器判据量的是两页算出来的颜色与不透明度**逐字相同**——不必知道今天哪种天时，这个比法任何天时都成立。

首页那片星空随今日天时变（`ui/weatherSky`）：星的颜色、亮度、多寡各按三档调——沉（月蚀、罡风、
仙劫日、雷鸣：星稀而晦）、暖（赤阳、霞光、紫气东来：偏赤金偏浓）、清（其余五者：最平常的一档）。
分组依据是天时名字本身的意思，不是机械平均。这是本作里**唯一一个完全没有功能的东西**：不提示、
不奖励、不判定——放置游戏最缺的往往不是内容而是此刻感，玩家每次打开看到的都是同一屏，
而一行天时文字与一片跟着变的夜色，后者才让人觉得「现在是此刻」。

大境之槛另有一声与一道光（`core/audio` 的 `majorBreak` + `.burst-ring--major`）。每重境界十个小层
（`SUB_LEVELS = 10`），十次突破里只有一次真换了重天——而从前两者共用同一句 `playSfx("breakthrough")`、
同一圈金环，大境只多一个「大 境」小章。音效这条尤其明显：`rare`/`rareHigh`/`rareTop` 三档早分了，
`worldRise`（跨界）也单有一档，**中间那一档是空的**。新档的分量靠三样拉开，不另创乐汇：
更低更久的底钟、两个八度的上行刮奏、双钟叠定音。

大境必渡劫（`needTribulation = isMajor`），故浏览器判据要一份能渡过劫的存档：渡劫每道伤害乘
`rng.float(0.85, 1.15)`，把随机源钉成 0 即取下限；波数随 major 涨，故用最低的可用大境（major=1）。
major=0 时突破钮不可点（炼气是起始境），major=3 有七道劫、直接被打死。

日课全部结清时，首页那张卡落一枚「日课已结」的朱砂小印（`ui/dailySettle`）。日课是玩家每天
都会经过一次的路径，也是放置游戏里最容易被忽略的节拍——它重复、可预期、做完就过去了。
此前全清只有三处静态文字变化（标题、正文、一个 `is-complete` 类），屏幕上没有发生任何**事件**。
印不编号：本作没有累计天数的账（日课按天重置），编一个 N 就是假的。判定复用既有的
`dailyAllDone`，不再抽第二份。用朱砂实框、微斜 0.8 度——像真盖下去的一方印，与导航那枚
石青细线的「通途印」区分开。

头一回遇见的凶物挂一枚「初见」章（`ui/firstSight`）。世界里已有敌人的**认知**系统
（`core/loreService` 的 `noteEnemy`：打得多就提示「你摸清了它的招式」），那套讲的是熟识；
「第一次」它没有——第一次遇见山魈与第十次看到的界面完全一样。

判定**必须在结算那一刻取**并写进战报（`LastBattleView.firstSight`）：照面次数记在
`adventure.recordBattle(view)` **之后**（`noteEnemy`），界面读战报时已经 +1，拿它判初见
永远得到 false。这份账随神魂带走，故「初见」说的是生生世世头一回。

这一块的条件与内容现已同源（`ui/combatChips`）：块显示与否 = `chipsOf(...)` 结果非空，
块内渲染的也是同一个数组。此前那块的条件是 `isBoss || isNemesisFoe || shownTraits.length`——
一串「每枚章条件之或」，加一枚新章忘了改它，屏幕上一片空白，而编译、类型、单测全绿。
第 42 轮的「旧仇已雪」与第 43 轮的「初见」连续两轮踩了同一个坑，都是真浏览器探针
量到 `chipsWrap: 0` 才发现。修法不是「下次记得」，是让条件的来源只剩一处。

宿敌那一枚章写全（`ui/nemesisChip`）：未雪耻时「宿敌 · 已败三次」，雪耻后换成「旧仇已雪」。
章背后两个字段此前一直没上界面——`lossCount`（输给它几次）与 `avengedAt`（哪一次赢回来的）。
雪耻那一刻尤其安静：打赢之后 `isNemesis` 立刻返回 false，章直接消失，玩家看到的是
「什么都没发生」；而 `core/worldMemory` 那边已经把 `avengedAt` 记上，还会据此产出「残魂」形态。
章里写**门槛值**（三次）而不是实际次数——`lossCount` 值域是 3 到 ∞，一章撑不住，
具体次数留给传承页那张宿敌表。

那条「旧仇已雪」必须放在 chips 块**之外**：那一块的条件是
`isBoss || isNemesisFoe || shownTraits.length`，而雪耻一过 `isNemesisFoe` 就是 false——
挂在里面永远显示不出来（探针量到 `chipsWrap` 为 0 才发现）。

重复遭遇同一事件时，正文下面多一句「你想起上一次，自己走的是「…」；这已是第 N 次。」
（`ui/eventRecall`）。95 个事件里只有 8 个标了 `once`，其余 87 个可以反复出现，而第二次遇到时
标题正文选项一字不差。弹窗里那块「余波」（`core/worldMemory`）要 `times ≥ 2` 且只
`AFTERMATH_CHANCE = 0.2` 抽——于是**第二次遭遇完全没有标记**，第三次起也有八成不亮。
这一句补的正是那一格：必出、不掷骰、从第二次起就有。两句分工：余波是世界那侧的、偶发的、
带情绪的；这一句是你自己那侧的、每次都有的、只陈述事实。

突破失败弹窗在安慰之后补一行**下一步**（`BreakthroughView.nextStep`）：失败那一刻有三件事同时
发生——准备加成被 `consumeBreakthroughPrep()` 取走（失败也不退）、挂上伤势、修为掉一截——而这是
一扇全屏弹窗，遮住了修行页上那些准备按钮。只说「来日再战」等于让玩家自己回想刚才少了什么。
那一行从结算里取（`sparedByHeritage` / `breakthroughPrepState()`），不手写话术。

名字的上限只有一处定义：`utils/nameLimit` 的 `NAME_MAX = 8`。道号、构筑名、挑战书名、
转世名号草稿四处都读它；`PLAYER_NAME_MAX` 保留为别名（第 37 轮建立的调用方不用改）。
这个 8 不属于任何一个模块，放在 store 里会让另外三处为了一个常数去 import player store。

道号的上限是 `PLAYER_NAME_MAX`（`NAME_MAX` 的别名），创建页的 `maxlength` 与
提交时的裁剪都读它。此前这个 8 只手写在创建页两行里，而 store 的 `setName` 完全不裁——
契约活在页面上，谁都能从代码里调 store 绕过去。顶栏那行 `truncate` 仍是必要的兜底
（旧档里可能有更长的名字），但**新输入**不该依赖它：玩家敲进去的字被悄悄削掉，不会报错也不会提示。

`formatPercent` 的极小值守卫按**取整之后**是否为零来判，不按取整前的量级。原先写的是
`Math.abs(v) < 10^-dp`——`dp=0` 时阈值是 1，于是 0.9% 也被清零印成「0%」；而 0.9% 四舍五入
就是 1%，抹掉它等于凭空否定一次真实的收益。道果边际在软上限后正好落在这个量级。

道果边际的百分数（`fruitMarginalInfo().deltaPct`）改用 `formatPercent(delta, 2)` 而不是手写
`toFixed(2) + "%"`：手写那份不处理上溢（`eff` 极小时比率可以是 Infinity，会印「Infinity%」）。
取两位而非全仓默认的整数位是有依据的：这个数掉到 0.9% 一带，取整会把它压成 1% 或 0%，
而 0% 会让玩家以为「再攒一枚也没用」——与事实相反。

倍率的写法收在 `ui/multText`（`multText` / `multNumberText`）：两位精度、削尾零、带 `×` 前缀。
此前同一份值是三种写法——`toFixed(2)` 印「×1.20」、直接插值印「×1.2」、
`Number(x.toFixed(2)).toString()` 又是另一种。同一份灵根倍率在人物页与转世确认页
印成两个样子，看上去像两个精度。保留两位而非一位，是因为倍率差 0.01 有意义
（灵根 1.02 与 1.03 差的是整条修速曲线）；削尾零是因为 1.20 与 1.2 同数。

灵兽也记「何时与它结的缘」（`petMoments`）：第 27 轮给称号补这一刻时只修了称号那条，
而 `quests.petCompanions` 同样只是个 id 数组。转世会把灵兽清零，故谱上每一只都是这一世
结的缘——但没有时间读数时，二十只并排就分不出哪只是刚遇见的。与称号、图鉴共用同一份道历
（`ui/codexMoment`）。旧档照实说「早年收录」，不补造。

注意：「拥有」看 `collections.pet`，「相伴过」看 `petCompanions`，两者不是一回事。

称号也记「得它的那一刻」（`titleMoments`）：此前称号只有个 id 数组，玩家有一排功名，
却分不出哪个是刚才得的、哪个是上一世挂着的。与图鉴共用同一份道历（`ui/codexMoment` 的
`codexMomentOfPlayer` / `codexMomentText`），不另写一套历法。旧档里已到手的称号没有这对读数，
照实说「早年收录」，不假装是这一世得的。

卷首眉批说「此刻最该做的一件事」（`ui/nextStep`）。修行页早已有一个「当前阶段」，
但那**只讲突破这一件事**且只在该页；玩家点开洞府、法宝、灵兽，卷首各自只报本页的账，
没有一处回答「我现在该去做什么」。规则按**卡住了什么**排序、只吐一条：挂着的际遇 >
正在历练 > 破境条件齐 > 终点已至 > 未领的赏 > 可收的洞府账 > 法宝空位 > 更好的装备 >
修为已满待关。指向本页的建议不出（玩家已站在那儿），一条都不成立时整行不渲染。
规则是纯函数（不 import 任何 store），取数在 `ui/useNextStep` 一处完成。
取数三项各有既有来源、不重造：未领的赏读 `currentMainQuestProgress()?.done`（与领赏判定同一份）、
法宝空位比 `artifactSeatCap()`（与整理装配表同一个函数）、未上阵的一件看行囊里有没有没穿的。
「更合手」那项**不做换装模拟**——那要跑一遍 `finalStats`，到这里只会变成又一份账，
文案也随之收敛成「行囊里有未上阵的一件」，说到的正好是它知道的那件事。
「终局已至」读 `endgame.daoPath`——道途一旦选定不可改（来世方可另择），选过了就是终局已至。

那行字**可以点**：它说「该去哪」就把玩家送过去。初版是一枚 `<p>`——写着「关隘已开，可去破境」
却不能点，等于把「去导航里找」的成本推回给玩家。语义上用 `<button>`（站内单页应用，
没有可分享的 URL 语义），`aria-label` 里带上目的册名。热区扩到 28×28 的触控下限，
靠负外边距 + 等量内边距实现，**视觉位置与行高都不动**；悬停反馈包在
`@media (hover: hover) and (pointer: fine)` 里，否则触屏点过之后那枚箭头会一直偏着。

八句**用这本书自己的口吻**，不用通知体：去掉「正」「已经」「手里还有」这类播报用的虚字，
留下的都是动作与去处。「此程未完，且先走完」比「这一程尚未了结，先走完它」少六个字，
意思一点没丢；每句不超过 14 字（眉批与副题同段，长一句就把下面挤走）。

稀有提示的那**一声**也分层（`ui/rareSfx`）：灵/玄/地是原来那一响（管钟 D5 + 高音 D7），
天/仙升到 F5 + A7，神品升到 A5 + A7 并补一个低八度 A3 作根基。用**音高与声部数**分，
不用音量——音量在手机扬声器上几乎听不出差别，而和声的厚度会变。三层始终留在「管钟」
这一族，不刮奏：刮奏冲顶是「大境界突破」的语义，借过来会把那件事稀释。

声与光共用一份判定（`flashPlanOf` 同时给出 `tier` / `seconds` / `colorToken` / `sfx`）：
同一条提示不该出现「光按神品闪、声按灵品响」这种分叉。判据两侧都核。

稀有提示落地时那道**全屏一闪**按品阶分层（`ui/flashTier`）：`rank < 6` 走默认金色 1.1s，
天/仙 用那一档的品阶色 1.35s，神品 1.6s。从前只有一种色一种时长——神品与灵品落地时，
屏幕上最重的那一层完全同款。时长比颜色更有效：品阶色在暗场与亮场观感差别很大，
而 1.1s 与 1.6s 的差别不需对比就能感到。本模块只分类（哪一档、多久、色从哪个 token 取），
RGB 由界面用 `getComputedStyle` 求一次——品质表里写的是调色板 token，纯函数不该假装知道它。

提示条可带**去路**（`ui/toastTarget`）：`Toast.target = { kind: "equipment" | "artifact", id }`，
拾得装备与法宝入手时由 core 填上，界面点一下即打开对应详情并收起提示。去路是**动作**不是路由链接 ——
提示条浮在任意页面上，链接会把玩家从当前页带走。不填去路时点击只收掉自己（绝大多数提示）。

`setNotifier` 的转发器必须用 `...args`：这里栽过两次（先漏 `seal`，再漏 `target`），两次都类型合法
——JS 丢实参不报错，而单测直接调 store 的三/四参版本全绿，只有真浏览器里「怎么没效果」。

「第几册」的读法收在 `ui/folioPosition`：`卷三 · 第三册`、顶栏 `第三册 · 行囊`、玄枢图册目清单的
册次也读汉字。此前是「卷三 · 第 03 册」——同一句里前半汉字、后半两位数字。**册次与行号分开**：
册次是体例（五卷十七册，读序数词），行号是计量（行囊 200 件、藏珍 400 枚，仍是 `01`/`02`），
后者不动。转写同样走 `utils/format` 的 `cnNumber`；「第…册」的**外壳**由本模块提供，
因为「三」是数字而「第三册」是序数词，两者从十起就分叉。

卷首那枚最大的**册次水印**写汉字（`ui/folioOrdinal`）：`一` `二` … `十` `十七`，与卷次小字「卷三」、
章序「壹贰叁」、页签「乙丙」同一套序数语言。此前它是 `01`/`02`——页面上最重的视觉元素，
却是全作唯一一处读得出来的阿拉伯序数。转写走 `utils/format` 的 `cnNumber`，不另写一张数字表；
数字仍留在 `data-folio-ordinal` 上供机器核对，两者同源于 `navigationPositionOf` 的册目位置。

自动重铸的预算行多一条**总账**（`ui/reforgeBudget`）：`洗满 N 次至多 器灵尘×X · 灵石 Y`，
付不齐时改写成 `尚差 …`。它只做乘法 —— 单价取自 `core/reforge.reforgeCost`，不另算一份。
明写「至多」是因为自动重铸会提前收手，预算次数对应的是上界；「预计」要按命中概率加权，
那已由逐条的「约 N 次」给出，两个数混成一句会自相矛盾。预算上界与输入框的 `max`
共用 `REFORGE_BUDGET_MAX`，不在模板里再写一个字面量。

悟道分支择定之后,已选那一块末尾多一行**未行之道**（`ui/unwalkedBranch`）：其余几条的名字 + 各自
当时会给什么，按原表顺序，写成字不写成按钮（它们已不可选）。只列没走的那几条 —— 自己那条就在上一行。
与悟道录的 `branchStage`（没走的那条记为「已见」）是同一个事实的两个面。

器评帖的共鸣段多一行**共鸣缺口**（`ui/resonanceGap`）：`还差 N 件凑成「X」：槽位·件名（处境）`。
三种处境分开写 —— 在行囊 / 见过待刷 / 未曾见，因为下一步完全不同；「见过」以 `lore.equipLore`
为准（不是「行囊里有」）。缺口只取**按槽位序的前 N 件**（N 为还差件数），不是把所有未穿件都列出来；
凑齐后整行不出。本模块不给数值、不改 hook —— 能不能共鸣仍由 `core/equipSet` 的库调用说了算。

图鉴页脚的「收录时间」读**道历**（`ui/codexMoment`）：`第 N 世 · M 岁`，两枚读数在收录那一刻
由 `quests.collect` 写下（`collectedMoment`），此后不随玩家变老而改。它替掉的是此前唯一的
`new Date(ts).toLocaleString("zh-CN")` —— 全作唯一一处露出现实世界的钟，且带时区。
旧档没有这对读数时照实说「早年收录」，不按现在的年岁往回编。

界域志的境界谱在三态（已渡 / 此刻 / 未至）之外多读一种「**曾至**」（见 `core/peakRealm`）：
转世把 `major` 折回起点，而 `player.reincarnation.peakMajor` 只增不减地记着历世到过的最高一境。
两者刻意分开——合并就等于让门槛跟着历史放宽，那是另一套游戏；`peakMajor` 只读，不参与任何分支判断。
谱上当前境仍是「此刻」（信息量更大），曾至的那几行用石绿字与虚线印面（虚线＝属于上一世）；
卷首那行「此身曾至 X」只在当前境低于历世最高时出现，否则整行不出。

提示条（`components/common/ToastHost.vue`）可带一枚**品阶印**：`Toast.seal` 是可选品质 id，
`notify` 的第三个参数把它递下去。印的画法与 `QualitySeal` 同一套阴文口径（纸底 + 品阶色字 + 细边），
尺寸取行高内，故不改提示条高度；没有印的提示布局一字不差。转发器必须把第三个参数
原样送到落点 —— 曾经写成 `(text, kind) => toast(text, kind)`，类型合法、实参被静默丢弃，
单元测试直接调 store 全绿而界面永远收不到印；判据现由 `toastSeal.spec` 走端口直测。

装备详情的眉题行在品阶名之后另有一句**品评**(见 `data/qualityVerdicts`):九档各一句
「这一档凭什么」,不写数字也不重复品阶名,与品阶名、器类、阶数、在佩状态同处一行。
坊市验货签与藏珍详情读同一份;`CodexEntry.quality` 是可选的 —— 灵材、见闻与成就没有档,
那几册整句不出,不给它们硬安一句「山野之物」。它有排版上界(一行以内),由
`qualityVerdicts.spec` 与真浏览器的「品评说得出一档的分量」两侧盯住。

装备详情收成一张「器评帖」:卷首先报品阶、器形、本件战力与相对当前同槽件的真实
增减;空槽只报可补位,已佩本件只报在佩。灵品以上的器首还带一行**器铭**
(见 `core/inscription`):两字铭名走楷体、铭文退说明档、成色是这一件词条掷点均值
的读数(0~100),三段同处器首那一条虚线之下,不另起卡片。铭里**不再复述器类与界域**——
那一行眉题已经报过,同一屏说两遍正是本仓反复清掉的那类。同一枚铭在坊市验货签、
拾得提示与归来卷轴里说的必须是同一句话 —— 它只由 uid 决定,存盘与导出导入
之后不许改口。**器铭不参与选件**:它描述「这一件是谁」,不提供任何数值、不进排序。
候选列表和详情共用 `equipPowerComparison`,不在界面另减一遍。器性、词条、换装后流派、炼器进度与
工坊依序展开,只沿弹窗内的上下账线、栏间线与器色上缘续排,不再逐段另套四边框;
自动重铸与词条转移展开后仍是同一张账,连强预算也只留上下账线与左侧短笔;
封存价签只以账栏分隔,不伪装成第二枚按钮;品阶只落在器首左侧短笔与器印。
部位候选也沿同一张上下账线续排,佩戴件只留石绿淡染,逐件不再套纸卡;常态是
器印、正文、战差与动作三段账,195 CSS px 下决策退整行而战差与换上仍守同排。
重铸长账回到可滚正文,页脚只留卸下、强化与分解返还。结构与窄屏判据由
`equipmentDossier.spec.ts` 与 `layout-check.mjs` 守住。页脚的换装对照与分解返还

未开启的终局册页不再用一块大白卡占位。天界与器魂共用 `UnopenedFolio`:册名只留在
公共页首,正文以紧凑「封」印起笔,先把目标写成一句「尚待 真仙 · 再越 N 重境」,
再把**当前境界 / 门限 / 尚隔几重境**摊成一张门径账。账下按 `gateMajor` 逐重境落齿:

构筑页的卷首是同一张「铸道盘」:六段契合弧、六枚路印与中心当前路印都读

纸卡。成路后,正文收成一册「铸道续卷」:壹「道途阶梯」报当前阶段

### 桌面书桌:左书脊导航,右册页阅读

手机与横屏仍是一张竖版单叶;960px 以上、游戏已经开局时,外壳从 430px 手机框展开成

4.25rem 的图标书脊,保留 28px 触达高度;1100px 以上展开成 14rem,显示卷次、卷名与
册名。手机底栏在桌面退场,不再把五枚页签平均拉长到一千多像素。书脊本身也按 960px
断点真实挂载,不只在手机用 CSS 藏起 —— 十七册目录和身份读数不该占着手机 DOM。

矮横屏(620px 以上、560px 以下)仍是单叶,但卷首要先让给正文:右侧与正文重复的

要露出下一段正文,手机竖屏与桌面书桌不受这条断点影响。

620~959px 仍是单叶,但不再把正文锁在 430px 手机栏里:外壳铺到视口两侧各留一指,
最宽收到 60rem,页面内部原有的两栏硬账因此有地方展开;底栏五册继续常驻,真正的
书脊与双页仍从 960px 开始。五枚章印签在宽叶里不跟着拉成一条长栏,而在 40rem 处
收束居中,每枚仍留 96~128px 触达宽度;手机宽度下照旧铺满栏底。高屏平板上下各留
一指并描出页边,844×390 这类矮横屏则让高度优先、不加上下留白。620×900、
768×1024、844×390 与 959×1024 四档的十七页都由真浏览器逐页核对外壳宽度、居中、
底栏保留、书脚索引收束与书脊不得提前出现;开局欢迎页和建号页共用同一张宽叶。

960~1099px 的书首收在正文列内,仍是同一条天幕批注带:图标书脊没有册名,顶栏保留玩家
身份、玄枢入口与资源账。1100px 以上书首整条撤下,身份、资源、卷册与世界都由展开
后的书脊承担,避免同一份名号在左右两栏重复。桌面正文按阅读密度分三档:设置这类线性读卷收在 48rem,
避免长文被拉成长行;历练、人间、坊市、界域志、器魂、营造、门庭、流派、名号、轮回录、

只有能稳定落成成对关系的四册才展开成 66rem 的双页。

修炼、行囊、道躯、藏珍四册的信息能成对阅读,再展开成
`1.08fr / 0.92fr` 的双页:修炼的「修行」与「下一步」并置,人物页的「道躯总案」跨两栏,

续读;藏珍的行动章与卷目章同住一册,960px 起再左右并读,页签横跨两页。双页中缝只画

首页单独走宽案,在内部自己排主舞台与双列仪表盘;哪一册走读卷、宽案还是双页由

而在开卷态单独放宽到 72rem;单叶、宽案与双页也各有明确数据属性。源码契约在

网格列数、宽案下限与读卷上限。书脊的册目完整度、当前册唯一与手机底栏退场由

仍靠一条拉长的手机导航时假装完成。

这是一款游戏,不是按章回顺序阅读的电子书,故正文末尾不铺「回翻 / 续翻」页签。
跨册去向只走底栏、桌面书脊与玄枢图:玩家去的是「洞府」「器魂」「坊市」这些目的地,

- **玄枢图**是一张五卷案台。顶部先给「寻」口与快捷入口,中间一条当前落点册口签,
  五枚卷次签是 `tablist`,只展开当前卷;每卷仍以方印、淡墨卷名水印与连续目录行呈现,

- **页签**是书口索引签:只留一道下缘墨线,当前签以文字与底边朱砂短线落位,不再
  铺整块纸底或画方框。选中态不是实心胶囊,滑动的是那条落款线。
- **底栏**只在手机与横屏出现,是一排落在纸面上的章印导航:当前册只亮朱砂光晕与
  文字色。图标角标与「可破境」提示与桌面书脊共用同一份信号,换壳不丢提醒。
- **弹窗**是一张摊开的笺:世界色上缘是书签带,题签先报分卷与卷页,右上角以
  「合」收卷;纸色、世界光晕与纸纹共用同一层,不加四边框与第二道内框。
- **限时机缘卷**是弹窗里必须作答的一支:顿悟与洞府巡游共用同一张卷,卷首以
  「悟 / 巡」方印、来源与题名先报来历,真实剩余时间同时给出数字与进度轨。
  三签各摊开签文、风味与由结算同源现算的得失;有惩罚的签单独标「有代价」。
  临散前十秒,时机与进度轨一起转朱砂。背板、Esc 与关闭键都不静默舍签,

`src/ui/opportunityDesk.spec.ts` 守住取数、急色与极窄档;桌面书脊的独立判据在

### 字号只有五档，桌面分紧凑与阅读两档

**字号档位**：18 / 15 / 14 / 11 / 10
960px 出现书桌骨架时先沿用紧凑桌面档 20 / 16 / 15 / 12 / 11，卷首题字 28；
1100px 完整书脊展开后切到阅读档 24 / 18 / 16 / 14 / 12，卷首题字 34。
后一档的正文从 12 提到 14、注脚从 11 提到 12，宽屏不再把手机字号原样放大一份。
手机与 200% 缩放档仍用第一组，不因桌面改版变大。

这些值只住在 `src/style.css` 的 `--type-heading / --type-section / --type-title /
--type-body / --type-note / --type-display`。模板写 `text-heading` 这类语义类，
不再写 `text-[18px]` 裸值；Tailwind 只负责把类名转发到变量。这样桌面放大时，
正文、卡片题头、页签、弹窗与导航一起换档，不会出现标题变大了、说明仍是手机 10px
的两套账。

这对数字与 `uiLayering.spec` 里的 `PAGE_TIERS` 是同一份清单 —— 判据会逐个数比对，
改动一处而不改另一处会当场红。
各断点内不许再长出 13 / 9 这类私档 —— 相邻两档只差 1px 时，读者分不出主次，
层次就塌了。这条由 `uiLayering.spec.ts` 的「主巡页 · 字阶同一套」逐页守着。

**排版角色**（`src/style.css`，每个角色只管字号/字距/行高，颜色由调用处挑）：

| 角色 | 用在 | 度量 |
| --- | --- | --- |
| `.t-card` | 卡片题头 | title 档 · 字距 0.1em |
| `.t-entry` | 入口卡 / 列表项的标题 | title 档 · 字距 0.2em |
| `.t-item` | 卡内条目名 | title 档 · 字距 0.25em |
| `.t-body` | 正文一句话 | body 档 · 行高 1.625 |
| `.t-note` | 脚注（紧跟正文，不另起一行） | note 档 · 行高 1.625 |

为什么要有名字：配色早有一整套 token 与五条判据，排版此前只有「竖版阅读节奏」
一句话。于是同一个角色被手写了上百遍 —— 正文那三连（`text-[11px] leading-relaxed
text-ink-*`）逐字重复 97 次，卡名四种字距并存。**没有名字的角色，每写一张新卡
就得凭印象抄一遍，抄歪了也没人发现**（字号档位那轮 9/12/13 私档正是这么长出来的）。

新增角色要先在这里登记，并想清楚它与前四个的差别；只差一点字距的不算新角色，
那是其中一档没写对。

**这一轮把「手写三连」收编成角色**：`text-note leading-relaxed`（69 处）与
`text-body leading-relaxed`（11 处）都改用 `.t-note` / `.t-body` —— 两组写法与角色
类逐字等价（同一枚 `--type-*` 加同一行高 1.625），换过去版式不动，但从此「脚注」
只有一个名字。字阶判据也同步认这些角色类，否则会出现「换成角色类之后扫描器
当这页没写字号」的假绿。

**样式里没有尸体**：同理，重构摘掉某段模板时留在样式表里的类不会再报错，只会让
下一个人反复判断它活没活。`src/ui/deadStyle.spec.ts` 把「每条带连字符的类选择器
都得有人在用」立成判据，放行三类：Vue `<Transition name>` 生成的过渡类、
模板里 `is-${state}` 拼接的状态类、BEM `--变体`；以及上面这张角色词表
（它本就是「给下一张卡准备的名字」）—— 但角色词至少得有一个真在用，否则整节
就是一块谁也不认的公告板。

**角色类住在 `@layer shared` / `@layer page` 里**。这两层定的是「谁让位」,不是装饰:角色
(`.card-ink` / `.chip-ink` / `.btn-seal` / `.t-*` / `.tap-row` …)裸写在
`@tailwind utilities` 之后时,同特指度下后出现的赢 —— 模板里拼在角色上的工具类会
**静默失效**(实测 36 处:胶囊上的 `text-[10px]` 仍是 11px、卡上的 `border-dashed`
仍是实线、`bg-cinnabar/6` 与 `shadow-lg` 一个都没落地,连秘境卡「未解锁 = 虚线框」
从上线起就没画出来过)。全局层序固定为 `reset < shared < page < app-utilities`;
页面样式随路由分片加载,但后到的 `page` 仍不会翻到工具类上面。角色定基线,
调用处的工具类永远能盖 —— 这才是上面「装饰性间距/颜色仍用 utility 拼」那句约定的
真实含义。层内仍是普通书写顺序,暗色覆写照旧按特指度与先后生效。

## 字体:三端统一用随包内置的楷体子集

正文走系统字体栈;标题、境界名、名号走 `font-kai`(楷体),**三端统一用随包内置的
霞鹜文楷子集**(`src/assets/fonts/`,1.7MB)。

为什么内置:iOS 的华文楷体与 Windows 的楷体(还属"中文补充字体",没装的机器本就没有)
各是各的字形,同一款游戏摆在一起会是三种气质。用的这一支是 **GB 屏幕阅读版** ——
GB 版按 G 源改了字形(原版源自日本的 Klee One,「这 边 过 运」的辶旁是日式两点辶),
屏幕阅读版把笔画调实,10~13px 的小字清楚得多。系统楷体退到字体栈第二位,
只替子集盖不住的生僻字兜底。

重做切片(加了新内容、字表不够用时,或要调片的大小):

```bash
uv run scripts/fonts/build-kai-font.py        # 每片约 180 常用字 + 700 储备字
```

子集分成二十来片按需下载(每片一段 `unicode-range`,声明是生成物 `src/assets/fonts/kai-subset.css`):
一份 1.8MB 的子集在冷启动时是整份下载的,而首屏真正用到的字不过一两百个 —— 切片之后浏览器
只取页面上真出现的那几片。字体覆盖与「切片 ↔ unicode-range 对得上」由
`kaiFontCoverage.spec.ts` 盯着,首屏到底取了几片、多少字节由 `scripts/first-paint.mjs` 量
(口径与实测见 [development.md](./development.md) 的「首屏与构建时长」)。

## 图标:全套水墨笔意(`src/ui/inkIcons.ts`)

图标是最后换掉的一层,如今**整层都是自己画的**:界面其余部分(宣纸底、松烟墨、楷体、
印章按钮、五声音阶配乐)本来就是古风的,唯独图标那一层曾是 lucide 的西式几何线性图标
—— 等宽笔画、圆头圆角、左右严格对称。单看没毛病,摆在楷体与印章旁边就是「现代 App」的
口音。

换的是**形与笔,不换语言**:同 24 网格、同线宽(2 起)、同圆头圆角。

- **形**用中式名物:山(洞府)、丹炉(修炼)、双剑(历练)、囊(背包)、打坐的人(人物)、
  灵石、云气(灵气)、墨齿毂(设置)、兽爪、枯骨、横头斧、长枪、仙禽、草檐屋舍、锻锤、
  灵苗、典籍、亭台(界域)、葫芦、文书、水纹…… 原先是火焰、登山包、人像、齿轮、
  西式尖顶小房子那一套。
- **笔**留一点手写偏差:峰不顶尖、两侧不对称、起收笔略短。
- **功能性图标只改笔不改形**:锁、开锁、分解、关闭、刷新这几枚是入口的形状约定 ——
  把「锁」画成中式挂锁可以,换成别的意象就让人找不到入口了。

每一枚都对着**真尺寸的真上下文**定稿(导航条 20px、背包格 16px、界域卡 16px)。其中两枚
改过两轮:斧(数据里刀、戈都归它)试过「大刃短柄」与「长柄小刃」,放进 16px 的背包格都
读成一把钩子,横头那版才立得住;长柄兵器(枪、钩都归它)原画「杖头一颗珠」,16px 下与
字母 P 无异,改成斜杆加倒刺才读得出是杆兵器 —— 只对着原型图看,这两处都会自以为是。

判据在 `src/ui/inkIcons.spec.ts`:常驻那八处必须是水墨版、每一枚都得在界面真的用得到
(画了没人用只是多出来的第二种语言)、笔路不许越出 24 网格、写死的图标名必须登记过
(认不出的名字会静静落成星芒,`shield-check` 就这样藏了很久)。

兵器的名目按件分开了:刀 `saber`、戈戟 `halberd`、枪 `spear`、钩 `hook`、斧 `axe`,
长条的鞭与尺归 `wand`。原先只分两类(刀戈斧都归 `axe`、枪钩戟都归 `wand`),于是
「长刀配斧形图标、长枪配枪形图标」这种近似对得上、细看不对的情形一直在。

敌人与灵宠的形按**族类**发(`src/data/beastFamilies.ts`),不按「大类够用」。原先是数据里
直接写 icon,于是 132 只敌人只用了 19 枚形:46 只挤在一枚骷髅里(独角妖狼、霞光巨蟒、
黑风妖王、玄冰蛟、万妖林主都是一枚骷髅),兽爪那一枚同时是野狼、野猪、石猿、灵狐 与
「麒麟」;灵宠那边应龙与螭龙幼子是星芒、麒麟是兽爪、雪背小龟是一面盾。现在数据里写的是
族类(`family`),形由 `BEAST_FAMILIES` 给出 —— 29 族对 29 枚形,146 条(132 名敌人 +
14 只灵宠)各归其族:狼 `wolf`、狐 `fox`、豕 `boar`、熊 `bear`、猿 `ape`、鹿 `deer`、
蛇蛟 `serpent`、龙 `dragon`、麒麟 `qilin`、龟 `turtle`、蝠 `bat`、羽禽 `bird`、鱼 `fish`、
走兽 `paw`、草木 `leaf`、水属 `waves`、亡灵 `ghost`、傀儡 `puppet`、剑器 `sword`、枪器
`spear`、甲士 `shield`、妖魔 `demon`、仙 `immortal`、神 `god`、灵 `sparkles`、星辰 `star`、
月华 `moon`、天外 `cloud`、金玉 `gem`(雷属那一条没立:御雷猴的名物是猴,归 `ape`)。

判据在 `inkIcons.spec.ts` 的「图标 · 族类」一节:**一枚形被一个以上族类共用即红**;另加
「同族共用同一枚形、数据不许自己写 icon」与「族类表里不留闲族」两条。新画的十五枚形都
在 16px(灵宠列表)与 18px(战斗面板)的真尺寸下核过 —— 走兽那一类形近,靠耳、角、吻、尾
这类可辨的部件拉开,不是靠原型图上的细节(斧与长枪当年就是这么返工的)。

### 三生录的「行年」:把散在四处的道历收成一本按岁读的谱

图鉴、名号与灵兽三处各自记着「何时得来的」(道历 = 第几世 · 多少岁,见
`src/ui/codexMoment.ts`),但三张表**各按自己那一册的规矩排序** —— 图鉴按品类、
称号按名录、灵兽按品阶。那是那三册的正事(找某一件东西时按品类才好翻)。

可「我这一世都做了什么」是另一件事,而它此前没有一页在讲。行年就是这一页:把
四处已记的道历合成一条年谱,按**世分卷、卷内按岁**排开。

版式上只做三件事,都有理由:

- **按世分卷,卷次从新到旧**。道历的两个读数本来就是一粗一细(`世`跨世不变、
  `岁`在每一世里从零数),故「世 → 卷,岁 → 行」是那对读数自己的形状,不是排版偏好。
- **一枚小方印标来路**(册 / 名 / 兽 / 世),沿用全页 `.legacy-duel__mark` 那种方印,
  不另造记号。旧世那一卷的印用虚线边 —— 它是归档,不是这一世新得的。
- **卷内分页,先铺 8 行**。后期此世光图鉴就两百多条,一帧全铺会让这一册比同页其余
  几册重一个量级;续开按钮报「余 N 笔」,与全站长列表同一套(`core/listRender`)。

两条**诚实**口径,比版式重要:

- 旧档里已收录的条目没有道历(那三处的用例各自钉着「不补造」)。它们进不了年谱,
  卷首照实说一句「另有 N 笔早年的账未记道历」—— 把不知道的时刻编出来比空着更坏。
- 前几世没有逐笔道历,旧世那一卷只写那一世的**终局一笔**(终点境界与终寿,取自
  `LifeRecord`),不假装记得那一世某年某月做过什么。

册口在手机上铺 2×2、末一枚**整宽收束**(第五册落第二列会读成"少了半格");
620 起五列并读。两条都由 `scripts/layout-check.mjs` 量住,含「续开真的多出行」一条。

### 四册的道历都要报「何时得来」—— 法宝册是最后一册补上的

「何时得来的」是一类事实,记在**同一个入口**:`quests.collect()` 给每条收录写下
`collectedMoment = { life, age }`(第几世 · 多少岁),`ui/codexMoment` 把它说成
「第 N 世 · M 岁」。

但**读**它的地方是陆续补上的:装备与丹药图鉴(第 7 轮)、称号(第 27 轮)、
灵兽(第 34 轮)。行囊的法宝册一直没读 —— 数据早就在,只是那张行卡从没印过。
于是四册里三册报得出「刚得的还是早就有的」,唯独最稀缺的那一类报不出
(全表 45 件、神品 5 件,还是「天降机缘」式地落进手里)。

补法只有一句:**读同一份 `collectedMoment`,用同一个 `codexMomentText`**。
不新记字段、不新写历法;旧档里没有读数的照实说「早年收录」—— 与其余三册同一条口径。
行卡上的位置、落点(`data-artifact-moment`)与灵兽谱「结缘的那一刻」一脉相承。

顺带修掉了夹具的一个盲区:展品档的 `inventory.artifacts` 恒为空数组,
于是法宝册在**所有**截图与排版门里都是空态 —— 行卡上的被动、神通节拍、下一重、
何时得来,一个分支都没被量到。现在夹具里放了神品与凡品各一件(混沌钟 + 墨玉葫芦),
高档与低档的行卡同时在场。

### 灵兽谱也盖品阶角章 —— 全库最后一份兑现「形状线索」的名册

`ui/qualityTier` 把规矩写死过一句:

> 稀有档另有 QualitySeal 角章作形状线索 —— 色弱玩家不靠颜色也能分档。

各处都照做了:装备格、功法书目、法宝行卡、候选件、坊市货架,天品起都盖一枚阴文小章。
唯独**灵兽谱**没有 —— 而它恰恰最需要:那是唯一一张四十只**全部排在一起**的长名册,
颜色相近的邻行挨得最近(良品 jade 与精品 qing 同属青绿系,纸面上几乎难分)。

颜色是**顺序标尺**(要比较),章是**离散标记**(扫一眼就有)。两者并存才既排得开也认得出。

补法不新造记号:直接用现成的 `QualitySeal`,位置与功法书目那一枚同款(名字前、`shrink-0`),
判定走共享的 `isRareQuality` —— 界在哪一档只由 `ui/qualityTier` 一处决定。
相伴面板与逐行各盖一枚,落点 `data-pet-quality-seal`。

**未结缘那几只刻意不盖**,也不给名字(显示「???」)—— 名都不给看,自然不该透露品阶,
那是「去结缘」的钩子。判据因此只量已结缘的行,且**两侧都量**:该盖的要盖,
精品的一枚都不许多。两个方向的变异都试过(删掉角章 / 去掉稀有判定),判据都当场红。

### 提示条停多久 —— 四条感官里最后一条跟上了品阶

品阶的分层是逐轮补起来的:

| 层 | 轮次 | 分档 |
| --- | --- | --- |
| 颜色与边框 | 第 18 轮 | 灵/玄/地 · 天仙 · 神 |
| 全屏那道光 | 第 21 轮 | 1.1s · 1.35s · 1.6s(`ui/flashTier`) |
| 那一声玉振 | 第 22 轮 | rare · rareHigh · rareTop(`ui/rareSfx`) |
| **提示条停多久** | **本轮** | 2600 · 4200 · 5200 · 5600(`ui/toastLife`) |

前三条都是「一瞬间」的反馈,第四条是玩家**真正去读**的那一层:「天降机缘!获得法宝
「混沌钟」」这种句子要读完,还要决定点不点开去看详情。神品那条更长、更值得读,
此前却和灵品同时消失 —— 读慢一点就没了。

时长比颜色更稳:颜色在暗场与亮场观感差别很大(品阶色有深有浅),而 4.2 秒与 5.6 秒的差别,
人不需要对比就能感到。这与 `flashTier` 选时长当主尺是同一条理由。

**四层读同一把尺**:分层的界(rank < 6 / 6-7 / ≥8)只在 `ui/qualityTier` 定,其余三处都引它。
同一条提示不许出现「光按神品闪、声按神品响、却按灵品的时长停」。

**寻常提示逐位不变**:info / success / warn 仍是 2600,没有印的 rare(转世 / 突破 /
里程碑)仍是 4200 —— 这次只给稀有段那两档加时。

判据落在真浏览器里:停留时长是四条感官里唯一**看不见**的那条,只能实测。故算出来的毫秒
落到 `data-toast-life` 上,门才能量「神品那条真的比灵品久」。判据做的是**两档对比** ——
同一条真路径(藏经阁参悟)跑两遍,只把池里剩下的那一部换成另一档的功法,
差只差在品阶。变异验证:把 high/top 都压成 4200,三条判据同时红。

### 器评帖补一行「行迹」—— 它经历过什么,不只是它生来是谁

每件装备身上早就记着四笔账(`types` 的 `EquipmentInstance`):强化等级、
重铸次数、封存词条、累计投入。但这四笔此前**分散在四个角落**:

| 账 | 此前在哪读得到 |
| --- | --- |
| `level` | 器评帖眉题上一枚 `+N` 角标 |
| `reforgeCount` | 只有重铸面板那一行 |
| `sealedAffixIds` | 同上 |
| `invested` | 只有分解返还与器魂警告 |

于是玩家点开一件跟了自己几百场的旧器,看到的是「品质 + 词条 + 器铭」这一套**出厂信息** ——
它经历过什么,详情页里一句都没有。

器铭讲的是「**它生来是谁**」;行迹讲的是「**它后来成了什么**」。两件事,两处:
不把工序塞进铭文,也不把出身复述进行迹。版式沿用器铭那一行(虚线分隔、note 字号、
左「行迹」右读数)—— 同一张帖里两种分隔线会读成两套账。

**不新增任何字段**:四笔账都是既有字段,这条信息一行都不缺,谈不上迁移。
**不给任何加成、不参与任何判定**(与器铭同一条纪律)。

诚实口径三条:

- 什么都没做过的一件 —— **整段不出**,而不是印一句「尚无经历」占地方;
- 只有 `invested` —— 也不算经历:投入说的是"花了多少",不是"做过什么工序";
- 坏值(负数 / NaN / 封存条数超过词条数)夹回合法范围,不印出「封存 5/2」。

判据落在真浏览器里,且**两侧都量**:炼过的那件要真读得出那三笔,
全新那件一个字都不许多说。变异验证:把 `v-if` 改成 `false` → 做过工序的两件报红;
改成 `true` → 全新的那件报红。还原即绿。

### 品质读数只增不减 —— 分解不该让「曾得过」消失

**复现出来的事故**:成就谱上「天品 / 仙品 / 神品」那几行的进度条,读的是
`inventory.items` 里**此刻**最高的那件(两页各写了一遍 `reduce`)。而分解会
`inventory.removeEquipment(uid)` 把那一件拿掉 —— 于是:

```text
得一件仙品 → 「现持 仙品 → 神品」 → 分解掉它 → 「现持 凡品 → 神品」
```

更糟的是已解锁的成就不掉回(`quests.achieved` 只增),所以同一屏会出现
「✓ 已达成」与「0% 尚未达成」并存,两张卡互相打脸。

**为什么「曾得过」才是对的**:成就是**一次性事实**,与 `core/peakRealm`
(历世最远那一境,「转世折回起点不会把足迹抹掉」)同一条规矩。品质这一处漏了。

**做法**:新记 `quests.peakQualityRank`,只增不减 ——

- 抬升只在**一处**:`progress.checkQualityAchievement`,凡是"见过这一档"的路径
  都从那里过(与 `player.notePeak` 同一条纪律:两个调用点就是两本账);
- 兜底在 `sanitize`:旧档没这一栏时按**当前持有**回填一次,不按成就反推更高的值;
- 折算法是纯的,落在 `core/qualityPeak`;读 store 的编排落在 `ui/qualityPeakStores`
  —— 因为 `core` 不许 import store(`core/layeringAudit.spec` 的名单制判据当场红)。

**只算装备,不扩到四类**:品质不是装备独有(法宝 46 件、灵兽 40 只、功法 68 部各有品阶),
初版一度把四类一起算了。但 `a_q8` 的条件原文是「获得一件**神品装备**」—— 把法宝/灵兽/功法
也算进来,成就就比它自己说的更宽松:玩家拿一只神品灵兽就点亮了「神物自晦」。
故这一处**只读装备**;要扩到四类,该改的是成就条件原文与被它读的口径,不是悄悄放大读数。
(这条是排版门当场撞出来的:夹具有一件神品法宝,四类算法把该行顶成"已持 神品",
整组因此被排到第一位,另一条成就判据当场红。)

判据走**真路径**:种一件仙品(a_q8 差一档)→ 记读数 → 器评帖垃圾桶 → 确认分解 →
读数必须一致。中间补了一条**反空转**判据:「那一件真的没了」 —— 第一版就是栽在
东西没分解掉、读数当然不变、门看起来是绿的。

### 九佩也盖品阶角章 —— 同一件装备,两处长得不一样

`ui/qualityTier` 写死了规矩:「稀有档另有 QualitySeal 角章作形状线索 ——
色弱玩家不靠颜色也能分档」。库里各处都照做了,**连同一套装备的另一处也照做了**:

| 位置 | 此前 |
| --- | --- |
| 点开某一席看的候选清单(`SlotCandidatesDialog`) | 有章 ✓ |
| 行囊主页那九张席位卡(`InventoryView`) | 只有名字的字色 ✗ |

于是玩家扫九佩时分不出哪一张是天品,点开候选清单才看得到章 —— 同一件装备,
两处长得不一样。

而九佩恰恰比候选清单更要紧:候选清单是"换装时"才打开的,九佩是**每局都在眼前**的
那一屏;九张并排,颜色相近的邻格挨得最近(良品 jade 与精品 qing 同属青绿系)。

补法同前几轮:直接用现成的 `QualitySeal`,判定走共享的 `isRareQuality`,
位置沿用其他名册的规矩(名字前、`shrink-0`)。

**这一轮的夹具教训值得单记**:第一版把「凡品那席」也填成 `w_zhuqing`(一把剑),
而 `head` 槽根本不收武器 —— 入库层当场把那件丢了,于是"不该有章"那半边**根本没渲染**,
判据空转还不报红。是变异测试(给所有席位都盖章)撞出来的:
两个方向都该红,结果只红了一个。现在夹具按槽位给模板,并补了一条
「两席里有一席没装上件 → 判据空转」的显式守卫。

### 品质成就的报喜也盖品阶印 —— 同一件事的两次报喜不该差着量级

`progress.announceAchievement` 对所有成就发同一条提示:

```text
notify(`成就达成「${def.name}」`, "rare")
```

而 rare 这一族早就按品阶分层了(印 / 光 / 声 / 停留时长)。于是:

| 事件 | 提示 |
| --- | --- |
| 拾得一件神品装备 | 盖「神」印 · 神品色的光 · 神品那一响 · 停 5.6 秒 |
| 成就「神物自晦」达成 | 什么都没有,与「初有积蓄」同款 |

而「神物自晦」的达成条件**就是**获得一件神品装备 —— 同一件事的两次报喜,
第二次比第一次轻了一整个量级。

做法与前面几轮一致:**从条件里读**,不在数据里再抄一栏。成就定义里已经有
`cond: { type: "quality", rank }`,那一档的名字与颜色全在品质表里,故只做一次
「rank → QualityId」的翻译(`ui/achievementSeal`),不新增字段、不往每条成就里
各抄一遍品质 id。

**只管品质型成就**:累计击杀、境界、自定条件没有「品阶」这回事,给它们编一个印
就是在撒谎 —— `achievementSealOf` 对非品质条件返回 undefined,提示条退回原样。

判据走真路径(老档自愈:身上有一件神品、成就还没解锁 → 启动补扫触发报喜),
两侧都量:**神品那条要有「神」印,非品质成就一枚都不许多**。
判「哪条该有印」读的是 `ACHIEVEMENTS` 的 cond,不靠名字猜 ——
第一版就是按名字列的,把「玄光初现 / 天命之子 / 仙缘深厚」当成了非品质成就,
而它们**正是**品质成就(rank 4/6/7),判据当场把自己举报了。

### 战报里的法宝也带品阶 —— 全作最后一处没有品阶通道的屏

品阶在这一作里已经有很完整的表达(角章 / 光 / 声 / 停留时长 / 器铭),
唯独**战斗回放里那几十行字**没有任何品阶信息:每行只有 `t`
(atk / skill / crit / shield / heal / dodge / proc / info / win / lose),
颜色按 `t` 分档。

而法宝自动出手走的是 `t: "proc"` —— 与「锋连诀」「罡盾崩碎」同一个桶。
于是凡品「墨玉葫芦」回血,与神品「混沌钟」轰出单位伤害,在战报里是**一模一样的字**。

战报是玩家**反复看**的那一屏(每场都回放一遍,一场几十行),而法宝出手是玩家自己
攒出来、配上去的东西 —— 它该在回放里认得出自己。

做法上只加一个可选字段,不动任何既有形状:

- `CombatLogEntry` 加 `quality?: QualityId`,七处法宝出手全递进去;
  老存档没有这一栏,渲染退回原样(与 `LastBattleView.loot` / `firstSight` 同一条先例)。
- **不改 `t` 的联合类型** —— 那会让所有按 kind 分支的地方都要加 case。
- 九档只折三档(`ui/combatLogTone`):战报是密排的几十行,九色认不出;
  只有天/仙/神那三档才描色,神品再加一档分量(竖线加厚)。

**一个 CSS 顺序的坑**:`proc` 本来就有自己的紫(「特殊触发」)。品阶那几条规则
必须写在 `data-log-kind` 那批**之后** —— 同优先级下后写的赢,写在前面就被紫色盖掉。
判据当场撞出来了:神品那行读到的色是 `rgb(178,150,220)`(紫)而不是它该有的朱砂。

判据两侧都量,且**判「染的是不是这一档」而不是「与别的行不同」**:
把该行自己的 `--log-quality` 求一次值,再与实际 `color` 逐一相等比对 ——
只核"与凡品不同"会漏掉"染错了档"。

### 注释里的规模数,是最难发现的那本账

`views/CollectionView.vue` 在分批渲染那段注释里写着:

```text
九册全收是 809 枚 chip,首帧全铺实测 1326 DOM;
```

而按当前数据算,图鉴九册是 **816** 枚:

```text
装备 288 · 悟道 151 · 事件 104 · 功法 68 · 丹药 69
法宝 46 · 灵兽 40 · 天赋 34 · 材料 16  =  816
```

差 7 枚 —— 内容是长出来的,注释留在原地。这种偏差不报错、不崩,只是让下一个读它
的人按错误的分母估算首帧预算。

**它是最难发现的一本账**:不参与任何计算,没有任何判据会红。上轮那条「一律」
是同一形态 —— 写下来的规矩若没人守,它只是一句话。

故补 `ui/codexScale.spec` 三条:

- 九册都非空(空册子说明取数路径断了);
- 注释里「九册全收是 N 枚」与实物相等,红时把九册构成全列进消息;
- 注释里那串构成明细也逐册对得上(写进注释的每个数都得是真的)。

同时把注释改成 816 并把构成列全 —— 下一个读它的人不必再数一遍。

变异验过:把 816 改回 809,判据立刻红,消息里直接给出九册构成,哪一册长胖了一眼看得出。

（这一处是绕了弯才找到的:我先怀疑 816 本身错了,手工估成 528 —— 那是因为漏算了
悟道录 151、事件 104、天赋 34 三册。用 Pinia 起一份真 codex 数出来才确认 816 是对的,
错的只是注释。）

#### 同类:风味文字不许带数值,三处声明只有一处有判据

三份数据文件各自写着同一句话:

| 文件 | 原话 |
| --- | --- |
| `data/earlyGame.ts` | 「`desc` / `effect` 只写**风味**,一个数字都不许带」 |
| `data/inscriptions.ts` | 「每句都不带数字:铭文是叙事,数字该来自这一件自己的成色」 |
| `data/petVows.ts` | 「每句都不带数字:数字该来自 `mods` 与 `petTraitText`」 |

理由是同一个:同一个数既写在结算里又抄进文案,改常数那天文案就开始撒谎。

实测只有铭文那条有判据(`core/inscription.spec`),早游戏与灵兽誓词两头空着 ——
与前一轮那处同一形态:规矩写了,没人守。故补 `core/flavorTextNoNumbers.spec`
把三处一起管住。

**只禁阿拉伯数字,不禁汉字。**灵兽誓词里有「一坐下去,脚下的土都实了三分」——
「三分」是文学虚指(实了三分 = 很实),不是数值承诺,判成红就是误伤。
真正的风险是 `+8%` / `3 分钟` 这类阿拉伯读数:它们长得就像结算真值,抄进文案
才有撒谎的余地。故判据只认 ASCII 数字,并另用一条用例把「汉字数字合法」锁住,
免得后来者收紧口径时误伤。

变异验过两个方向:给 earlyGame 的 desc 加「修行 +8%」→ 红;
把誓词的「三步」改成「3 步」→ 红。

#### 同类:代码注释里的表规模

`core/engineUnlocks.ts` 的头注释写着「内容(`data/achievements` 的 **62** 枚)」,
而成就实际是 **66** 枚。这行字不参与任何计算、没有任何判据会红,
只是让读它的人按错的分母理解「成就对库的接入」这件事。

本仓此前两处规模数都有判据守着:

- `data/*.ts` 的文件头注释 —— `dataHeaderAudit` 读源码文本、取声明的数字比对数组长度;
- 玩法文档 `docs/usage.md` —— 同一份 spec 从表数出数、再要求文档里那句话长得一样。

**而代码注释两头都没管。** 判据只认一个机器可识别的形状:
反引号包住的 `data/<表名>` + 数 + 量词(枚/条/件/部/个/种/只)。认宽了会把散文里
所有数字当成承诺,那是另一种噪音;认这个形状,既抓得住真引用,也不误伤普通叙述。

补完之后另有一条反空转:若一处都扫不到,说明判据退化了,它自己先红。
变异验过:把 66 改回 62,立刻红并点名是哪一行。

顺带说明两处**不是**缺陷的: `core/divination.ts` 的「手写 64 套数值」是在解释
为什么不给六十四卦各写一套(数值只写八卦,`TRIGRAMS` 正是 8);`bossArchetypes.ts`
的「8 种机制家族」与实物一致。注释里出现数字本身是正常写作,判据只盯「引用表规模」
那一种。

### 一条写了"一律"的纪律,却没有判据守着 —— 白泽就是这么漏掉的

`data/events.ts` 在仙品灵兽那批发放事件前写着:

> 境界带纪律:r7 收在 14-17(god),r8 收在 18-20(chaos)。
> 神品**一律不收进** god 带 —— 否则神界就能开出 0.76 预算的镇岳尊。

这条纪律保护的是**稀缺性**:神品被动预算是仙品的一倍多,若神界就能开出神品,
"混沌海才有的东西"这层意思就没了 —— 与法宝那头「早窗的神品仍是这一窗该有的强度」
是同一种保护。

**但没有任何判据守它。**把发放事件按带摊开:

```text
chaos(18-19):10 只,全是神品
god(14-17):  7 只仙品 + 白泽(神品,realm 15)
```

白泽的预算 1.64 是最低的神品,甚至低于最高的仙品(古岳犀 1.77)—— 它大概是
规则收紧之前放的,没被回头清理。注释里那句「0.76 预算的镇岳尊」也已过时
(实际 3.37),说明这段话立得比数据早。

补判据 `core/petWorldBand.spec`:举凡神品灵兽,其发放事件的境界带必须落在 chaos。
另加一条仙品不许落回人间界、一条反空转(混沌海确实收着神品)。

随后把白泽挪到 chaos 带:tags `god → chaos`、`minRealm 15 → 18`,
事件文本里的「神迹荒原」也改成「混沌之滨」—— 与同带事件(北冥化鹏、混沌凶兽)
同一套意象。预算曲线一分未动,只是把位置摆回纪律之内。

**这类缺口的形态值得记住:注释里的"一律/必须/永远"若没有对应判据,它只是一句话。**
变异验过:只改 tags 不动 minRealm 时判据仍绿(判据按 minRealm 优先,符合设计);
连 minRealm 一起改回才红。

### 转世那一刻也该看见道龄 —— 那是它最有力量的地方

道龄(见下面那节)最初只接进了「修行画像」。而**转世对话框没接** —— 那是
「这一世结束了」的一屏,header 里写着:

```text
第 3 世 · 寿数已尽
行世 320 载,止步于真仙。皮囊坐化,神魂仍可再启一程。
道果 12 枚
```

「行世 320 载」是**这一世**的寿数(游戏内时间)。「你陪他走了多久」是另一件事,
恰好在"这一世收官"时最该被看见,却一个字都没有。

**措辞是这一处的关键。**两件不同的量并排最容易误读:`player.age` 是本世的,
`totalPlaySec` 是全账号的。若只写「伴道 45 天」,玩家会以为"这一世玩了 45 天"。
故那一行写「**至今共** 45 天」。

判据两层:

- 单测(`ui/rebirthCompanion.spec`)守接线与措辞 —— 读 `companionTime` 同一对函数、
  读 `totalPlaySec`、带累计标记;
- 浏览器门挂在既有的「走完一次转世」流程上(夹具把 `totalPlaySec` 从 0 改成 45 天,
  否则读数没有量级可言),两侧都量:要有那一行、要读出 45 天、要带「至今」。

变异验过两个方向:去掉「至今」→ 红(「会读成一回事」);整行隐藏 → 红。

### 道龄 —— 一条从没被读过的存档事实

`game.totalPlaySec` 是「**活跃游玩**时长」的存档事实,语义被刻意钉死过
(见 `core/engine` 的注释):缺席时段只走离线那本账,**不进**它 ——
挂机一晚不换天、不白得八小时。它同时是天时、值日宿与际遇概率的派生源
(DEC-120:序号只由游戏内时长决定)。

而这条事实**从来没有被展示过**:全仓对它只有一处读取(星宿对齐),界面上一个字都没有。
于是玩家玩了三个月,看不到任何「我陪这一号人物走过多久」的读数 ——
而这恰恰是放置类游戏最该有的那种感觉。

**放在「修行画像」而不是顶栏**:顶栏是**此刻**的读数(灵石、灵气、寿元),每秒都在变;
道龄是**累计**事实,变了也没有意义去盯着。与「行年」把散落的道历收成一册同一条取向 ——
累计的东西集中在一处读。

**只说人话,不报精确到秒**(`ui/companionTime`):

| 量级 | 标签 | 读数 |
| --- | --- | --- |
| 一分钟内 | 初入此世 | 才开卷 |
| 一天内 | 道龄 | 3 小时 20 分 |
| 一天以上 | 伴道 | 45 天(四舍五入,不带更小单位) |

秒级读数在累计语境里是噪音:玩了 37 小时的玩家不关心多出来的 12 分钟。
两个词也都短(≤6 字),进得去画像那一行。

判据走真路径(夹具种 45 天),两侧都量:要读得出「45 天」,且**不许带更小的单位** ——
后一条防的是「累计读数退化成秒表」。变异验证:藏起那一行 → 红;让更小单位漏出来 → 红。

### 「曾相伴」—— 同一段相伴史,两本书各抄了一半

`quests.petCompanions` 的注释写得很明确:

> 唤作过伴的灵兽 —— 灵兽册「曾相伴/相伴中」档的**唯一来源**。
> 由 player.setPet 唤伴时记档;暂别/换伴都不除名,册上留的是「此世同行过」。

图鉴照做了(`ui/codex` 的 `petStage` 收 `wasCompanion`,四档:
未录 / 已结缘 / 曾相伴 / 相伴中)。

而名号页的灵兽谱**没读它**:`ui/titlesDesk` 的 `petEntryState` 只收
`{ owned, active }`,于是只有三档。结果:

```text
一只你唤作伴、后来换了别的伙伴的灵兽 → 名号页上仍是「已结缘」
与一只从没相伴过的灵兽          → 长得一模一样
```

那段同行在名册里根本不存在。更别扭的是名号页自己的分组提示写着
「**相伴置顶** · 已契次之 · 品阶降序」—— 排序键里只有 `active`,
一只"曾经相伴、此刻不随行"的灵兽既不置顶,也没有任何地方说明它曾相伴过。

补法:让名册与图鉴读同一份 `quests.petCompanions`,`petEntryState` 加收
`wasCompanion`,排序也跟着「相伴中 → 曾相伴 → 已结缘 → 未结缘」——
与提示语逐字对齐。

**两份实现不必逐格相等,而且不该相等**。它们回答两个问题:

- `codex.petStage` —— 图鉴的**深度**(我把它记到多深)。故「相伴中」要求
  曾相伴标记真记过档,`current` 单独撑不起最深的档(防存档缺标记就当满了)。
- `petEntryState` —— 名册的**当下事实**。正伴着就是「相伴中」,不必再查历史。

硬把两者拉齐会把其中一边改错。真正必须共享的是**底线**:
没结的缘,两边都不认相伴标记。

判据两侧都量:A 有结缘 + 有相伴标记 + 非当前伴 → 必须「曾相伴」;
B 有结缘 + 无相伴标记 → 必须仍是「已结缘」。后一条防的是"人人曾相伴"。

**夹具坑**:`seedSave` 是一个只跑一次的 `addInitScript`(靠 localStorage 守卫位),
同一页再种第二次不会生效 —— 第一版两侧探针共用一页,结果都读成「曾相伴」,
判据当场红。改为每次探针单开一页、单用一个守卫键。

### 逆旅契进履历 —— 「被记住」是这份契约唯一的回报,而它没被记住

`data/lifeTrials.ts` 的文件头把这份设计讲得很清楚:

```text
花道果 → 为这一世签一份只加难度的契 → 本世历练全程生效
      → 转世时记入履历 → 记录不进任何计算
```

为什么回报只能是「记录」—— 四条给收益的路(属性 / 资源 / 宿慧 / 道果)全被出口空间
审计堵死,「剩下的只有『这一世确实与众不同,且它被记住了』」。

`core/reincarnation` 照做了,写进 `LifeRecord.trialId`,注释也是同一句:

```text
// 逆旅契入履历 —— 这是契约唯一的回报:被记住,且不进任何计算
```

而**历世履历那一屏从头到尾没读过这一栏**:`LegacyView` 的 `lifeRows` 只取境界名、
寿数、命题与宿慧。玩家花道果买下一世的逆境,转世后翻履历,看到的与从没签过契的
那一世**一模一样** —— 这份契约在玩家眼里确实没有任何回报。

补法只加一行:把 `trialId` 翻成那一契的名与印(`ui/lifeTrialArchive`),
在履历那一世下面补一枚朱砂印 + 契名。纯读 —— 与文件头那条「记录不进任何计算」逐字对齐。
不带 `paid`:实付道果是签约那一刻的账,履历要说的是「那一世你立过此契」,不是一个价签。

判据两侧都量:签过的两世要有那一行(且契名对得上),没签过的不许有。

**夹具坑两道**:①履历按世序**倒排**,签过契的第 1、2 世在最末一页 ——
判据得先把后十八世铺开才量得到;②那一段必须跑在既有的续开/回翻流程**之后**,
自己在中间再点一次「再看」会与既有的 `waitForFunction` 抢状态,任务当场抛异常。

### 器灵尘进「本次所得」—— 少报的恰是玩家没看见就没了的那些

历练面板上那一行写着「本次所得 · 灵石 +X · 修为 +Y」。而一场战斗真正会进账的还有
**器灵尘**:行囊满、或智能留取判定把某件判为不值留时,`acquireEquipment` 会把它当场
折成器灵尘(+ 退灵石),并 `resources.addSmall("dust", …)` —— 尘是真的进了账。

但这条数**从来不进会话账目**:`AdventureSession` 有 `stoneGain` / `expGain` /
`itemGain` / `wudaoGain`,没有 `dustGain`;`afterWin` 的 `DropSummary` 也没有这一栏。
「本次所得」于是少报一样 —— 而少报的恰恰是**玩家自己没看见就已经没了**的那部分:
一件被自动折算的装备,唯一能知道它变成了什么的地方就是这一行。

同一份文件里 `wudaoGain` 的注释早把这条纪律写死了:

> 本场累计所得悟道点(连胜档赏 + 际遇所给 + 重复法宝折化)
> —— 结束总结要报,不能只活在账本里

器灵尘是同一个道理,只是当初漏了。做法是一路加到界面,每一跳都取上一跳的数:

```text
acquireEquipment 的 dust(已有)
  → afterWin 累加成 DropSummary.dust
  → exploration 的会话 dustGain
  → CombatPanel「本次所得」第三格
```

渲染上只在尘 > 0 时出现 —— 这一格不许常驻 0,否则它变成噪音。

**两层判据分别守两件事**:spec 守数据链(`dust += acquired.dust`),
浏览器门守渲染(有尘要报那个数、没尘一个字都不许多)。
第一次做变异时只改数据链,浏览器门**没红** —— 因为它的夹具直接写了
`dustGain: 340`,绕过了累加路径。这不是门写错了,而是它本来就只回答另一半问题;
把两层分开之后,三条变异(不累加 / 常驻 +0 / 整格隐藏)各有其门去红。

### 同一份账的第二处说法 —— 收尾播报也得跟上

上一轮把器灵尘接到了面板的「本次所得」,却**漏了收尾那条播报**:

```text
此行太乙雷池历练圆满,胜 4 场 · 负 1 场,际遇 1 次;
得灵石 120万、修为 340万、悟道点 12、拾获 3 件
```

面板上写着 `器灵尘 +340`,结语里一个字都没有 —— 同一份账两处说法不同。

`dustGain` 当时有四个写入点、**只有一个读取点**。这正是"字段加了、出口没加全"的
典型形态:数据链一通到底,而读取端是一处一处接的,漏一处不会报错、不会崩。

修法上顺手把那段手拼的模板字面量抽成纯函数
(`ui/adventureText.sessionHaulText`),与既有的 `sessionRecordText` 同构:

- **可测**:手拼字面量只能靠正则截文本,而那正是本仓反复说的
  「文案里手写数字,改常数就撒谎」。现在判据喂一份账、断言读出的话。
- **口径一致**:灵石与修为每趟必给;悟道点、拾获、器灵尘只有真发生了才报 ——
  0 尘不写「器灵尘 0」,正如悟道点为 0 时不写悟道点。
- **顺序稳定**:由「每趟必给」到「偶发」,判据钉住这个序。

既有那条 `uiLayering` 断言原本钉的是 exploration 里的模板字面量
(它守的是"散文用全称『悟道点』,不许写裸『悟道 N』")—— 那句话搬了家,
断言就跟着搬到新出处,守的东西一模一样,另外补了一条
「不许又冒回来一份手拼的」。

### 同一行里的两种尺子 —— 器灵尘要走同一个 formatGN

「本次所得」那一行写着三样:

```text
本次所得 灵石 +120万 修为 +340万 器灵尘 +12345
```

灵石与修为走 `formatGN`(折成「万 / 亿」),而器灵尘是两轮前新加的,当时直接印了
原始数字。同一行里两种格式并排 —— 前两个折过,第三个是裸的。

**不是理论问题**:一场战斗最多一次装备折算(尘 1~256,见 `DECOMPOSE_DUST`),
看着不大;但「本次所得」是**一场会话的累计**,最长的长线云游是 4 小时,
按战斗间隔算下来上千场,累计到五位数是正常量级。实测三档:

| 尘 | 读出来 |
| --- | --- |
| 340 | `器灵尘 +340` |
| 12345 | `器灵尘 +1.234万` |
| 1234567 | `器灵尘 +123.5万` |

修法上注意一处:**格式化落在模板那一处,不在 computed 里**。
`gains.dust` 得保留原始 number,因为同一段模板要用 `> 0` 判这一格出不出;
在 computed 里就折成字符串,判空那句会变成拿字符串和数字比
(实测 TS 当场报 `Operator '>' cannot be applied to types 'string' and 'number'`)。
判据因此也看模板里那一句,而不是 computed。

### 账格的印 / 状态 / 单位 —— 器魂第一格把「席」念了三遍

器魂页卷首那三格,读出来是:

```text
席 三席 0/3 席      闲 闲置 0 缕      凝 可凝 3/3 件
```

第一格里 `mark`(印)是「席」、`label`(状态)是「三席」、`unit`(量词)又是「席」——
同一个字出现三次,而这一格真正该说的是「用了几席」。

`LedgerTally` 是三个页面共用的账格组件。天界那边四格用的是
「印 + 状态 + 判断短语」(道/道途/道已定、征/远征/界已破),每个字都在传信息;
器魂这三格里唯一重复的那一格,恰好是玩家最先看到的一格。

改法只动 `label`:三席 → **已用**。于是三格结构一致(印 / 状态 / 量词),
读作「席 已用 0/3 席」——印说明是哪一本账、状态说明这个数是什么、量词说明单位。
下面那行 detail 照旧报「尚空 3 席 / 三席俱满」。

判据守的是**状态不复述印与量词**,而不是"三者两两不同":
印与量词同字是合法的(「席」这本账数的就是席),「闲·闲置」这种自然搭配也不算复述。
第一版判据写成"三者不许重复",把这两类都误判了 —— 写宽了会逼人去改本来正确的格子。

### 天品法宝 —— 九档里唯独那一档是空的

`data/artifacts.ts` 的文件头如实列着各档分布,里面有这么一项:

```text
· 玄 6(t28-29)· 地 5(t30-31)· 天 0 · 仙 1(t32)· 神 5(t19/20/31/32)
```

「天 0」被记在案,但它与其余八档并列 —— 那是**如实记录**,不是设计意图。
反证在本文里:

> 各处都照做了:装备格、功法书目、法宝行卡、候选件、坊市货架,天品起都盖一枚阴文小章。

天品被当成正常存在的档在界面语言里用着,而法宝池里那一档是空的 ——
玩家从地品一路炼上来,在地品之后、仙品之前撞上一段没有东西可捡的路。

补的是「**归墟混沌盏**」(天品 · 混沌海 t31 · 吸命)。几处约束都是算出来的,不是估的:

| 约束 | 要求 | 取值 |
| --- | --- | --- |
| 效果阶梯(同族不回落) | 同族 t27 灵品 3.623 ≤ x ≤ t32 神品 8.014 | 基线 3.0 × 天品倍率 2.236 = **6.71** |
| 被动预算 | 同族 1.2 ≤ x ≤ 4.2 | base 0.79 × 2.236 = **1.76** |
| 界域印记 | 混沌海须命中「混沌鸿蒙本源真灵无极开道界神魔」中一字 | 名里带「混」「沌」 |
| 吸命封顶 | 回复不超过打出去的那一份 | healPct 0.4 × 2.236 = 0.89,未撞 1.0 的顶,留祭炼空间 |

判据守的是**九档皆不空**,而不是"每档至少一件":灵兽那边「九档中补齐七档」是明写在
文件头的设计取舍(按神话谱系收,不硬凑),法宝这边没有任何一句「天品留空」的说法 ——
两种意图不同,判据也不该一样。另有一条钉住文件头那张分布表与真实件数同源。

补一件法宝会撞到五处对账(表头计数、README 特色段、系统一览表、usage.md 结构数、
高界名字带界域印记)—— 这正是本仓「不做两本账」在起作用,一处没同步就红。

### 元婴境只有两部主修 —— 而主修席只有一个

把功法按准入境界摊开,境界 4(元婴)只有:

```text
大光明普照经(主修)· 幽冥噬魂录(主修)
```

主修席位是**唯一**的。于是元婴境的玩家在功法上其实只有一个选择:两部里挑一部戴上,
另一部连同整个辅修/秘术两层都摸不到 —— 一直要等到境界 5 才有辅修。

**这不是新标准,是数据文件自己写的**。`data/gongfa.ts` 补仙界那几境时留了:

> 仙界其余四境各补一部 —— 此前 10-13 境的人只有一件本境功法可参,
> 「主修只此一部、辅修只此一部」的时候,**参悟这件事就没有选择可言**。

作者已经认定"没得选"是要修的缺陷并按此补过内容;境界 4 是那轮补漏之后的残留:
它有 2 部,但**同为主修** —— 席位数不变,选择数还是 1。

补了「元神灵动篇」(辅修·玄品)与「婴火炼神术」(秘术·玄品),各配两条悟道分支
(`gongfaBranch.spec` 要求全书功法都有分支,漏了会被当场拦下)。

判据 (`core/gongfaRealmCoverage.spec`) 只说一件事:**每个准入境界都至少有一部非主修功法**。
它不规定每境几部、什么品质 —— 那是内容设计的事;它只钉住"除了那唯一的主修席之外
还有东西可参"。

为什么不用「每境三类齐全」:开局几境本就该轻(境界 0 有 9 部可挑),
拿"三类齐全"去卡会把一个健康的节奏判成红的。**少一档不是缺陷,只剩一个选择才是。**

补完撞到四处对账:文件头部数与分类数(66→68 / 辅修 23→24 / 秘术 15→16)、
README 特色段、系统一览表、usage.md 的部数与分支数(147→151)。

### 判据可以被"恰好"绑架,也可以被过滤器骗过

法宝册那条「炼化换位后焦点不能丢」的判据,原写作:

```text
refined.shown === backStart
```

它只在焦点卡**恰好**仍落第 0 批时成立。法宝池补到 46 件,焦点卡换位更远,
窗口按同一条规则开到第 3 批末尾 —— 组件是对的,判据把"恰好"当成了契约。

改成写死「重开到第 N 批末尾」也不行。实测:同品阶只有 6 件、批次也是 6 件,
单次 +1 级**不可能**把卡推出同一批。那条路在当前数据与排序规则下走不到,
守一条走不到的路等于没有判据。

故改为守两条路都成立的**共同承诺**:焦点仍在那张卡上、窗口覆盖它、
窗口停在批次边界上。批次常量从组件源码读而不手抄(先抄成 12,组件实际是 6)——
手抄一份就是第二本账。

**这一轮真正花时间的是一个方法论错误**:为快速迭代,我曾用
`LAYOUT_ONLY=<任务名>` 只跑一个任务。但那段判据属于 `taskArtifactListOverflow`,
我却用 `LAYOUT_ONLY='名号与灵兽两册'` 去跑 —— 任务根本没进,于是:

- 三种变异全部"通过",看起来像判据空转;
- 加了必失败的探针也不出现,更坐实了"空转"的误判。

真相是**过滤器一个字对不上,整个任务就没跑**。换成正确的任务名后,
探针立刻出现、变异立刻变红。教训:用名字过滤时,名字要从注册表里核对,
而不是凭印象写;变异测试跑绿了,先怀疑过滤,再怀疑判据。

### 触感 —— 四个感官都分层了,手还是没感觉

品阶报喜在本作已经分了四层:

| 层 | 模块 | 分法 |
| --- | --- | --- |
| 颜色与边框 | `ui/qualityTier` | 灵/玄/地 一档、天仙 一档、神 一档 |
| 全屏那道光 | `ui/flashTier` | 1.1s / 1.35s / 1.6s |
| 管钟那一响 | `ui/rareSfx` | D5 / F5 / A5 + 低八度 |
| 提示条那枚印 | `ui/achievementSeal` | 色与单字取自品质表 |

而**手**什么都没收到。手机是拿在手里的设备 —— 拿到一件神品时,眼睛看到印、
耳朵听到钟、手指却毫无知觉。这是五感里唯一空着的那一个。

补 `ui/haptics`:

- **档位不另立一份**。三档的界只存在于 `ui/rareSfx` 的 `rareSfxOf(rank)`
  (≥8 神、≥6 天仙、其余灵玄地),`hapticTierOf` 直接转调它。
  判据用 14 个 rank 逐位比对两个函数 —— 变异验过:把触感的界改成 ≥9,
  rank 8 处立刻被抓住("声音说神品、手感到天品"正是本仓最忌的分家)。
- **型样用「段数 + 间隔」而不是一次长震**。单次长震在任何设备上读起来都一样;
  点几下、点多久才分得出厚薄:灵品一下 12ms、天仙两下、神品三下且末一下最重。
  与声音那边"同一口钟敲在更高的地方"是同一思路。
- **各档都要短**。超过约 200ms 会在手掌里变成"嗡嗡"而不是"一记";神品三段共
  约 120ms 已经够重。
- **独立开关,不挂到音效上**。想听声不要震的(手机放桌上)、想要震不要声的
  (深夜戴耳机)都常见;绑在一个开关上,玩家只能在两者间二选一。
- **还要尊重「减少动效」**。那个开关的语义是"别给我动的东西",而震动比动画
  更直接作用在身体上。故实际条件是 `hapticsOn && !reduceMotion`,设置页在
  两者冲突时明确写出"两处要一起开才会震",不让机制藏在结算里。
- **不支持就静默降级**。`navigator.vibrate` 在 iOS Safari 上不存在、桌面通常也没有
  —— 这不是错误,是这台设备没有这个感官;不抛错、不打日志。

接入点在 `stores/ui` 的 `toast()` —— 所有提示的唯一出口,品阶在 `stamped` 里已有。
只在 `kind === "rare"` 上震:寻常提示每分钟好几条,每条都震就是骚扰。

补开关时撞到 `settingsDesk.spec` 那条「六组设置选择共用可点账签」—— 数字要
从六改七。判据的实质是"每组都用 `InkChoice`、不留 38×22 小号开关",
新增的触感组也用了 `InkChoice`,符合实质,故是同步而非放宽。

## 动效

`rise-in` / `shimmer` / `pulse-ring` / `bar-grow` 等关键帧,`.stagger-in` 做入场序列;
动效只用来表达"发生了什么"(获得、进阶、进度推进),不用来点缀。

全站换页也按书页方向读,而不是统一上下淡入:从玄枢目录较前的册翻到较后的册时,
新页自右手边压进来、旧页向左退;回翻相反。欢迎页、建号页这类尚未入册的开卷才走
横向展开。方向由 `navigationPositionOf` 的卷次册次判定,书首卷次、卷首册签与
翻卷动效因此共用一套「前后」。位移只十余像素,不把正文甩出屏幕;
`prefers-reduced-motion` 与应用内「减少动效」仍把时长压到零。

卷首书口签在常态优先报短册名,不只留单字猜谜:390px 起露出两字短名,320 与
195(200% 缩放)自动退回单字签,不让导航本身把页头撑成两行。

## 无障碍

`prefers-reduced-motion` 下全局禁用动画;交互元素保留可聚焦性与语义标签。
小字的对比度账目(哪些一档过 AA、哪些还欠着)由 `src/ui/palette.spec.ts` 盯着。

**页面不许禁掉缩放**。`index.html` 的 viewport 从首个版本起写着
`maximum-scale=1.0, user-scalable=no` —— 低视力用户放大不了页面,而这条规范与 AGENTS
的移动端口径都在「按 200% 缩放防折行」上做了好几轮:一边修 200% 档的排版,一边把
200% 关了门。它当初大约是为了挡 iOS「输入框聚焦自动放大并顶偏布局」,而那是可以正面
解决的:**文本输入框字号 ≥16px**(iOS 的自动放大门槛是计算字号 <16px)。两条一起成立 ——
只关缩放是拿无障碍换省事。现由 `uiLayering.spec.ts` 两条判据守:viewport 不许含
`user-scalable=no` / `maximum-scale=1`,文本输入框一律 ≥16px。

另外两条在真浏览器里量(`scripts/layout-check.mjs`):

- **渐变与图片底上的对比度(第四十二条)**:`palette.spec.ts` 与「按声明色合成」那一条都只
  算得到色号 —— 底色一旦是渐变、纹理或图片,它们要么按最外层的默认白算,要么把半透明的纸
  当成不透明的纸。故这一条直接采样屏幕像素:把文字临时藏起来拍一张,逐像素问「这枚字落在
  这一像素上读不读得出来」,读不出来的像素超过两成就红。**它第一次跑就抓到一处真事**:
  外壳角上那两团云雾是 `bg-white/40`,白天是纸上的湿气,夜间把底色抬到 `rgb(78 76 74)`,
  没进卡片的淡墨小字(章节副题、栏目标签、列表注脚)掉到 3.8:1 以下。现在云雾按主题给
  明度(`.mist` / `.mist-soft`,夜间 0.06 / 0.04 —— 收到这个量才让 11px 的淡墨在
  最亮那一片雾上也过 AA)。
- **两百档字号(第四十一条)**:390 宽的机型按 200% 放大后,布局视口只剩 195 CSS px ——
  比 320 那一档还窄 125px,量的是**缩放档**而不是宽度档。尺子与巡页同源(同一个
  `measurePage`),判六条:横向溢出、外壳被滚偏、越界元素、主值行折行、**文字被挤成竖排**、
  **短动作标签被折行**(≤6 字)。
  后两条是补上的:此前只判前四条,而这一档恰恰最容易把「一行几块横排」挤成一条 ——
  实测 195 宽下 14 个页面把标题、属性名、动作键压成一字一行,门一路全绿。补它必须
  先逐页修完再收口(一把放开就是十几处同时红,逼人削判据)。
  按钮折行只算**短标签**:整宽长文案按钮(「散尽修为,重入轮回(清空存档)」这类)折行
  是读得出来的正常换行,不该判红。它抓到两处:
  设置页的 `input[type=range]` 按原生最小宽度把整行顶出去 6px(`min-w-0`),修炼页的
  修为行被挤成两行(`flex-wrap`,值整块落到第二行而不是折断)。
  器魂页的三列槽位在这一档退成三行账:195 宽下若仍三列,每格只剩 49px,
  「显形·锋魂」六个字必然折成两截、动作键一字一行;退成三行后,序号、印章副本与
  动作沿同一行续排,名字与短动作都保持横读,320 / 390 两档不受影响。220px 档位与
  共享排版巡页同源,不在组件里另写一套阈值。
  这一档量**两遍存档**:主巡页那一遍是刚建号的空档,后期档那一遍是神人境 + 成套装备 +
  在途秘境。理由是空档量不出这一档真正的难处 —— 九位数灵石、满屏内容全挤在 195 宽里;
  与 320 那一遍同一个道理,只是那一遍的视口还没窄到 195。

- **28px 触达下限是两个轴(第四十三条)**:这条门曾经在 1280×800 的 /adventure 上
  报过一次「28px」的红 —— 打印出来四舍五入正好等于下限,实际是 27.6px 的子像素抖动,
  而那个按钮声明的是 `min-h-[28px]`。一条会自己变红的门比没有门更糟,故四处量 28px 的
  地方统一成:声明的 `min-*` 到了 28 的给半像素容差,报数带一位小数。
  原先只量**高度**:高度给足了,宽度可以窄到 7px 也算过 —— 实测「修为 5.7」那枚可点数
  只有 17.5px 宽、「▸来路」25px,高度都在 30~32px,判据一路绿灯。横向同样按 28 判,
  窄的那条用横向负外边距补(`-mx-1.5 px-1.5`),视觉位置一分不动。
- **控件的声明 = 控件的行为(第四十四条)**:器魂页的空槽位从前无论有没有器魂都挂着
  `role="button"`、`aria-label="空"`,tabindex 才给 -1 —— 读屏念出一个"空 按钮",按下去
  只把详情对象赋成 `null`,弹窗连开都不开。声明了 affordance 却不给操作,比不声明更坏:
  人会以为自己漏做了什么。现在的形状:卡壳不挂任何 role,「详情」与「卸下」是两枚同级
  原生 `<button>`,有无器魂由 `soulAt(i)` 一处判断(两枚按钮与空槽那句「空」都从它取值)。
  还有一笔账藏在排版里:词条行用 `w-full truncate` 收在一格之内,这要求祖先链上留着
  **有确定宽度**的 flex 容器 —— 容器自己若是 `max-content` 就跟着内容长,`w-full`
  退成 no-op。拆走外层 role 时顺手把这层容器删了,390 / 320 两档的三列网格就被最长的
  那条词条撑出去 53 / 64px(排版自检当场报出,量法见第四十条那一族)。
  三道门同守:`layout-check.mjs` 的 `deadControls` 与 `nestedControls` 逐页扫**看得见**
  的假按钮与套娃控件(前者豁免 role=tab 的 roving tabindex、置灰的 disabled /
  aria-disabled、零盒子;后者放过 `<label>` 里的原生关联与 role=tab 一类组合控件),
  `uiLayering.spec.ts` 的 `buttonNesting()` 再扫一遍**源码** —— 旧形状
  (`div[role=button]` 里嵌真 `<button>`)与「把卸下挪回详情里」都会当场红。
  同一道闸反过来也成立:**真能操作时才给入口**。空槽从前只写一个「空」,而玩家手上有
  闲置形意时那一格正是他下一步该按的地方 —— 现在补一枚「装配」,但它由
  `v-if="idleSouls.length > 0"` 决定**存不存在**,不是 disabled 灰着一枚(那又回到
  "念得出却按不动");点开的是那张清单由玩家挑一缕,不替玩家装某不知名的魂。
  夹具因此要留一缕不装:后期档原先两缕全装上,那枚按钮在 188 页 × 视口那一遍里
  一次都不存在 —— 门量不到的东西,绿得毫无信息(与 `data-value-row` 的活信号同一道理)。

## 镇压：收益受谁影响（查证记录）

- **灵石 / 材料 / 装备与境界无关**：`suppressYield()` 只看区域层级（`1 + tier × 0.15`），
  `stoneByTier()` 同理。同一区域同一时长，境界只影响修为那一路。
- **修为红利随修炼速度涨**：`expGain = cultPerSec × 每秒 8%(每区,封顶 40%) × 时长` ——
  这条本来就该跟着境界走，它是「同源挂机曲线」。玩家感觉到的「境界影响」来自这一条。
- **转世会清零**：`rebirth()` 清空 `suppressedRegions / suppressQualified / suppressedSince`
  （见 `core/samsaraAudit.ts`），界面也已写明「转世重修后需重新镇压」。
- 教训：此前两次「实测境界差 1.8 倍 / 18 万倍」的读数都是**测量方法错误**
  （两次结算塞进同一个测试、以及只比较 GNum 的尾数 `m`）。单次干净实测：两个境界都是 180。

## 洞府为什么不显示「回本时间」

看起来是个好指标,实际算不出来:七座建筑里 `洞府` 抬离线上限、`炼丹炉/炼器台/藏经阁` 给的是
能力或保底;真正产资源的是 `灵田`(灵草)、`聚灵阵`(灵气)等,而它们的**成本是灵石** —— **本作没有定义灵石与灵草的兑换率**,
所以「花 N 灵石多久回本」无法成立。灵脉那条有明确的分红数字,已在 `VeinInvestCard` 里给出。

要提供类似信息,先要有一个官方兑换口径(目前没有,也不该为一个界面而临时发明)。

## 数字一律等宽（tabular-nums）

界面上到处是每秒都在变的读数：灵石、修为、进度 `x/y`、趟数。比例数字的宽度随数值变化，
整行会跟着「抖」——同一屏里几个读数一起变时尤其明显。

规则写在 `body` 上（`font-variant-numeric: tabular-nums`），不是逐个加 `.tabular`：
漏一处就会有一处抖，而漏掉的那处恰恰最难被注意到。新增组件时无需再操心这件事。

## 视觉基线（可复算，别凭感觉）

改界面前后各算一次，数字变了就能对症：这些值都是**不靠眼睛也能量**的。

| 项 | 当前值 | 怎么算 |
| --- | --- | --- |
| 弱字对比（明亮） | `ink-faint` 对纸 **5.13 : 1** | token 取 `--color-ink-faint-rgb` / `--color-paper-rgb`，按 WCAG 公式 |
| 弱字对比（夜间） | **6.47 : 1** | 同上，取夜间那组通道值 |
| 字号分布（17 页合计） | 9/10/11/13/14/15/16/17/18/19/20/22/30 px | 每页遍历文本节点取 `font-size`，合计计数 |
| 外壳一致性 | 15 页共用一套内边距 | `visualRhythm.spec` |
| 裸色 | 组件内 0 处（2 处注明例外） | `visualRhythm.spec` |

口径说明:

- 弱字两档都高于 AA 的 4.5:1 —— 觉得「糊」时先看**字号**，再看颜色。
- 字号里没有 12px 是刻意的:11 → 13 之间不放档，避免两档只差 1px 而难以区分。
