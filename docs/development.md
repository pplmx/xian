# 开发

## 环境

[Bun](https://bun.sh) 1.4.3(与 `package.json` 的 `packageManager` 一致,CI 与 Docker 都按它装;过低会被 `scripts/env-check.mjs` 拦下)。
TypeScript、Vite、Vitest 等都在 `package.json` 里,`vp install` 一次就够。

> `vue-tsc` 钉在 3.3.11:3.3.12 的模板类型检查有回归(把普通 `Record` 常量当 ref,
> 对 `ELEMENTS[e].name` / `STORE_NAMES[id]` 误报 `.value` 与索引类型错误)。
> 待上游修复后再放开。

```bash
vp install
vp dev            # 开发服务器(vite --host)
vp build          # 类型检查 + 生产构建
vp preview        # 预览构建结果
```

### 运行时策略

这个仓库同时有 Bun、Node 两组环境变量,各自管一段,别混淆:

| 角色 | 谁来当 | 承担的事 |
| --- | --- | --- |
| 包管理器 + 脚本执行器 | **Bun** 1.4.3 | 装依赖、锁文件(`bun.lock`)、跑 `package.json` 脚本;`packageManager: bun@1.4.3` 明确的正是这一层 |
| 工具链兼容基准 | **Node** ≥ 24 | `engines.node` 表达的是"跑 Vue / Vite / vue-tsc / Oxlint 这条工具链至少要 Node 24",**不是**「应用跑在 Node 上」(CI 的 `setup-vp` 就装 Node 24) |
| 生产运行时 | **浏览器** | Web / PWA 的最终宿主 |
| 平台运行时 | **Electron / Capacitor** | 把同一份 Web 产物包进 Windows 桌面与 Android 的壳 |

`engines.node >= 24` 与 `packageManager: bun@1.4.3` 并存**不矛盾**:一个约束
「工具链要跑在 ≥24 的 Node 上」,一个约束「安装与脚本托管交给 Bun」,管的是两层。
只要包管理走 Bun、工具链跑在 ≥24 的 Node 上即可。

> **`prepare: vp config --no-agent` 为什么每次 install 都跑**:它在 clone 后把仓库里
> **已跟踪**的钩子(`.vite-hooks/pre-commit`、`.vite-hooks/commit-msg`)
> 注册进 git —— 设 `core.hooksPath` 并生成 `.vite-hooks/_` 分派器。pre-commit 跑
> `vp staged` 和 `bun run type-check`,commit-msg 拦下把 bullet 写成字面量 `\n-`
> 的提交信息,是本仓库自己的提交流水闸;
> 少了它,clone 后这些门会悄悄失效。每次 install 重跑只是幂等的本地注册,代价是毫秒级,
> 换来"钩子永远在"——所以**保留在 lifecycle 里**,不要为了让 install 少一步而拆掉。
> (这些钩子只影响本地提交,CI 用 `vp install` 另跑 `check`+`test`,不依赖它。)

### 用 bun 还是用 vp

**默认用 `vp`**。它统一接管 dev / build / test / lint / fmt / check:
`bun dev`、`bun preview`、`bun run test` 这些只是薄封装,最终都落到 `vp`;
直接用 `vp …` 少一层跳转、行为一致。具体分工:

| 层 | 入口 | 说明 |
| --- | --- | --- |
| 工具链入口(推荐) | `vp …` | `vp dev` / `vp build` / `vp test` / `vp lint` / `vp fmt` / `vp check` / `vp run verify`,全部经 Vite+ |
| 脚本托管 | `bun run <script>` | 跑 `package.json` 里的自定义脚本(`shots`、`test:report`、`check:engine` 等非标准步骤);`bun dev` / `bun preview` / `bun run test` 是薄封装,vp 优先 |
| 别用 | `bun test`、`bunx` 等 | `bun test` 不读本仓库路径别名,整片报找不到模块;统一交给 `vp test` |

> 想要一整套常用命令时,直接用 `vp`;只有跑仓库自定义脚本(不在 vp 命令表里的)才退到
> `bun run`。个别脚本内部仍会 `exec vp`(如 `build` = `vue-tsc -b && vp build`),那是最小薄封装,不是双入口。

**机器上的 `vp` 必须与仓库钉的那一版同版。** 仓库在 `package.json` 的 `catalog` 里把
`vite-plus`(CLI)与 `vite`(它内嵌的 core)一起钉在同一个版本,两条**必须同版** ——
只升一条,`vp build` 会当场拒绝:

```text
error: Failed to resolve vite command: GenericFailure, Expected
@voidzero-dev/vite-plus-core@1.4.0, but found ...@1.3.0
```

而机器上那份 `vp`(mise / 全局安装)与 catalog 不同版时,报的是同一条错 —— 真实处境
是「机器比仓库新」,而错误信息里的 `vp migrate` 是**升级仓库工具链**的动作,照做会把
整条链搬走。`bun run check` 开头的 `scripts/env-check.mjs` 会把两边版本都打出来提醒;
`src/core/gateWiring.spec.ts` 守着 catalog 自己那两条别写歪。修法二选一:用仓库自己那份
(`./node_modules/.bin/vp …`,与 CI 完全一致),或把机器上的 vp 降到 catalog 那一版。

## 命令一览

| 命令 | 作用 |
| --- | --- |
| `bun run test` | 全量用例(全量 595 个 spec;本作自己那部分 515 个) |
| `bun run test:report` | 一次完整测试 + 按系统分类的摘要 + 文档例数核对:未登记分类、文档里的例数与本次运行不符都会直接红并列出(CI 与发布闸用它替代 `test`,少跑一遍测试) |
| `bun run check` | 环境自检(`scripts/env-check.mjs`)+ 类型检查(`vue-tsc -b`)+ Oxlint(`vp lint`,类型感知 + 模板级规则由 vite.config 的 lint 块配置)+ 文档自检(`scripts/docs-check.mjs`) |
| `bun run lint` | 只跑 Oxlint(经 Vite+ 的 `vp lint`) |
| `bun run check:first-paint` | 首屏预算:冷启动解码字节 / FCP / 楷体换上(`scripts/first-paint.mjs`) |
| `bun run check:ui` | 六个浏览器门的本地入口:构建时长 → 首屏 → 帧率 → 排版 → 冒烟 → 离线(先 `bunx playwright install chromium`;一轮约五分钟,故**不进** verify / pre-commit,只在发版前与改界面后跑) |
| `bun run shots` | 从当前构建重拍 README / 文档的界面图(默认写 `images/app/*.webp`;`--theme dark` / `--device desktop` / `--out <目录>` 可选) |
| `bun run build:favicon` | 重出 `public/favicon.ico`:从 `public/icons/icon-512.png`(与安装图标同一枚)缩出 16/32/48 三档,装成一枚(判据见 `src/ui/favicon.spec.ts`) |
| `bun run test:engine` | 只跑公共库(万象引擎)的用例。**`bun run test` 已经含它** —— `vite.config.ts` 的 `include` 同时列了 `src/**` 与 `packages/engine/**`,这条命令只用于快速迭代库本身。全量 595 个 spec = 宿主 514 + 引擎 80,别把 594 当成「只有宿主」 |
| `bun run build:engine` | 出公共库的 dist |
| `bun run check:engine` | 库的产物自检:编译 → 从 dist import → 跑完整一圈 → 发布包真装一遍 → 宿主引用方式 → 独立仓与本仓同树 |
| `bun run check:engine:standalone` | 库的独立成库自检:复制到临时目录后独立编译 / 跑用例 / 跑示例 |
| `vp run verify` | 一键整链:`clean-dist` → `check` → `test` → `test:report` → `vp build` → `check:engine` → `check:engine:standalone`(`cache:false` 每次都真跑;提交/推送前跑它,最不会漏的就是后两项)。**耗时构成**(2026-11-09 实测):引擎那两条合计 **35s**(`engine-dist` 28s + `engine-sync` 2s + `standalone` 6s),余下是 `check` 与全量测试。**那 28s 拆开看**:`verify-dist.mjs` **33.9s** 是绝对主体,而它自己内含「真打包 3.4s + 解包 + 真装 + 两个 node 探针」;`engine-dist` 自己的其余步骤是 tsc 1.5s / `npm pack --dry-run` 3.1s / `attw --pack` 4.0s / `publint` 0.2s。这些不重复:dry-run 查**清单**(发布包里该有 12 个文件、不许混进 `src/`),`verify-dist.mjs` 查**真装**(消费者按包名与子路径 import 得到类型);`standalone` 又是另一件事 —— 整份复制到临时目录重编译、重跑库自己的用例。**没有可省的**。 |
| `vp check` | Vite+ 内置:全仓格式 + lint + 类型一次过(不是 `bun run check` 脚本) |

> **别用 `bun test`。** 那是 Bun 自带的测试器,不读本仓库的路径别名(`@/…`),
> 会整片报"找不到模块"。要用 `bun run test`(即 Vitest)。

### `layout-check` 的偶发失败 —— 先重跑,别先改代码

`bun scripts/layout-check.mjs` 有一部分判据依赖**采样时机**与**随机触发**,
满载并发时会偶发红。实测口径(同一份代码连跑四次,`--jobs 4` 与 `--jobs 8` 混合):

| 运行 | 结果 |
| --- | --- |
| 1 / 2 / 4 | 全绿 |
| 3 | 1 处红 |

已观测到的三类偶发。**前两类是真偶发,第三类要当心** —— 见每条末尾:

- ~~**`pressure-mark` 的像素对比度**(`/adventure`,日间报 `1:1`、夜间报 `2.02:1`)~~
  —— **2026-11-09 查实:这不是偶发,是判据的结构性缺陷**。原以为它是「11px 细笔画的
  抗锯齿边缘」,实际是**采样把笔画本身当成了底色**:那张截图是「已经画上了字」的页面,
  采到笔画内部时 `bg` 就等于文字色,`fg` 算出来也是它,对比度**恒为 1:1**。
  11px 汉字的笔画能占矩形的两三成,而失败线正是「≥20% 采样点读不出来」——
  于是这一处**必然**报红,只是比例随字体光栅浮动(本地恒绿、CI 连红三次)。
  配色本身没问题:日间朱砂 `rgb(168,63,57)` on 纸 `rgb(243,239,228)` = **5.32:1**,
  夜间 `rgb(255,119,115)` on `rgb(33,31,28)` = **6.37:1**,都过 4.5。
  修法:采样时剔除与文字色距离过近的像素(它们要么是笔画,要么是抗锯齿边缘),
  判「字压在什么底上」就该只看**没被字盖住的部分**(`a7bf00db`)。
  **教训**:把「本地恒绿、CI 连红」归为偶发之前,先问一句「判据采样的对象对不对」——
  时机没落定会偶发,采样对象错了就是**必然**,只是两侧浮动的幅度不同。
- **`[375]` 引擎事件的 `cave` 机缘缺失**。洞府巡游挂在引擎 30 秒周期上,判据给 80 秒上限并
  在注释里写明「旧上限 20 / 40 秒都在并发满载时误报过」。满载时首轮周期会被渲染任务挤晚。
- **`repeatedShortLines` 的「同一句说了两遍」**。它依赖首屏 `innerHeight` 内的元素
  位置,视口与字体落定时机不同会进出首屏 —— 但**「进出的只是能否看见,重复本身是必然的」**:
  一处真重复平时不显,只是因为它有时落在首屏之外。

  > 这一条此前举的例子是 `/build` 的 «最弱 0%»,并被打成「偶发」。2026-11-08 查实
  > **那是真缺陷**:章首 fact 报 `weakestMatchup.winRate`,而 `weakestMatchup` 就是
  > `matchupSorted[0]` —— 对局列表首行同一个对象,数值必然相同(实测 1280×800 上
  > @600 与 @711 相距 111px 同值)。已改成章首报「几类过半」(`9e99a2a2`)。
  > 同一个月里同类真缺陷还有三处:市场换货时钟三遍(`0f9552e3`)、铸道案契合度两遍
  > (`482b45aa`)、名号页「尚未佩印」两遍(`70285973`)。
  >
  > 故**别把这条当噪声**。判断办法:红了去查那两处是不是同一个数据源 ——
  > 是就修,不是才归偶发。真正该归偶发的只有「同一个数位在首屏边缘进进出出」,
  > 而不是「重复本身时有时无」。

### 取景:42 个会导航的任务,凭什么只有 19 个调 `clearOverlays`

Round 107 修 `taskResetFlow` 时发现它没收拾取景,于是把同类全查了一遍。结论**不需要逐处补**
—— 因为另外几种写法已经把风险消掉了:

| 分类 | 数量 | 为什么安全 |
| --- | --- | --- |
| 有 `page.goto`,且调 `clearOverlays` | 19 | 取景当场收拾干净 |
| 有 `page.goto`,但**钉了 `Math.random`** | 16 | 引擎不会掷出随机浮层(比事后关更彻底) |
| 有 `page.goto`,但**不播种存档** | 11 | 没有存档,引擎不运转,根本没浮层 |
| 有 `page.goto`,直接操作 store 而非点 DOM | 1(`taskSensoryParity`) | 用 `page.evaluate` 调 `ui.toast(...)`,浮层挡不到 |

总计 116 个 `task*` 函数,42 个会导航。

**教训**:查「有没有漏了 `clearOverlays`」时,别只按「调没调这个函数」数 ——
钉随机源(`addInitScript`)与不播种存档是**另外两条等价路径**,漏掉它们会把
16+11 个安全任务误报成缺口。这与本仓反复吃过的那个亏同形:
**判据写的是「我见过的那种写法」,不是「这件事的所有写法」。**

**处置口径**:

1. 红了先**重跑一次**。连续两次红才当成真缺陷 —— 上面三类在老代码上也会红。
2. 真缺陷通常表现为**固定路由 + 固定视口**每次都红,而不是每次都换一处。
3. 不要为了让偶发变绿去放宽阈值(`allowedRepeats`、对比度 `need`、机缘等待上限) ——
   那会把真缺陷一起放过去。要改就改**采样确定性**(等字体/图就绪、按 kind 精确找卷),
   这几个判据的注释里已经各有一段这类改造的记录。
4. **「量不到」与「超预算」要分开报**。2026-11-08 实测:`first-paint` 等
   `document.fonts.ready` 再睡 400ms 就收摊,而 4G 档 `loadingdone` 比 `fonts.ready`
   晚 1113ms(2015 → 3128)—— 于是 `__kaiSwap` 常读到 null,`?? Infinity` 把它算成
   「无穷晚」,报「楷体换上太晚」。那一条把人往带宽与时序上引,而真问题是采样窗口。
   同一类错误还有更坏的一种形态:量不到时**默认值让判据变绿**(下面 `fileAt` 那节就是)。
   判词要么分开,要么显式说「没量到」,不许让缺失的数据冒充一个具体的读数。

## 测试与判据

这个仓库的取向是:**能用机械判据回答的,不靠自觉。**

| 判据 | 钉住的事 |
| --- | --- |
| 用例 | 全量 595 个 spec(本作自己那部分 515 个),按 9 个系统分类归档 —— 新 spec 没登记分类,`test:report` 会红。文档只记 spec **文件数**(静态可数,由 `docs-check` 核对);**用例条数不写进文档** —— 它每次都随加删用例变,记在文档里只会逼人频繁改、且改漏就打红,而它的真实数 `test:report` 每次都会自己打出来 |
| 门禁接线 | CI 里跑的每个 `bun scripts/*.mjs` 都必须在 package.json 或 verify 里有对等入口(反之 verify 点名的脚本必须真存在),由 `src/core/gateWiring.spec.ts` 守着 —— 「本地静态门过了,CI 静态门就过」这句话从此不是注释 |
| 数值对账 | 四套系统迁移到万象引擎时,与**迁移前冻结的旧口径**逐位相等(见 [engine.md](./engine.md)) |
| 数据自审 | 内容表的头注释计数与真实数组长度比对、敌人 / 区域 / 模板引用闭合、文本与词表覆盖 |
| 样式无尸体 | 样式表里每条带连字符的类选择器都得有人用(`src/ui/deadStyle.spec.ts`)。放行三类源码里查不到全名的:Vue `<Transition name>` 生成的过渡类、`is-${state}` 拼接的状态类、BEM `--变体`;排版角色词(`.t-card / .t-entry / .t-item / .t-body / .t-note`)整词豁免,但至少得有一个真在用 |
| 标点一致 | 同一页模板里不许同时出现全角与半角的中文括号或逗号(`src/ui/copyPunctuation.spec.ts`)。全站两种写法都有人用(中文半角逗号 265 处 / 全角 178 处),判据只要求**一篇之内自洽** —— 全角在竖排与题签里是正当写法,不禁止。扫描面 = 可见文本 + 标签属性值(两处玩家都读得到),注释与 `{{ }}` / `${}` 里的代码逗号不在其内。同一份判据还钉住:乘号只写 ×(不用 ASCII x)、中文与手写数字之间留一个空格(「买 1」而不是「买1」)、中文散文里的省略号写「……」(紧贴中文才算;`…+N` 与 `万/亿/兆…` 这类清单收尾是图形标记,不受此限) |
| 排版与冒烟 | 全量路由 × 五档视口的渲染审计(`scripts/layout-check.mjs`)、界面冒烟(`ui-smoke.mjs`,逐页点按钮 + 四条专场景:旧档迁移、存储写满、挂机稳定、导入存档,外加「找到控件却一个都没点成」这条下限)、Service Worker 离线层(`offline-check.mjs`)。前两者**并发**跑(每个视口与每件事各是一个独立任务,`--jobs` 或 `LAYOUT_JOBS` / `UI_SMOKE_JOBS` 调路数,默认按核数、上限 8)—— 一轮从约 17 分钟压到约 5 分钟 |
| 读源一种写法 | 界面契约测试读文件只走 `@/test/readSource`(`src/ui/specReadSource.spec.ts` 守)。`readSource` 里带着「`src/style.css` 要走 readStyleCss() 拼装」这条分支 —— 直接读那份拿到的只是按路由拆过的残卷,而断言照样会绿。目录遍历同理由 `walkFiles(dir, 谓词)` 承担:八份各自的 `walk` 只差一行扩展名判断,而那正是最容易抄错的(`.spec.ts` 少个 s、把 `.d.ts` 当源码),故把差异摊成具名谓词 `isSourceFile` / `isTypeScriptOrVue` / `isVueFile` / `isSpecFile` / `isSourceOrScript` |
| 首屏预算 | 冷启动解码字节 / FCP / 楷体换上三条上限(`scripts/first-paint.mjs`,自带静态服务与 4G 限速)。结算窗口**必须等到它要量的那一拍**:原先等 `document.fonts.ready` 再睡 400ms,而 4G 档实测 `loadingdone` 比它晚 1113ms —— 于是经常读到 null、拿 `Infinity` 比预算,报出「楷体换上太晚」而字体明明正常。现已改成显式等 `__kaiSwap` 落定,并把「没量到」与「太晚」拆成两条判词(两者混报会把人引向带宽与时序)。这条由 `gateWiring.spec` 守着 |
| 文档与实现一致 | `scripts/docs-check.mjs`(已并入 `bun run check`):文档里引用的 `bun run` 脚本必须真存在、反引号路径与相对链接必须存在、「全量 N 个 spec」必须等于真实文件数 —— 实测抓到过一次 25% 的漂移(文档写着 199 个 spec 时,实际已是 294) |

### 怎么找下一个问题

判据讲的是「怎么判」,这里讲**怎么找**。上面那张表里的每一行都来自一次具体的发现,
而发现本身没有方法 —— 于是同一个病会被修三遍才有人想起来统计。

按命中率排序,实际奏效的找法有五种:

**一、找「同一件事在不同地方做法不同」。** 有参照物时,判「对不对」变成判「一不一样」,
后者容易得多。实例:品阶在各处都盖 `QualitySeal`,只有离线归来只有颜色;
设置页两扇不可逆确认,导入摊了底细、重置没有。

做法:选定一条纪律的载体(`QualitySeal` / `hasOpenModal` / `摊数字`),把它所有
调用点列出来,看谁不合群。

**二、找「注释与文案的承诺 vs 代码事实」。** 数据文件头、组件注释、玩家读到的文案,
都写着设计意图;而代码可能只实现了一半。实例:`weather.ts` 头注「飞升之后天象随界域
而变」,而夜色表只写了人间与仙界十二种,神界混沌海六种全走兜底;往生三程文案说
「真正不可撤回的是三程末」,而 `step` 只有单向赋值。

做法:读文件头那几句话,逐条去代码里找它对应的实现。

**三、把一次性统计固成判据。** 前两种找法都是「逐个看」,靠注意力,而注意力会漏。
第 9 轮的品阶统计(数每个文件里 `QualitySeal` 与品阶名的出现次数)一次就收干净了 ——
这种查询要立刻写成 `*.spec.ts`,否则下次还得靠谁想起来。

**四、真浏览器量,不靠读源码。** 首屏重复、面板是否落在视口内、200% 缩放下的竖排,
都只有跑起来才看得见。做法:遍历首屏文本节点数重复次数;量 `getBoundingClientRect()`
是否在 `window.innerHeight` 之内。

**五、从「玩家会记住的那几个瞬间」往回看。** 前面四种都在找**错**,这一种在找**缺** ——
弹窗本身完全正确,只是少了一句本该在那里的话。而这类「缺」用「哪里坏了」的问法是
永远找不到的,必须换成「这一刻该被说到的,都说了吗」。

实测有效的一个例子:大境突破弹窗把印、金章、境界迁移、总结全做好了,唯独没说出
跨进去的那一境**是什么**;而 `realm.lore` 那句话本来就是为这一刻写的(见
`docs/design.md` 的「大境突破那一刻」)。换成这个问法之后,十几轮没找到问题的一轮
立刻就有一处。

这一作值得逐个过一遍的瞬间:

| 瞬间 | 组件 | 这一刻玩家最想知道 |
| --- | --- | --- |
| 大境突破 | `BreakthroughResultDialog` | 我跨进了什么地方 |
| 渡劫失败 | 同上(失败分支) | 我失去了什么、下一步怎么办 |
| 往生三程 | `ReincarnationDialog` | 这一世带走了什么、留下了什么 |
| 顿悟 | `EnlightenmentModal` | 这三条路各通向哪里 |
| 洞府奇遇 | `CaveEventModal` | 这个选择会改变什么 |
| 离线归来 | `OfflineRewardDialog` | 我不在时发生了什么值得说的事 |
| 拾得神品 | ToastHost 五感层 | 这是什么东西、有多稀罕 |

问法要具体到「这一刻」,不能停在「这个页面信息够不够」—— 页面信息通常是够的,
缺的是**在该被击中的那一秒没有击中**。

> `effect`(`enlightenmentEffectText` 从 buffId / reward 现算)、洞府奇遇有

#### 找完之后,先问三个问题

- **这是缺陷还是设计?** 五个页面报「首屏重复」,四个是合理的(三个空席各报状态、
  多境界共用的出处)。检测给候选,判断还得读那句话在说什么。
- **改哪里更对?** 首页重复有两处可删,选了法球那处 —— 因为「修为 0%」脱离境界
  就没有意义。删对了次数、删错了位置,同样会红。
- **这次改的值不值?** 有些候选查完影响面为零(去掉注释后「只活在注释里的类」= 0),
  那就记进 `design.md` 等第二次撞上,不为零收益动判据的口径。
- **算过没有?** 改动前先把**真实读数**打出来,不要照着截图估。实测栽过一次:
  修行页「还剩 100% · 约 1天11小时」看着像四舍五入把 99.9% 抹成了 100%,于是判定
  「取整太粗」并改了精度 —— 打真实值才发现 `expProgress = 0.0000094`(万分之一),
  保留一位小数**仍然是 100%**。原实现是对的,改完回滚。

  教训很小但很贵:估算与真值差了两个数量级时,你修的不是那个问题。**先 `console.log`
  真值,再决定动不动**。

### 加固什么:先问「出错时谁会知道」

找到问题之后有两种修法:修掉它,或者**再加一条判据让它不会再犯**。前者解决当下,
后者解决将来。这两种都该做,但优先顺序取决于一件事:

> **如果这段代码明天被改坏,谁会知道?**

- **有人会知道** —— 玩家会看到、会来报,或某条没跑的判据会红。修掉就行,不必加判据。
- **没人会知道** —— 那就值得加一条。这类代码的特征是:**静默**。

按「静默程度」排序,这几类最值得加固(也是实际加过的):

| 类型 | 为什么静默 | 实例 |
| --- | --- | --- |
| **初始化路径** | 只跑一次,平时没人看 | 开局赠礼五件东西,删任一行门全绿,而玩家第一天就卡住 |
| **落盘数据** | 坏值穿存档,到界面才现形 | 17 个 store 的 `sanitize`,漏一个就是「NaN 天前」 |
| **跨版本迁移** | 只在旧档上触发,新档测不到 | v1 → v2 的法宝位迁移 |
| **不可逆操作** | 出错时已经晚了 | 重置存档只给一句形容词、往生三程没有退路 |
| **同一屏的重复说法** | 单看每句都对 | 「真仙·四层」在首屏出现两遍 |

反过来说,**不必**加固的:纯展示、错了玩家一眼能看出来、且改了不痛的地方。
`deadStyle` 那个注释盲点查完影响面为零,就没动 —— 判据本身也有维护成本。

#### 判据写完,先破坏一次

新判据第一次跑通常就是绿的,而**绿的判据等于没写过** —— 除非你确认它真的会红。

所以每写完一条,故意把被保护的东西改坏一次(删一行、改个顺序、换个名字),
看它是否**精确地**指向那一处:

- 好的破坏实验:只有那一条红,报错文字说清了是什么坏了;
- 差的破坏实验:连红三条 —— 说明判据之间有状态泄漏(实测遇到过一次:
  测试压了一扇浮层进栈,断言失败时没出栈,污染了后面每一条)。

这条和上面「找完之后先问三个问题」是同一件事的两端:找的时候怕漏,写的时候怕假。

#### 一条反面经验

**别拿现成工具用在它不该用的地方。** `gnum.ratio` 的指数差钳在 ±15(给血量百分比用的),
拿它算「离线修为 / 本境所需」报出了「推 1011 层」;`layout-check` 里 `main button`
的第一个、`/突破成功/` 正则,都在页面结构或文案变了之后指错对象 ——
而且**错得很安静**,它不会报「找不到」,只会量到另一个东西。

## 首屏与构建时长

首屏传多少字节、第几毫秒看得见字、构建跑多快,各有上限。

### 构建

生产构建就是 `bun run build`(类型检查 + `vp build`)。曾经为了 Chrome 51 / Android 7
那批老内核,发布路径还要多跑一遍 legacy 兜底(本机 32s 的构建里 26s 花在这一步)——
对个人项目纯属死重,已整条拆除:没有 `build:release`,也没有 `XIAN_LEGACY` 开关。

构建器对超过 500KB 的 JS 块只发警告、不会失败,警告看久了就等同于不存在。现在
`crypto-js` 单独成 `vendor-crypto` 块(约 18KB),`player` 从 504KB 降到 486KB,
首屏总字节只多约 1KB;加密库是最稳定的一层,内容更新时还能继续命中浏览器缓存。
`layout-check` 会把任一块 JS 超过 500,000 字节、或 `vendor-crypto` 丢失判红。

### 首屏预算(实测:4G 档、390×844、冷缓存)

| 冷启动解码字节 | 2681KB(楷体 1783KB) | **1256KB**(楷体 48KB) · 线传 505KB | 1500KB |
| FCP | 692ms | **404ms**(本地服务上 gzip 后) | 1400ms |
| 楷体换上(swap 那一刻) | 2255ms | **2000ms** | 3400ms |
| 首屏楷体请求 | — | 48KB(1 片) | 160KB |
| 最大 JS 单块 | — | 394KB(`player`) | 500KB |
| 构建时长 | 32s | 12.6s | 90s |

> **2026-11-09 两次修正,按顺序读**:
>
> 一、**文档里的读数过期了**。复测得 1256KB / FCP 1124ms,而表里记的是 1150KB /
> 1120ms。用 `--repeat 3` 稳定复现,不是波动。这 106KB 的增长**不是判据类改动引入的**
> (spec 不进产物;查了未推送的 19 个提交,改 `src/` 的 13 个全是 spec 与文档)。
>
> 二、**「线传」那一栏一直等于「解码」—— 本地服务没上 gzip**。`content-length` 取的是
> `body.length`,而生产环境(GitHub Pages / nginx,见 `nginx.conf` 的 `gzip on` +
> `gzip_min_length 1024`)都压过。补上 gzip 后:
>
> ```text
> 解码 1256KB —— 预算 1500KB(线传 505KB)
>   Script 1036 → 422KB · Stylesheet 163 → 31KB · Font 48 → 48KB · Document 9 → 3KB
> FCP    404ms —— 预算 1400ms
> ```
>
> **FCP 1128 → 404ms 不是产品性能提升,是测量环境修正** —— 那个读数此前一直在为
> 一个不存在的带宽压力买单。补了自检:线传必须明显小于解码,否则报红。
>
> **当前余量**:首屏**解码** 1256/1500KB = 84%(这个口径没变 —— 浏览器真要解析的就是
> 这些字节),但**线传**只有 505KB,占带宽预算的 34%。最大单块 `player` 394/500KB = 79%
> (上限见 `layout-check` 的构建产物任务)。两条线都还有余量,下一轮功能扩展前先想清楚
> 是压首屏还是拆单块。
>
> 拆单块的可行方向只有一个:把 `player` 里的数据表(`titles` / `mentors` / `talents` /
> `heritage` / `samsara`,合计约 25KB 源码)挪出首屏。但**五个表各被 4~11 个文件引用**,
> 不是孤立依赖,拆它们要先改 `player.ts` 的调用方式 —— 风险配不上现在这点余量。
>
> 复测时顺便量了构成:`Script 1036KB + Stylesheet 163KB + Font 48KB + Document 9KB`;
> **最大单块 `player` 394KB(原始)/ 144KB(gzip),占首屏脚本的 42%** ——
> 它 gzip 后仍占 42% 是因为 store 里塞了整条依赖链(39 个 import,
> 其中 8 个数据表)。真要压首屏,该从这里下手;但 1256KB 离上限还有 244KB,现在不做。
>
> 2026-11-08 再测(同一台机、同一天,`--repeat 3` 取中位):**FCP 1368 → 1120ms**,
> 来自「`@font-face` 声明分两份」(见下文四处改动的第 1 条)。三条一起降 ——
> FCP −248ms、冷启动解码 −44KB(入口 CSS 208 → 163KB)、楷体换上 −230ms;
> 首屏字体请求仍是 1 片 / 48KB,没变。
>
> 2026-11-08 重测:上一版这张表记的是 2026-11-02 的读数(1161KB / 1304ms / 2937ms /
> 41KB 1 片)。一周后三项都涨了 —— 一周 300 个提交、+37988 行的正常增长。
> 其中**首屏楷体请求 41KB → 134KB(1 片 → 3 片)不是增长,是退化**:
> `BOOT_FONT_CHARS` 是手写表,开卷文案里的「门 / 未 / 闭 / 方」没进表,漏到第二三片。
> 补齐后收回 48KB 1 片(第一片比原来大 7KB,换完整覆盖)。判据补在
> `kaiFontCoverage.spec`(开卷文案的每个字都必须在表里),破坏注入验过。
> **FCP 余量当时已从 96ms 收到 32ms** —— 下次再涨就该动 JS 了(`player` 块 394KB 是大头);
> 同日晚些把 `@font-face` 声明拆成两份之后,余量回到 280ms(1120 / 1400)。
>
> 2026-10-06 重校准:楷体换上上限 2800 → 3400 —— 旧值按"本机无 preload 2159ms"
> 定的,而 CI 量的是随代码量增长的排版,迁移前后稳定落在
> ~2942-2952ms(9c739b9 迁移前就 2942),预算比实测还低,Pages 连红数推。
> 反「整份 1.8MB 打进来」的量级守卫改由**首屏楷体请求字节断言(≤160KB)**确定性承担,
> 与机器快慢无关;时序这条只守"字体加载奇慢"。

四处改动:

1. **楷体按需分片**。原先一份 1.8MB 的子集在冷启动时整份下载,而首屏真正用到的字不过
   一两百个。现在按**用法频次**切成二十来片(每片一段 `unicode-range`,声明由
   `scripts/fonts/build-kai-font.py` 生成到 `src/assets/fonts/kai-subset.css`),
   浏览器只取「页面上真出现的字」所落的那几片。开卷页真正落在 `font-kai` 上的字
   (含紧接的建号章号)固定放进第一片,再补一档高频字;首屏只取 1 片 / 48KB;
   而「玩家起了个生僻名」
   这种时候也只多拽一小片,不是一千多 KB 的储备整段。片多大是取舍(片越小越省字节、
   请求越多),取 180 字/片是实测的口径。`kaiFontCoverage.spec.ts` 会核这组首屏字
   没有掉出第一片,也核**开卷文案里的每个字都在这组里** —— 后一条是 2026-11-08 补的:
   那张表原是手写的 42 字,开卷文案改动后「门 / 未 / 闭 / 方」漏了进去,
   首屏从 1 片涨到 3 片(41KB → 134KB)而判据全绿。补齐后是 72 个汉字 / 第一片 48KB。
   **声明分两份**:22 条 `@font-face` 的 `unicode-range` 合计 41.9KB(5580 段区间),
   原先全部压在渲染阻塞的入口 CSS 上,而首屏只认第一片。现在阻塞那份
   (`kai-subset.css`)只留第一片,其余 21 片写进 `kai-subset-rest.css`,由
   `core/kaiLateFaces` 在正文可读之后注入 `<style>`(不是再加一条阻塞的 `<link>`);
   生僻字上屏时浏览器照样按 `unicode-range` 去取对应切片,行为不变。那份 CSS 走**动态
   导入**:静态 `?inline` 会把它编进入口 JS(实测 +48KB 到 `index-*.js`),等于把字节从
   阻塞 CSS 挪进首屏必下的 JS,总字节一点没省 —— 动态导入才让它落成独立分块。
   实测 **FCP 1368 → 1120ms、冷启动解码 1194 → 1150KB、楷体换上 3183 → 2953ms**
   (三点,同一台机、同一天、`--repeat 3`)。判据是
   `kaiFontCoverage.spec` 的两条:阻塞那份只能有一条 @font-face、入口样式表不许把
   延后那份 `@import` 回来;破坏注入(把 21 条合并回阻塞那份 / 重新 @import)两处都红过。
2. **不打 preload**。同一份产物只改 `index.html` 里那一条链接、各量 3 遍取中位:
   不打 → FCP 1360ms · 楷体换上 2858ms;打 → FCP 1456ms · 楷体换上 2681ms。
   预载虽让字体早到,却把首帧推后约 100ms —— 抢的仍是首屏 JS 与渲染的带宽。
   故只留 `font-display: swap`;`bun scripts/first-paint.mjs --variant preload`
   可随时复量这个 A/B。
3. **浮层按需装载**。装备详情、事件、转世、归来等九扇浮层只在事件发生时出现,却合计带着
   各自的数据链;原先静态挂在 `App.vue`,所有玩家打开首页都要先下完。现在它们由
   `defineAsyncComponent` 拆成独立分块,并等正文所用楷体落定后再挂载,避免在慢网下与首条
   路由、字体切片抢带宽。浮层状态仍在 store 中,晚一拍挂载不会漏掉事件。

   > 2026-11-08 修:「等楷体落定」原先是等 `document.fonts.ready`,而它的语义是
   > 「**当前已请求的**字体都加载完」—— 页面刚起来还没渲染楷体字,那个 promise 于
   > **15ms** 就结了,`overlaysReady` 随即置 true,十个浮层分块(**128KB**)在 **110ms**
   > 就被拉走,而首屏楷体要到 **171ms** 才 `loadingdone`。设计意图一直没生效。
   > 改等 `loadingdone`(带 1.2s 超时兜底)后,浮层推迟到 153ms,
   > **楷体换上 2954 → 2595~2783ms**(三遍实测)。判据 `overlayTiming.spec` 守着。
4. **样式先于模块预载排队**。Vite 默认把入口 CSS 放在几十条 `modulepreload` 之后;
   4G 冷启动时预载 JS 会先占满连接池,首帧只能等样式最后一个到。构建插件只调换
   `<link rel="stylesheet">` 与模块标签的顺序,不删预载、不改依赖;实测 FCP 提前约 80ms。
   `layout-check` 直接查构建产物,防止插件顺序变化后静默退回。

### 试过但**没有**吸收的:按需装载引擎

`core/engine` 静态引着探索 / 离线 / 事件 / 镇压 / 世界记忆那一整片(35 个模块、
约 252KB 源码),从前是 `App.vue` 的静态 import。把它改成按需装载看起来是白捡的
—— 入口静态图从 213 个模块降到 178 个。**实测不成立**,三种时机都量过
(同一份产物、同一天、`--repeat 3` 取中位):

| 方案 | FCP | 楷体换上 | 冷启动解码 |
| --- | --- | --- | --- |
| 静态 import(现状) | 1132ms | 3006ms | 1256KB |
| 按需,挂载即装 | 1116ms | 3133ms | 1039KB |
| 按需,字体落定后装 | 1128ms | 3197~3205ms | 1257KB |
| 按需,字体落定 + 空闲拍 | 1124ms | 3204ms | 1258KB |

FCP 没有实质变化(±16ms 是抖动),而**楷体换上一律变慢 130~200ms**。
原因:首屏带宽是同一个池子,引擎那 217KB 只是**换个时间**进来 —— 挂载时装,它和
字体请求一起排队、还比字体后到;字体落定后装,引擎分块又插在 `loadingdone` 之后的
那次排版与合成里。冷启动解码那一列也说明问题:前两行省下的 217KB 在第三、四行又回来了,
因为门禁的观察窗口会等到心跳起来之后。

**结论:这条不吸收。** 那 252KB 不是"多传的",是**首屏之后就要用到的**;把它挪到
首屏之后传,只是让它在更糟的时机挤进同一条带宽。真要省首屏 JS,得省**首屏真正不需要
且永不参与首屏竞争**的那一部分(浮层那九扇已经这样做了,见第 3 条)。

判据没有留下 —— 没有可守的行为变化。留这段记录是为了不让人重走:这条路上
「入口静态图变小」是个很有说服力的假信号。

### 什么时候该复量 —— 三个条件,不同时成立就别动

文档里那些「实测」都带一个隐含的时效。**盲目复量等于白干**(本会话踩过:从
「心跳感觉还能再快」出发重查,结果撞上下面的结论)。三条都成立才值得重测:

1. **它没有实时门守着。** 帧率、首屏、内存、离线、排版都由 `check:ui` 的六个门
   每次真跑并比预算 —— 文档里那张帧率基线只是**记录**,不是判据,过时也不会有后果。
   反之 `accrue` 每拍多少微秒这种事,没有任何门会告诉你它变了。
2. **记录之后,被测的那段代码真的改过。** 用
   `git log -S"<那句话>" -- docs/development.md` 拿到记录的日期,再
   `git log --since="<那个日期>" -- <被测文件>` 比对。**改在测量之后**才有嫌疑。
3. **改动会改变被测量的那个量。** 这一条最容易漏。2026-11-09 的 4 次 refactor
   都动了 `player.ts`,但只有 `6c7dd10a` 在 tick 里**新增了一个 `Object.entries`
   循环**——另外三次改的是传参方式,不改变每拍的计算量。同理,`finalStats` 那次
   10-23 的实测至今仍有效:`statsCalc.ts` 自那以后**一行没改**,`player.ts` 的
   改动只是换了取值路径。

**2026-11-09 按这三条过了一遍**:`accrue` 那段复量了(三条都成立);帧率基线
(条件 1 不成立)、`finalStats` 7.4µs(条件 2/3 不成立)都不该复量。

### 测试耗时量过一遍 —— 只有 `phase21` 是真慢,其余是并行负载

2026-11-09 量了每条用例的耗时(`vitest --reporter=json`,看 `endTime - startTime`)。

### 运行时(帧率 / 长任务)

首屏只管「第一屏多快」,不管「玩起来卡不卡」。放置游戏的心跳每秒改一批响应式状态
(`stores/{player,resources,dongfu,cultivation}` 等),视图若在内容变多时开始整块
重渲染,帧间隔就会拉长 —— 这一维此前没有门。`bun scripts/perf-profile.mjs`(npm 脚本
`check:perf`)补上:对每个游戏视图,在 390×844 移动视口 + 后期档(神人境 + 成套装备)下
采几秒 rAF 帧间隔,量最差帧、>50ms 长帧、DOM 节点数,断言不崩溃、无页面异常
(见 `scripts/perf-profile.mjs` 文件头的量法说明与预算)。

> 与排版/冒烟的分工:那边量「点不点得动、排版对不对」,这边专门量 jank。运行时门
> 是**回归门**不是基准 —— 预算按本机读数留数倍余量(见下文),红的是「成倍长回去」,
> 不是机器抖动。

背包视图按**真实规模**量(`--bigbag N`,默认 300 件):这类放置游戏 jank 的真实来源是
玩家攒下几百件装备后,背列表随每秒心跳整块重渲染。小包 2-3 件量不出列表成本,故默认
压到 300 件(远超在线能攒的典型规模,仍 60fps;`--bigbag 0` 或 `PERF_BIGBAG` 可调)。

### 显示心跳的粒度(为什么秒针能走、`totalPlaySec` 仍是 5 秒一盖)

倒计时的秒针要每秒走,而 `totalPlaySec` 由引擎按 `ACTIVE_STAMP_MS`(5 秒)盖章 ——
两者靠 `composables/useGameNow` 解耦:显示自起 1s 表、读 `gameNow()`,结算链照旧读各自口径。

> 当初把「不解耦」的理由写成「`finalStats` 是全库最重的 computed,每秒重算受不了」。
> **2026-10-23 实测把这条推翻了**(本机,神仙期满装 + 闭关状态,bun/vitest 内 `performance.now`):
>
> | 读数 | 实测 |
> | --- | --- |
> | 每次 `totalPlaySec` 变化后读 `finalStats.mods` + `cultPerSec` + `qiRegenPerSec` | ≈7.4µs |
> | `currentTribulationPlan`(逐波推演整段雷)同条件 | ≈18.5µs |
> | 修行页 1s 心跳的真浏览器帧率(`perf-profile --view cultivation`) | 最差帧 17ms · p95 17ms · 零长帧 |
>
> 每秒重算本身不贵。解耦的真理由是**语义**:`totalPlaySec` 是「已游玩时长」这一存档事实,
> 它的盖章节流同时服务 `lastActiveAt` 落盘 —— 让落盘节奏决定秒针怎么走,是两个不相干的
> 东西被一根线串起来。**推论**:以后若还要论证「某个每秒重算太贵」,先量,别沿用这条旧印象。

## 发版

**发版是一个显式动作 —— 推 tag。** 构建 Electron 与 Android 产物、发布 Release 的流水线只在 tag 上触发:

```bash
# 1. 先提 package.json 的版本号(它决定 APK 的 versionName / versionCode)
# 2. 本地体检:缺正文、工作区不干净、tag 重名都会被拦下
bun run release:check
# 3. 打 tag 并推上去(版本号以 package.json 为准,这里只是例子)
git tag vX.Y.Z
git push origin main vX.Y.Z
```

`bun run release:check` 只答本地能答的四件事(版本与正文对得上、工作区干净、tag 没被用过、正文里的绝对链接指的都是本版 tag —— 复制上一版正文时最容易漏改那几处图链),
外加一条提醒:自上次 tag 以来若有提交动过 `android/`、`electron/` 或发版流水线,它会把条数
摆出来 —— 那几条路径**本地永远绿、只有 tag 跑得到**,打完 tag 要看真跑结果。

这条流水线第一件事是核对 tag 与 package.json 是否同一个版本(判据看的是两者**相等**,
不是某个具体版本号),对不上直接红掉 —— 免得发出「Release 页上的版本、与装到手机上的
versionName 不是同一个」的包。

**Release 正文写在仓库里,不写在页面上。** `docs/release-notes/` 下与 tag 同名的文件
(如 `docs/release-notes/v0.0.1.md`)就是那一版的正文:release job 优先取它,没有则退回
GitHub 自动生成的提交清单。理由很实在 —— 手改页面上的正文会被下一次流水线重跑冲掉,
落在仓库里才跟得住版本、也才过得了文档门。那份文件里的链接一律写绝对地址(图片与链接
渲染在 Release 页上,相对路径解析不到仓库内容)。

## 多端构建

```bash
bun run build:electron   # Windows 桌面客户端(Electron,输出 pkg/*.zip)
bun run build:android    # 同步 Web 产物到 Android 工程(Capacitor)
bun run build:apk        # 直接出 Release APK
```

> **关于 Android 签名**:签名私钥文件(`android/release.keystore`)作为历史遗留随仓库分发,
> 它只提供「用同一把钥匙签出的 APK」这一致性,**不构成官方性与防伪** —— 任何克隆仓库的人
> 理论上都能用它签出包。因此签名口令绝不入库:CI 由 GitHub Secrets
> (`KEYSTORE_STORE_PASSWORD` / `KEYSTORE_KEY_PASSWORD`)注入,本地出包请临时 `export` 这两个环境变量
> (或建一个不入库的 `android/keystore.local.properties`)。

**Electron 打包开着 `asar`**(`package.json` 的 `build.asar: true`)。它曾经是 `false`,
来源是照搬参考仓 yunyin-xiuxian 的配置 —— `package.json` 首版提交 `cdce24d6` 时
`name` 还是 `yunyin-xiuxian`、版本 `1.33.0`,本仓从没为这个值写过理由。
而 electron-builder 每轮构建都在警告:

```text
• asar usage is disabled — this is strongly not recommended
```

2026-11-09 实测开启后的差别:

| | 产物字节 | 完整性校验 |
| --- | --- | --- |
| `asar: false` | 166,936,968 | 无 |
| `asar: true` | **164,074,083** | **有**(`updating asar integrity executable resource`) |

少 2.7 MiB,并且开启后 electron-builder 会自动给 exe 烧进 asar 完整性资源 ——
那是关着时完全没有的一层加固。开启是安全的:`electron/main.js` 只读
`app.getAppPath()` 下的 `dist/` 与 `public/`(asar 里由 Electron 自动虚拟化),
写盘只写 `app.getPath("userData")`(在 asar 之外)。判据见
`core/releasePipeline.spec` 的「Electron 打包开着 asar」。

### Android `versionCode` 的位段划分与碰撞边界

`android/app/build.gradle` 从 `package.json` 的 `version` 现算 `versionCode`:

```groovy
def appVersionCode = versionPart(0) * 10000 + versionPart(1) * 100 + versionPart(2)
```

即「主 × 10000 + 次 × 100 + 补」。当前 `0.0.2` → `2`,`v0.0.1` → `1`,单调递增,没问题。

但位段宽度是有边界的 —— **次版本号到 100、或补丁号到 100 都会碰撞**:

| 版本 | versionCode | 与谁撞 |
| --- | --- | --- |
| `0.1.0` | 100 | `0.0.100` |
| `1.0.0` | 10000 | `0.100.0` |

补丁号攒到 100 是**可能发生的**(每版几次小修),而 Android 用同一个 `versionCode`
的包安装会被拒(覆盖安装时"应用未安装")。真到那一步,把权重改宽即可
(如主 × 1000000 + 次 × 1000 + 补),但那会让已发布版本的 `versionCode` 跳变 ——
**Android 只要求递增,跳变无害**,故这是一次性改动而非兼容问题。

现在没加判据:本作版本号还在 `0.0.x`,离边界很远;等版本号真要跨过 100 再加不迟。
写在这里是为了让人**改版本号时知道这条边界存在**。

安装与部署(Web / PWA、Android、Windows 桌面、Docker、反向代理)见 [deployment.md](./deployment.md)。

## 端口:core 怎么在不认识 store 的前提下说话

`core` 有 168 个模块,其中 48 个必须读写 store(编排层)。另外 120 个是纯逻辑 ——
它们**也要说话**:弹一条提示、给界面递一份视图模型、把运行期异常留档。

直接 `useUiStore().toast(...)` 是最短的路,但那样 core 就依赖了 Pinia:测一个数值函数
要先建一整套 store,想把逻辑搬到别处也搬不动。

三个**端口**解决的正是这件事 —— core 定义接口,上层在 store 的 setup 里注入实现:

| 端口 | 说什么 | 落点 |
| --- | --- | --- |
| `core/notify.ts` | 「该提示什么」 | `stores/ui.ts` 的 `setNotifier` |
| `core/uiPort.ts` | 「该给界面看什么」 | `stores/ui.ts` 的 `setUiViewModelSink` |
| `core/diagnostics.ts` | 「运行期出了什么异常」 | `stores/diag.ts` 的 `setRuntimeDiagnosticSink` |

**效果**:30 个 core 模块经 `notify` 发提示、4 个经 `uiPort` 递视图,
而 `grep useUiStore src/core/*.ts` 只剩注释里几处、零实际调用。

### 两条必须守住的细节

**一、落点要用 `(...args)` 转发,不要手写参数表。**

`stores/ui.ts` 的注释记着栽过两次:先是漏了 `seal`(品阶印)、再是漏了 `target`(去路)——
两次都**类型合法**(JS 丢实参不报错),单元测试直接调 store 的全参版本全绿,
只有真浏览器里「怎么没效果」。写 `(...args)` 后,参数表由 `Notifier` 的签名约束,
端口涨一个参数这里不用改也不会漏。

**二、落点必须真被接上,否则是静默失效。**

`notify` / `uiPort` 在没人接时**按设计静默丢弃**(批量结算、脚本、库的调用方都可能不挂 UI),
但「忘了接线」和「本来就没接」长得一模一样。判据在 `core/layeringAudit.spec`:
三个 setter 都必须真在 stores 里被调用(注释掉的调用不算)。

> 同形的坑在 `core/diagnostics` 上真出过:`sink?.()` 在半初始化窗口里把异常丢了,
> 见 `core/startupOrder.spec` 与 `core/mainWiring.spec`。

### 判据不许空转：`fileAt` 与裸 `FILES.find`

`uiLayering.spec` 里有 200+ 处「按路径取一份源文件再断言」的写法。裸的 `FILES.find(...)`
在文件改名或删除之后返回 `undefined`，而 `expect(x?.src).not.toContain("…")` 对
`undefined` **永远通过** —— 于是「把坏代码删干净」与「把整个文件删掉」在判据眼里没有分别。

故 `uiLayering.spec` 里所有查找都走 `fileAt(path)`：找不到就当场抛错，并说明
「这个组件/视图可能被改名或删除，该改守新的那个或删掉它」。`core/assertionLiveness.spec`
守着这条：那两个文件里不许再出现裸的 `FILES.find`。

这是 2026 年那次 `EquipmentCard.vue` 事故的另一半 —— 那次是 `.toContain`（红得早），
换成 `.not.toContain` 就会一直绿着。

### 语义落点与布局落点

模板里的 `data-*` 分两类，判据只该覆盖第一类：

- **语义落点** —— 名字里带 `empty` / `warning` / `state` / `total` / `progress` 的，意味着某处存在一个
  状态需要被断言。这类落点没被判据读过，就等于那件事没人守。
- **布局落点** —— 名字是分区名（`data-dongfu-court`、`data-adventure-masthead`……），只给样式与
  调试用，不读是正常的。

2026 年盘过一次：780 个落点里 271 个从未被读。绝大多数是后一类，但混着
`data-lifespan-warning` —— 它管的是玩家的生死，而它从没被任何判据核过。
补它的判据时**两侧都量**：寿元将尽的要变朱砂、充裕的不许变；只核「出现过」
会漏掉「谁的寿元都被标红」这种更坏的情形。

### 转世三程的弹窗链（写判据时踩过的坑）

点「轮 回」进的是**往生帖**（`data-rebirth-folio`）→ 点页脚 `data-rebirth-enter` → 三程
（`ReincarnationDialog`，第一程 `data-reincarnation-begin`、第二程 `data-reincarnation-review-next`、
第三程 `data-reincarnation-confirm`）。「落印之前」那一章在**第三程**里。

这几处踩过六个坑，记下来免得再走：两个弹窗是**先后关系**而不是包含关系；它们都 teleport 到
body，`page.locator(...)` 的作用域在这儿不稳，页内在 `querySelector` 上点更可靠；
两处按钮文案都含「进入第」，按文案认会点同一颗。

还有一条**已查明**的异常（2026 年第 32 轮结案）：

`TypeError: Cannot read properties of undefined (reading 'id')`，点 `data-rebirth-enter` 时出现。

**根因是探针，不是代码**：探针用 `Math.random = () => 1` 钉死随机源，而 `rng.pick` 取的是
`arr[Math.floor(rand() * arr.length)]` —— `rand() === 1` 时下标正好等于 `arr.length`，**越界**，
返回 `undefined`。`Math.random()` 的值域是 `[0, 1)`，永远不会是 1；探针违反了这个前提。
于是 `offerThemes` 收进一个 `undefined`，下游 `x.id` 当场炸，而堆栈指向了另一个函数。

**怎么查出来的**：第 29–31 三轮回荡在「读源码猜」上（猜了六种全错）。第 32 轮改成
**运行日志取证**——在被怀疑的函数里打一行入参，构建后跑一次，日志显示数据完全正常
（`criticalSamsaraRows in: [12,4,20]`）。数据正常而仍然崩，就只剩「崩的根本不在那里」一种可能。
反查打包产物，堆栈里的 `ie` 是 `prepareReincarnation`。

**为什么不全局换成 0.5**：试过，当场三十余条红——`Math.random = () => 1` 在 46 处探针里是
**刻意**的（让随机选择落到数组最后一项，断言据此写死）。全局改动会打破整屏的对比度与货架判据。
故只改该改的，其余保留。

**留给后人的**：`rng.pick` 的签名 `pick<T>(arr): T` 在撒谎——它可能返回 `undefined`，
非空断言把越界藏起来了。默认随机源下安全，谁注入自定义随机源谁就会撞上。这条已写进
`src/utils/random.ts` 的注释，并由 `core/rngBoundary.spec` 钉住。

**第 33 轮把那条判据补上了**，路径终于走通。还差最后一块拼图：链上**没有**
`data-reincarnation-begin` —— 那个落点属于第一程（`step === "death"`），而第一程的条件是
`ui.deathDialog && !view`，点过兵解之后 `view` 就有了，第一程不再渲染。兵解直接把人送到
第二程（`review`）。所以正确的链是 `[data-rebirth-enter] → [data-reincarnation-review-next]`，
两跳到底。

另记一条阈值经验：清单与「踏入轮回」的距离按**屏数**算，不拍像素数。1257px 在 844 高的屏上
约一屏半，第三程本来就长（命题、天赋、灵根、道号都在这一屏），滚一屏半是正常的；
要拦的是「被挤到好几屏之外」。故取三屏为界。
