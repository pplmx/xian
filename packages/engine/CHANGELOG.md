# 变更记录

本文件按"对使用者有影响"的口径记录:接口新增/变更/移除、默认行为变化、判据口径变化。
内部重构(不改接口与数值)不占条目。

## 版本口径(0.x 期间)

- **攒批发布,不按"改完就发"**:初期尤其如此 —— 几十个改动攒成一个版本是常态,
  期间它们都记在下面的「未发布」一节里。tag / release 是**阶段性节点**(给外面的人一个可 pin 的点),
  不是每次改动的日记。
- **版本跟着实际分量走**:默认只加 patch(0.1.7 → 0.1.8 → 0.1.9 → 0.1.10 → …),真有里程碑
  (API 稳定到能做 1.0 的准备、或对外口径变了)才跳 minor,并在本文件写清为什么。
  要的不是"永远停在某个号",也不是"改一次发一次",是编号别起飞、发版有理由。
- **公开面就是承诺**:`src/index.ts` 导出的东西(75 个运行时导出 + 203 个公开类型)被
  `src/publicApi.spec.ts` 逐字钉住。增删都要显式改那份清单,顺带就是一次"这是不是破坏性变更"的自问。
- 0.x 期间不保证 API 稳定:**破坏性变更也在 patch 里发生**,但一定在本文件写明"怎么改";
  数值曲线本身不承诺不变(换题材本来就要调),而**默认值与旧行为**在未显式配置时保持逐位一致。
- 编号对齐说明:`v0.1.2`–`v0.1.5` 四份发布原本被编成 0.2.0–0.5.0(同一天内连跳四次),
  已按上面的口径重新对齐 —— 那几条 tag 只存在了几个小时、没有任何使用者。

## 未发布

- **示例:药庐二十四炉**(`examples/craft-loop.ts`)—— 一条"**技艺 → 采料 → 开炉 → 成品**"的完整小循环,
  把五个此前**没有任何示例**的层串起来:`skills`(技艺:等级曲线 + 每级给什么 + 满级择路)、

  `recipes`(开炉:**材料不足是"没开炉"**、失败按条保料、成功之后才掷双成)。
  实测二十四炉:成功率随技艺从 30% 涨到 65.6%,真开炉 23 次、没开炉 1 次(不扣料不掷骰)、
  成丹 11 颗(双成 1 次)、失败一共退回草药 33 株(保料把"亏"变成"慢"),并直说了一句
  内容作者常忽略的话 —— **灵药是瓶颈:它只出不进地用完了**。

  `Numeric<T>`;并用 `costFn` 演示"接管需求曲线"(给了它,引擎不插值、不缩放)。
  实测:学徒·见习 → 宗师·圆熟 871 天(进阶成功 28 次、失败 14 次、试炼 7 次),
  只把后段倍率 1.7 → 1.2、跨界那一档 3 → 2,**同一种子同一段循环 871 天缩到 660 天**。
  这一份把 `realms` 与 `numeric` 两个模块第一次接进示例 —— 至此 37 个模块全部有示例可用。

- **示例补上三个"只有签名、没有例子"的导出**:`drawMany`(一口气抽 N 张、这一轮不重复)、
  `softChance`(软保底曲线上"下一抽的自然概率",注意签名是 `(base, tries, pity)`)、
  `deltaOf`(只拿两个数比一比,不需要快照)。都不改运行时行为,只是让用法在示例里看得见。

- **新判据:示例覆盖自检**(`scripts/verify-dist.mjs`)—— 每个模块都得有一份示例走到,
  内容包则要求被示例 import 或在 README / 模块速查的装配片段里出现。审计时就是这么发现
  `realms` 与 `numeric` 两块空白的;这条判据把"下次再冒出一块"变成当场红
  (实测:把 `examples/realm-ladder.ts` 移走,自检直接点名这两块)。
  收口口径与"不承诺 75 个导出逐个有示例"的理由一并写进 [`docs/development.md`](./docs/development.md)。

- **新判据:定制表旋钮自检**(同上)—— 「想改什么,改哪里」那张表里凡写成 `a.b.c` 或
  `fn(...)` 的旋钮,末尾名字必须在源码里存在(162 个,逐个命中)。原来的定制表自检只查
  "名字有用例提到",查不出"表里承诺了一个源码里根本没有的开关";那张表就是承诺本身,
  读者会照着写。实测把 `realms.exp.costFn` 改成 `costFnXX` 后自检当场红。

- **组合验收(第八条链):一炉丹药的账**(`integrationCraft.spec.ts`)—— 技艺 → 采料 → 开炉 →
  入库 → 体检,五个此前**没有进过任何验收链**的层(`skills` / `companions` / `crafting` /
  `recipes` / `economy`)。实测 24 炉:采到料 13 炉真开、11 炉因灵药用尽**没开炉**(不扣料也不掷骰)、
  成 5 败 8、双成 3 颗,成功率随技艺 0.30 → 0.45。断言的是跨模块才看得出来的事:
  **没开炉不消耗随机流**(与一颗没被碰过的同名种子比下一个数)、**回执与公式同源**、
  **失败逐条保料**(草药保一半、灵药全赔,账本明细逐笔对得上)、**产出 = 成功 + 双成**、
  **体检与账本同源**(灵药只出不进 → 瓶颈、成品只进不出 → 烂在手里)、**同种子可复现**。
  用例 514 → 521(文件 70 → 71)。

- **修正:成功率算出 `NaN` 时不再传到骰子上**(`realms`)。内容的 `rateFn` 写出 `0/0`、
  表里那一格是空的、道具加成叠出 `NaN` —— 这些以前会让 `breakthroughRate` 返回 `NaN`,
  而 `rng.chance(NaN)` 恒为 false:**玩家"修为满了却永远进不了境",界面上还看不出任何可疑的数**。
  现在按 `recipes` 早已采用的口径处理:NaN 先归 0 再夹取到 `min`/`max`。
  **`±Infinity` 的行为不变**(仍有方向,照旧夹到两端)—— 未显式写出这些坏数的配置,行为逐位一致。
  回归用例见 `realms.spec.ts`(200 次里必须真的掷出成功,不是恒失败)。

- **消融实验(第 28 份):数字什么时候不够用**(`numeric.sim.spec.ts`)—— 补上"该换大数了"这句话的刻度:
  整数安全区到 **2^53**(不是 `MAX_SAFE_INTEGER`:在它上面 +1 还对,从 2^53 起才吞);
  **面板比数字先坏** —— `formatAmount` 在"京"档只留一位小数,同一个 `1.0京` 盖住 499 999 999 999 999
  (1e16 的 5%,约 2.5e14 个可表示数);首层 100 的曲线每层 **×1.5 到第 80 层、×3.2 到第 28 层**
  就会越过安全区;`1e308 × 10` 直接变 `Infinity` 而不报错。正面判据是"换过去真的能用":
  一份 **30 行**的 `Numeric<bigint>` 喂给同一个 `createRealmSystem` 配置,公式与内容一行不改,
  22 境 × 10 层那张表最深一格从 `2.15369396307555808960e+26` 变成精确的
  `215369396307555776631074700`。顺带钉住 `clamp(NaN, lo, hi)` 仍是 `NaN`。

  ③**见证不漏**(见过的 uid = 掉出来的 uid,收不收都算);④**容量不越界**;
  ⑤**面板单调**(换上更好的装备核心值不降,且明细之和 = 面板值);⑥**可复现**(同种子两遍逐字段一致、

  | 存档编解码 | 357 次/毫秒 | 十万个档约 **0.3 秒** |

  另一款作品常常是"按序掷,第一个命中即用" —— **随机流从此完全错位**,这不是调参数能对齐的。
  现在:返回一个技能 = 用它、返回 `null` = 这一回合不出技能、不返回 = 交回默认;
  钩子里拿得到本场的随机源与技能表,"按序掷"这类规则写得出来;
  · **`strikeFn`(整次出手怎么打)**:`damageFn` 只管"伤害怎么算",这一条管**整次出手的先后**
  —— 先掷浮动还是先判暴击、闪避怎么定、吸血何时结算、日志写成什么样。返回 `true` 即归你
  (用 `ctx.applyDamage` 落账,它返回的量就是这次出手的返回值 —— 反击 / 追击 / 钩子串联都靠它)。
  · **`actFn`(整回合交给作品)**:前两处管"出哪一招""怎么打",这一条管**节奏** ——
  回合开头回血还是回合末回、法宝每 N 回合的节拍、震慑什么时候清。返回 `true` 即这一回合
  归你(引擎不回血、不选技能、不出手);引擎保留的只有**回合调度与生命周期**
  (谁先手、几回合、何时分出胜负、事件怎么记)。
  三条都沿用库既有的钩子形状:**不配就完全不走**(默认路径逐位不变,连骰子数都不变),
  返回"没处理"也照旧走默认。
- **实测:接上三处主权之后,库能完全复刻本作那一格战斗**。均势·无技能场景 × 200 颗种子,
  把本作的口径整段写进钩子(先掷浮动再判暴击、减伤 = 防/(防 + 攻×1.15) 封顶 75%、
  每回合按默认打一记):**胜负与回合数 100% 相同**(默认配置同一格是 75%)。
  过程里最有价值的一条是**为什么第一次没对齐**:本作每次出手之后还会掷三颗骰子
  (反击 / 追击 / 震慑),**词条是 0 也照掷** —— 少了这三颗,后面所有随机都对不上。
  这与掉落层"保底照样掷骰"是同一条纪律:随机流的消耗个数本身就是契约的一部分。
- **复杂那一格也对齐了**(带技能 + 护盾 + 反击):同 200 颗种子下**胜负与回合数 100% 相同**
  (默认配置 58%)。这条路上卡过一次,两个原因都值得记下来:
  ① 复刻时**少掷了"没用上"的骰子**(出手后那三颗:反击/追击/震慑,词条为 0 也照掷);
  ② 后来一致率停在 92%,根因是**我把一部分写重了** —— 主权版的 `strikeFn` 自带 `CRIT_BASE`,
  而场景里又套了给"用库默认暴击"那份对照准备的 +0.05,暴击率成了 0.30 而本作 0.25。
  教训:**整段接管时要连"这一部分是谁加的"一起搬**,别让两边各加一次。
  本作暂不接管(战斗维持原样,见 DEC-119);这三处是给"想把整段战斗接过来"的作品留的。

版本 0.1.7 → 0.1.8(只加 patch,按上面的版本口径)。下面按"对使用者有影响"的口径逐条记。

- **软保底多了"从第几次开始涨"**(`SoftPity.from`,默认 1)。上一版只写了"每多一次加多少",
  而抽卡作品最常见的写法是**从第 75 抽起才开始涨** —— 之前只能由调用方自己减窗口,现在
  写成 `{ step: 0.06, cap: 0.6, from: 75 }` 就完了;不写 `from` 仍是"第一次就算一份"
  (本作的照面次数保底正是这种),故默认行为不变。
- **消融实验:保底把出货变成了什么样**(`pity.sim.spec.ts`,两万次抽取/档)。拿一份典型内容
  (基础 0.6% = 自然期望 167 抽)实测:

  | 内容 | 平均 | 中位 | 九成位 | 最差 |
  | --- | --- | --- | --- | --- |
  | 只有基础概率 | 165.7 抽 | 114 | 381 | 1621 |
  | 配 90 抽必出 | 69.4 抽 | 90 | 90 | 90 |
  | 再加软保底(第 75 抽起每抽 +6%,封顶 0.6) | 62.7 抽 | 77 | 81 | 89 |

  三条结论:①**硬保底是硬上限**(两万次里最差也就是 90 抽,这是判据不是大概);
  ②**保底把期望拉低一半以上**(167 → 69),这就是为什么"有没有保底"是玩法层面的事而不只是
  数值微调;③**软保底不封顶就等于偷偷换成硬保底** —— 同一份曲线若不封顶,第 92 抽的概率
  已经算到 1(必出),封顶 0.6 时那一刻还只是 60.6%(还是概率)。另有一条结构性质被钉住:
  保底没触发之前,随机流与"完全没有保底"逐抽相同,触发那一次也只是改写结果(照样掷骰)。
- **一次性解锁(成就 / 里程碑 / 勋章 / 教程节点)**有了骨架:`createUnlockRegistry({ entries })` ——
  与周期任务板、顺序任务链是一家人,区别只在**记多久**:任务板每隔一期重来,任务链一路往前,
  而这一层**一辈子只记一次**。四条口径:① **只登记一次**(重复解锁、重复扫描都不再发生 ——
  玩家最恨"同一枚跳两次""奖励发三遍");② **一次扫描可解多条,顺序即声明顺序**
  (一口气满足好几条是常事,奖励与战报顺序必须稳定);③ **未达成的不登记**;
  ④ **显式解锁同样去重** —— 有些成就没有可判定的条件(寿元低到某个比例、身上恰好带着某件
  东西),只能由**当时发生的动作**声明,而这类声明常常来自每拍都跑的检查,少了去重就会
  每拍发一次奖。另有 `has / list / count / remaining`:读数与解锁共用同一份账,
  认不出的旧 id 在列表里跳过(不让它把成就墙炸了)。
  本作的 62 枚成就已改走它(`core/engineUnlocks`):解锁顺序被记下来(成就墙与履历按它排),
  去重从 store 里的一行 `includes` 收进库的登记簿。
- **抽取保底(软保底 + 硬保底)**有了骨架:`softChance(base, tries, pity)` 与
  `createPityCounter({ hardAt?, resetOn? })` —— 掉落层管**单次判定**,这里管**跨次数的那本账**:
  ① **软保底要涨,也要封顶**:见得 / 抽得多了概率该涨(本作"照面次数保底"就是这条),
  但涨幅必须封顶 —— 否则后期概率被抬到 1,"越看越眼熟"就变成了"第 N 次必认出",中间那些
  次数的意义全没了;上下限同样要有(最难的那一味也留 4% 的一线,最容易的封在 90%);
  ② **硬保底 = 第 `hardAt` 次必出,而且照样掷一次骰子**:保底是**改写这一次的结果**,
  不是跳过随机(与掉落层同一条纪律) —— "开不开保底"不该让后续随机流整体错位;
  ③ **什么时候清零是内容的选择**:出货就清(默认 `resetOn: 'hit'`)与只在保底顶出来之后才清
  (`'pity'`:自然出货不消耗保底额度)两种作品都有,故写成配置;池子各记各的计数,
  换池 / 活动结束可手动 `reset`。
  本作的"照面次数保底"已经改走 `softChance`(见 `core/loreService`):辨识概率与药性概率
  逐点不变,但涨幅封顶与上下限这两条从"每一处都记得写"变成了库里的一句话。
- **示例:自习室的一天**(`examples/quest-loop.ts`)—— 把任务系统的三块串成一个可跑的小循环:
  计数器与基准快照(生涯与本期共用一份计数)、今日三件(`createTaskBoard`,按当日增量结算、
  换期幂等)、主线三节(`createChain`,一次结算连推三节)、一次性成就(`evalGoal` + 一次性解锁)。
  整份程序**没有一个字提到修仙**,并且进了 `bun run examples` 与独立成库自检的示例检查 ——
  "换掉名字与数字就是另一款游戏的任务页"这句,是跑得起来的。
- **顺序任务链(主线 / 章节 / 教程指引)**有了骨架:`createChain({ nodes, done, maxSteps? })` ——
  与周期任务板是一对:那个问"这一期干了多少",这个问"走到哪一节了"。四条口径:
  ① **一次结算可以连推多节**:玩家一口气满足后面几节是常事(一次大提升、一次离线回来),
  每次只推一节会让人看到"明明达成了却卡着不动",要等下一次事件才开始下一节;
  ② **推进必须有上限**(默认 5 节):内容写错(条件恒真)或坏档时,没有守卫的循环会一帧
  跳完整条链、甚至卡住渲染帧;而且撞上守卫要能**说出来**(回报 `capped`)——
  只把事故藏起来,下次还会再犯(本作撞上时会 log 一行,便于查内容);
  ③ **推进不可逆**:走到第 N 节就是第 N 节(回退 / 跳级都是另一件事);
  ④ **到链尾就停**:没有下一节时既不推进也不报错,通关是正常状态。
  条件由内容给(`done(node, ctx)` —— 库不认识境界、计数、物品),故同一套骨架既能做主线,
  也能做教程步骤、章节解锁、成就阶梯;`advance` 回报"走过的节点 / 停在哪 / 到没到头 / 撞没撞守卫"。
- **计数器基准快照**独立成一组原语:`snapshotOf(counters)` / `deltaOf(base, now)` /
  `deltaSince(base, counters, key)` —— 「今日斩妖 15」「本世斩敌 400」「本赛季攒够 10000」
  都是同一个问题:**一个只增不减的计数器,怎么同时回答"生涯一共多少"与"这一段多少"**。
  答案不是清零(清零会把生涯成就一起抹掉),而是**打基准快照**:起算那一刻把计数器原样
  记一份,这一段就是 `当前 − 基准` —— 同一份计数器同时回答两个问题,而基准是死数据,
  不需要任何地方记得"顺手加一"。两条边界也定在这里:增量夹到 ≥ 0(回档 / 坏账倒挂不给
  负进度,"够不够"的判定也不会变成永远为真)、缺基准按 0 起算。周期任务板(`tasks.ts`)
  改用这组原语,作品自己的"本世 / 本赛季 / 本次活动"也该用同一份 —— 同一条减法不要
  在三处各写一遍、各漏一次夹取。
- **周期任务板(每日 / 每周 / 赛季 / 打卡)**有了骨架:`createTaskBoard({ tasks })` ——
  它靠**计数器增量**推进(kills / 学习时长 / 步数……),而这里有三处是真踩过坑的:
  ① **进度是"当前 − 期初基准",不是"把计数器清零"**:计数器往往还要喂生涯成就
  (「累计击败 1000 个敌人」),换期清零会把生涯成就一起抹掉 —— 正确做法是换期那一刻给
  计数器打个**基准快照**;② **换期必须幂等**:引擎每次心跳都问一句"该换期了吗",
  若无条件重设基准,玩家同一天里第二次触发就**把当天已经攒下的进度清掉了**
  (白天打了一半、晚上再开游戏,进度归零);③ **增量夹到 ≥ 0**:回档 / 坏档让
  "当前 < 基准"时不该出现负进度(界面会显示负数,判定还会变成永远为真)。
  另两条:`claimed` 保证一期一次(自动结算 `settle` 与手动领取 `claim` 共用同一份记录,
  两条路一起用也不会重复给);结算顺序即声明顺序(一连完成三条时,奖励与战报顺序稳定)。
  本作迁移前的一天任务是**自动发放**,故这里以 `settle` 为主:`claim` 的未成原因用
  结构化码(`unknown` / `claimed` / `unfinished`),说法由作品定。
- **投资点(天赋 / 科技 / 属性点 / 灵脉)**有了骨架:`createPointPool({ branches, total, mainCap, sideCap, ... })`
  —— 加点系统看着只是"点数够就 +1",真正决定手感的是四条结构规则,而它们都踩过坑:
  ① **总容量与分支上限是两把尺子**:容量让"方向"有意义(投满就没了),主/副两档上限让
  主位更深、副位更浅;两把尺子的**判定顺序即界面的说法**(先报"容量已尽"还是先报
  "这条到顶了"),三句说法都由内容给(`fullReason` / `mainCapReason` / `sideCapReason`);
  ② **主位可换,但换位不作废已投点数**:落在主位的点数超过副位上限时,只封住"再投",
  已经有的照旧生效 —— 反过来做(读取时按上限截断)等于悄悄没收玩家的投入;
  ③ **没投成不该改变任何东西**:门槛没过 / 容量满了 / 钱不够,状态原地不动,尤其"首次
  投点自动认主"这条便利规则**只能在投成功的那一次生效**(本作迁移前正是反例:点了却没
  灵石,主脉被悄悄定在没投成的那条脉上 —— 这次一并修正,并在对账用例里写明);
  ④ 效果是"点数 → 效果"的函数,库不解释,原样带出给作品自己的属性汇总。
  门槛与费用也由内容给(费用数额是泛型,本作的灵石是大数);`blocked` 返回 `''` 表示
  "不说理由"(整块玩法还没开放时,界面本来就不显示)。
- **设施(建造 / 升级 / 每小时产出)**有了骨架:`createFacilitySystem({ facilities })` 与
  `accrue(frac, rates, sec)` —— 洞府建筑、书房与台灯、工厂与产线都是同一套骨架:
  ① **"能不能升"要能说出为什么**:门槛不止一条(解锁条件 / 自身品类上限 / 被别的东西
  卡着 —— 本作是"其余建筑受洞府等级所限",洞府自己不受此限),而**判定的先后即界面的
  说法**(先报"境界不够"还是"已至顶层",玩家看到的是两句不同的话),故门槛由内容给函数
  (返回一句人话或 undefined),顺序也由内容定,库只保证"能升"与"要花什么"出自同一次判定;
  ② **等级上限取小,而且只封升级**:自身上限与别人给的上限取小(`cap` + `capReason`),
  已有等级不会被改小(降级是另一回事);③ **每小时产出要留小数**:一秒一拍地取整会把零头
  丢光(本作 1.5 悟道点/小时、2.4 玄铁/小时,取整后永远发不出来)—— `accrue` 按**秒**
  推进、速率按**每小时**给(除以 3600 由库做),零头留在累加器里,够了整数才发,
  且**累加器里已经攒着的零头也要看一眼**(设施拆了也得把它发出去)。
  花费(键名与数额)与效果(`mods`)库都不解释,原样带出给作品自己的账本与属性汇总;
  费用数额是泛型 —— 本作的灵石是大数。
  「书桌与日常」那份示例又多一层:书桌与台灯(门槛给一句人话、上限由书桌定、开灯 50 分钟
  只发 1 点专注而零头留着接着攒)。
- **状态 / 时效增益**有了骨架:`createBuffSystem({ defs, stacking?, clock? })` ——
  丹药增益、事件祝福、负面状态、限时加成都是同一套骨架,而它有五处真踩过坑:
  ① **重复施加要"叠时长",不是"刷新"**(`Math.max(旧到期, now + 时长)` 看着稳妥,实则把
  剩余时长清零重算 —— 增益还剩 20 分钟时再服同一味药,那 20 分钟直接被吞);默认口径
  `stacking: 'extend'`:剩余 + 新时长,另有 `'longest'` / `'reset'` 备选;
  ② **已过期的旧实例以 now 起算**,不把负剩余叠进来(离线一晚上回来必踩);
  ③ **生效与清理共用一个判据**(到期时刻严格大于 now),省得一处 `>` 一处 `>=`,
  在"正好到期"那一帧飘出幽灵状态;④ **"清除负面"只认分类**(`clear(list, kind)`),
  库里不认识什么是负面,并回报剪掉几条;⑤ **快照带上"下一次变化在什么时候"**
  (`nextExpiry`),面板重算与倒计时不必各自再遍历一遍。
  另:效果(`mods`)库不解释,原样带出给作品自己的属性汇总;时间单位由调用方声明一次
  (`clock: 'sec' | 'ms'`)—— 内容表写秒、运行时时钟是毫秒,少写一次 ×1000 就差一千倍。
  「书桌与日常」那份示例也顺手用上了一层:自习的「专注」叠时长、熬夜的「瞌睡」按分类清掉、
  连上四节封在上限、下一次状态变化在什么时候 —— 依然没有一个字提到修仙。
- **掉落表**有了骨架:`createDropTable(entries)` —— "这一场给不给、给几份"。看着只是几条
  `if (rng.chance(...))`,但两处是真栽过跟头的:①**概率必须先钳到 [0,1]**(还可 `chanceCap`
  另设上限,如"再高也不超过 90%"):`rng.chance(p)` 是 `rand() < p`,而 p 是基础概率 × 福缘 ×
  首领 × 词条 × 活动叠出来的 —— 一旦叠过 1 就变成"必然掉落",界面上完全看不出来;
  ②**保底要能表达**("首领第一抽必出"),写成条目上的 `guaranteed` + 调用方的 `guarantee`
  开关(默认关),而不是 `||` 短路;且**每次尝试照样掷一次骰子**,开不开保底都不改随机流。
  另三处口径:翻倍翻的是**份数**(`countMult` 默认不改掷骰次数,要"多抽一次"得显式开
  `scalesWithAttempts` —— 本作的装备掉落正是这样)、`count` 支持闭区间且**只在命中时**才抽,
  **顺序即声明顺序**;命中当场处理(`onHit`)是给"生成装备、抽内容池"这类自己还要掷骰的后续
  动作留的位子,免得它们挤到别的判定后面。
- **结算回执**有了骨架:`createSettlement({ resources }, numeric?)` —— 掉落 / 任务奖励 / 活动补发
  都要同时回答"给了什么"(界面)与"实际到账多少"(账本),而这两件事各算一份就会出那个最招骂的现象:
  界面写"本次所得 120",行囊只多了 100。这一层把**实际入账**做成回执的唯一来源
  (取自 `resources` 落账时的实际发生额),被上下限夹掉的差额另给一栏 `clipped`,
  于是"同源"不再靠自觉 —— 想显示别的数,得先绕过回执,那是显式的越界。
 - **入库漏斗**有了骨架:`createIntake({ holding, accept?, evictable?, fallback, witness? })` ——
  "一件东西来了,收不下怎么办"。掉落、事件奖励、任务发放、邮箱领取的顺序都是同一套,
  而且每一处都踩过坑:①**先见证,再谈收不收**(本作的图鉴收录挂在唯一漏斗上 ——
  若在裁决之后才记,"化尘掉的那件"就不算见过);②**先问裁决**(自动回收命中就不进包,
  而总闸关着时一律照收);③**满了先尝试腾位**(只有值得留的新件才挤掉最该走的,
  且**腾位失败不追回** —— 已经折算的就是折算的);④**同一件东西在各条去路(被拒 / 被挤掉 /
  收不下)走同一条折算账**;⑤回执带人话与原因(`rejected` / `full`),界面直接显示。
  各条去路的判断由作品给函数,库只给顺序。
- **经济读数**有了骨架:`createEconomyReadings({ bands?, labels? })` —— 有一本账之后,
  下一个问题总是"**哪一样不对劲**"。这一层把读数从账里分出来,三条都有踩过的坑:
  ①**比值而不是绝对值**,且**出为 0 时是无穷**(东西只进不出 = 烂在手里,不是"刚刚好" ——
  这一条写错,任何没有出口的资源都会显示成健康);②**判词分档,阈值归作品**
  (默认 0.7 / 3 / 10 来自一款在运营作品的实测口径:低了瓶颈、高了过剩、再高纯噪音;
  判词名默认是档位 id,可换成作品自己的说法);③**没把握就明说**:模型没覆盖的出口带一句
  `note`,既不算健康也不算事故。附 `series`(按时代 / 赛季分期读)与 `summary`(各档各有哪些)。
- **世界记忆的档位**有了骨架:`createStageMemory({ stages, decayAfterHours? })` ——
  阵营好感、地区繁荣、门派声望这类"因为你做过什么,这里变成了什么样"的骨架,规则比看上去绕:
  ①**多路门槛取先到**(本作:打赢 30 场**或**守满 6 小时都算稳定 —— 只认计数的话,
  镇压之后不再产胜场,"守得住"就永远算不出回报);②**有资格才谈得上高档位**
  (没镇压过的地界再能打也只是混乱);③**会回落**(默认 48 小时不打交道退回低档 ——
  世界的记忆不是只增不减的计数器);④**钟的起点是"最后一次打交道"**(战斗 / 镇压 / 通关取最晚)。
  另有 `hoursUntil` / `idleBeyond`:倒计时与"够钟了吗"共用同一个阈值,不另立一份口径。
- **图鉴 / 见闻**有了骨架:`createCodex({ stages, stagesOf? })` —— 图鉴不只是"收没收录"两态,
  库给三条路与它们的边界:①**累计照面升档**(够门槛进一层,**一次只进一层** ——
  一场战斗不能一夜跳两级;首领之类的稀有对手可以另配一张门槛表);
  ②**按概率升档**(见得多不等于认得出:概率由作品算,库只负责"掷一次,进了就进");
  ③**用过才算真懂**(由行为直接推开到某档)。推进**不可逆**,档位只增不减。
  另附"**只记见过的最好一件**":各维度**各取其高**(品质与层级各记各的 ——
  「15 阶天品与 20 阶良品谁更好」没有定义),且与当前是否还持有无关(化了尘也是见过);
  还有"这条还差多少到下一档"的读数与"已知几条 / 共几条"的进度。
- **抉择(事件选项 / 任务分支 / 商店讨价)**有了骨架:`createChoiceSystem({ interpret })` ——
  库给四件事的顺序与边界:①能不能选(`available` 可以返回一句"为什么不能",界面直接用);
  ②后果**按权重掷**(同一句"伸手去拿"可能拿到、也可能被烫);
  ③后果由若干条效果组成,而**效果由作品解释**(库不认识"灵石 +50""悟得一门功法",
  它只逐条问 `interpret`,并把每一行说明收成**回执**);④玩家没选时的**三级兜底**
  (默认且可选 → 第一条可选 → 第一条),离线结算与界面超时共用这一处。
  边界也定了:权重全为 0 取第一条、没有后果也能结算、效果"没发生"只算跳过不影响其余条目。

## 0.1.7 — 2026-09-19

这一批是"把装备与时间这两侧补齐"的一次集中交付:洗练、自动去留、周期,外加一份第二种题材的
完整示例;另附一次**消融实验的结论**(库的战斗定位)。

- **周期(天时 / 每日 / 赛季)**有了骨架:`createCycleSystem({ periodSec, pools, pick?, seedOf? })` ——
  把"每隔一段游戏时间世界换一种样子"里最容易踩坑的四条写进实现:
  ① **确定性**(由周期序号派生**独立**随机源,不消耗全局随机流 —— 否则"今天是什么"取决于玩家此前掷过多少次骰子);
  ② **不依赖现实时间**(序号来自游戏内时长,改系统时间 / 跨时区 / 离线一晚都不变);
  ③ 分段换池(界域 / 赛季 / 等级段,由调用方给"当前用哪个池");④ `remainingSec` / `schedule` 让界面能预告。
  `pick` 与 `seedOf` 都可接管,便于已上线的作品**换到这一层而每一天不变**。条目本身(叫什么、权重多少、加什么成)是内容。
- **第二种题材的完整小循环**:`examples/daily-loop.ts` —— 「书桌与日常」,一次用上
  资源(上限 / 取整 / 收支带来源)、离线(时间账 → 逐步产出,到顶就不再进)、
  持有(文具盒容量与占位)、分流裁决(放学自动清理 + 读数)四层,而且**没有一个字提到修仙**。
  它进类型检查与两份自检(和另外三份示例一样,跑不起来就先红)。
- **自动去留(分流裁决)**有了骨架:`createTriage({ rules, skip?, fallback? })` ——
  **有序规则链**(第一条表态的说了算,谁都没表态才用兜底)+ **按同一条链算的读数**
  (`impact`:留下几件、扔几件、每条规则各判掉多少)。规则判据与文案都是内容;
  库给的是"顺序说得清、数字看得见"这两件事 —— 自动回收翻车最多的地方正是这两件。
  附 `compareBy(...comparators)`:"行囊满了先挤掉谁"那类多级排序的骨架。
- **洗练 / 重铸**有了骨架:`equipment.rerollAffixes(affixes, { rng, quality, tier, slot, keep, count })` ——
 保留你指定的(封存 / 锁定)、其余换成新词条与新掷点;**与 `generate` 共用同一处掷词条的实现**
 (池子、门槛、权重、数值曲线都是同一份配置),所以"掉出来的"与"洗出来的"不会有两套口径。
 纯函数:入参不动,品质 / 层级 / 部位也不动。目标条数取"品质区间"与"`keep + 1`"里较大的那个,
 尽量每次至少给一条新的;池子被门槛排空时只保留你指定的那些(要不要允许"洗了等于没洗"由作品的代价决定)。

**一次消融实验的结论(库的战斗定位)**

拿库的战斗按某款在运营作品的口径尽量配好,同场景 × 200 颗种子对比:量级接近
(均势场景胜率 83% vs 85%、38% vs 38%),但**同一种子下的胜负只有 75% / 58% 一致** —— 不可互换。
差异不在"钩子不够",而在伤害公式的形状、一次出手的顺序、技能选择消耗的随机流、以及作品自有的那批词条。
故库的战斗保持**"给没有战斗实现的作品一套开箱骨架"**的定位,不承担复刻某个上线作品战斗的义务;
真要统一,缺的是 `skillFn` / `strikeFn` 两处**主权**(整段交还给作品),而不是更多参数。

## 0.1.6 — 2026-09-19

**补上"手里那一堆"这一层:持有(`holding`)。**

装备系统管的是"怎么生成、属性怎么算",但**玩家手上那一堆**是另一件事:按 uid 找、
背包满了收不进、删一件要顺带从装配里摘掉、替换一件是同 uid 覆盖。这几件事每个游戏都要写一遍,
而且写得都不一样(尤其"什么算占位"这一条)。这一层补上它。

- `createHoldingSystem<TItem>({ capacity, counted })`:库只要求每件有个 `uid`(身份),
  于是同一层能装装备、丹药、法宝、卡牌、宠物、图纸……**它不知道你持有的是什么**;
- `capacity` 给函数就每次现算(洞府升级 / 行囊扩展);`counted` 决定"哪些件占背包位" ——
  最常用的写法是"**已装配的不占**"(把装配表交给它判断);
- `add` / `addMany`(满了返回 `full` 而不是替你决定折算成什么;`force` 收不占位的件)、
  `remove` / `removeMany`、`replace`(强化 / 重铸是同 uid 覆盖)、`find` / `has` / `indexOf` /
  `count` / `spaceOf` / `isFull`(全是纯函数,入参不被就地改);
- 装配联动:`assign` / `unassignSlot` / **`unassignUid`**(把某件从**所有**槽位摘掉 ——
  删装备时不做这一步,装配表里就会留一个悬空 uid)/ `assignedUids`。

**又一处"第一个用户"照出来的东西**:uid 是身份,**重复的件会被拒收**(`duplicate`)。
旧口径会照收 —— 而 uid 由生成器产出,重复只可能来自坏数据,故这是有意的收紧。

判据:持有层 8 条用例(容量 / 占位 / 现算容量 / 重复 / 取走替换 / 装配联动 / 批量);
使用方那边另有 6 条**冻结旧实现**的对账(容量边界、满了收不进、删件顺带卸下、替换、装配表)。

## 0.1.5 — 2026-09-19

**资源层被第一个真实使用场景磨了一遍。** 本作(第一款拿库定制的游戏)把自己的资源层接到库上时,
一上来照出两个缺口 —— 这一版都补了:

- **大数台账**:台账值走 `Numeric<T>`,但收支条目此前只收 `number` —— 于是"灵石"这种
  1e40 量级的资源根本加不进去。现在 `ResourceEntry<T>.amount` 收 `number | T`,
  `AppliedEntry<T>.applied` 与 `ResourceSummary<T>` 也随台账走;
- **整数资源**:`ResourceDef.integer` —— 材料 / 点数是整数(「灵草 ×2.5」没人看得懂),
  货币常常带小数;取整发生在夹取之后,口径由定义里那一个布尔值定;
- `gainSmall` 这类"只动一个键"的调用不再要求传全量台账(`Partial` 即可)。

顺带把口径写进文档:**收支条目用普通数字,台账用 T** —— 与 `victoryRewards[].amount`
等既有约定一致,大数实现者不必在每个调用点都构造一遍 T。

## 0.1.4 — 2026-09-19

**补上最后一块地基:资源账本(`resources`)。**

等级、属性、装备、副本、战斗、技能、炼制、伙伴、目标、内容池、离线时长账、存档 —— 这些库里都有,
唯独"灵石 / 信用点 / 零花钱"这一层没有,于是每个拿库的人都要在库外面重写钱包、上限、买得起买不起。这一版补上它。

- `createResourceSystem({ resources })`:`ResourceDef { key, name?, cap?, floor? }` ——
  键名与展示名分开,上下限逐个给;**上限还能随账本变化**(`capFn`:洞府升级 / buff 加成);
- `create(initial)` / `of` / `numberOf` / `normalize(raw)`:建账、读数,以及**形状修复** ——
  存档里坏了那一格按定义兜回来(缺的补 0、非数的当 0、越界夹回、未知键原样留着),不让整个档报废;
- `pay(ledger, costs, { partial? })`:默认**整笔要么全成、要么不动**,失败时返回缺口
  (`[{ key, short }]`);要"先付得起的部分"就显式开 `partial`;
- `grant` / `apply(ledger, entries)`:逐条落账,上下限在**落账时**夹取(而不是事后修补);
  坏条目被跳过并记进 `rejected`,不让一条脏数据炸掉整场结算;
- 每条收支都能带 `source`;`audit(entries)` 按资源与按来源各汇总一份(收入 / 支出 / 净额),
  明细恒等于合计 —— 这条由用例钉着;
- `produce(ledger, steps, perStep)`:按步产出,**逐步**夹上限,直接接 `idle` 的步数账
  (一次乘完再加是算不出"挂机中途到顶"的);
- 落账是纯函数:入参账本不被就地改;数值走 `Numeric<T>`,大数实现照旧可插。

**同一版里,战斗补了两个小口子**(写"组合技示例"时探出来的):
`shieldbreak` 事件(护盾被击破的那一刻,否则钩子只能去猜)、`gainShield` 收负数(扣盾,
表达"濒死治疗增幅但护盾消散一半"这类有得有失)。

**附赠一份探路示例** `examples/combo-arts.ts`:用库的钩子把三种真实战斗的机制
(破盾反震 / 满血会心追击 / 濒死治疗换护盾)各写一遍 —— **一行规则都没进库**,只用了
"破盾了 / 会心了 / 每回合结束"三个落点。它同时回答"库的接口够不够表达真实战斗"这个问题。

判据:新增 8 条资源用例(买不起不扣、上下限夹取、动态上限、逐步产出、审计恒等、形状修复、
纯函数与坏条目),战斗 21 → 23;示例进类型检查与两份自检。

## 0.1.3 — 2026-09-19

**给"内容驱动"的东西一套接口形状,但不实现它们的规则。**

- `BattleConfig.tickFn(ctx, rng)`:每回合结束叫一次。流血 / 中毒 / 灼烧、增益层数递减、冷却、
  首领的阶段阈值检查都有了落点;`ctx` 给的是同一套原语(出手 / 落账 / 加盾 / 治疗 / 定身 / 日志)
  加一个本场抽屉 `state`;
- `BattleConfig.onEvent(ctx, event, rng)`:引擎每记完一条事件交给你看一眼 ——
  会心即追加一记、破盾时触发法宝、挨打时回一口,都在这一个钩子里;
- **防递归**:钩子自己引发的出手与日志不会再触发 `onEvent`(否则"会心追加一记、那一记又会心"
  会指数膨胀)。判据里有一条专门盯着这件事。

**三样留在作品那一侧**(库只给形状,不给规则):**流派组合技**、**法宝自动触发**、**首领阶段** ——
它们绑内容,塞进库里等于把某个游戏的设计当成通用规则。README 给了三者的写法。

判据:战斗用例 18 → 21(回合钩子按层数累计掉血、事件反应不级联、不配钩子时结算与从前逐位一致)。

## 0.1.2 — 2026-09-19

**战斗从"够用的骨架"加厚一档** —— 护盾池、反击、追击、技能标签的通行解释,
全部**默认关闭**:不配,行为与 0.1.x 逐位一致。这四样是从一款在运营作品的战斗里抽出来的骨架

- `SkillEffectContext` 新增 `shieldOf` / `gainShield` / `heal`;`strike` 支持倍率、自定义标签与穿甲;
  新增事件类型 `counter` / `combo` / `shield`;`BattleResult` 增加 `playerShield` / `enemyShield`。
